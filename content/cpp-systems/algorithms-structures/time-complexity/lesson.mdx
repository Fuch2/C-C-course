## Теория и инвариант

Время на часах зависит от процессора, компилятора, кешей, планировщика и самих данных. Для анализа сначала выбирают размер входа n и модель стоимости: например, одно сравнение ключей считается одной операцией. Это позволяет сравнить рост работы независимо от конкретного ноутбука. Если ключ — строка переменной длины, само сравнение уже не обязательно O(1).

Лучший, худший и средний случаи — разные функции. Линейный поиск может закончиться после одного сравнения, а при отсутствии ключа просмотрит всё. Средний случай требует распределения входов. Суммируйте последовательные участки; перемножайте вложенные только с учётом реального числа итераций. Наличие двух циклов в тексте не означает квадратную сложность.

## Пошаговый разбор

Два последовательных прохода по 4 элементам дают 4+4=8 посещений. Вложенные проходы по 4 дают 4×4=16.

## Реализация и запускаемый пример на C17

Пример не требует stdin. Сначала предскажите результат; затем выполните код и измените данные. Функции демонстрируют алгоритм, а практика ниже требует самостоятельного ввода и обработки граничных состояний.

```c
#include <stdio.h>
#include <stdlib.h>
#include <stdint.h>
#include <string.h>
#include <limits.h>


int main(void) {
int count=0;for(int i=0;i<4;++i)for(int j=0;j<4;++j)++count;printf("%d\n",count);
return 0;
}
```

Ожидаемый вывод:

```text
16
```

## Почему реализация корректна

Для n=4 два последовательных прохода дают 4+4=8 посещений. Если второй проход находится внутри первого и каждый раз проходит весь массив, получаются 4×4=16 пар. Для n=8 это уже 16 и 64. Рост входа вдвое увеличил первую работу вдвое, вторую — вчетверо.

Сначала определите единицу работы: сравнение, чтение элемента или копирование. Стоимость вызова scanf и выделения памяти нельзя незаметно приписать сравнению ключей. В benchmark-задаче считаются только оговорённые события. После подсчёта можно отдельно измерить время, однако секунды не заменяют формулу: два процессора выполнят одно число сравнений за разное время.

## Сложность и память

| Время         | Два прохода: Θ(n); декартово произведение: Θ(n²).           |

Размеры в учебном коде ограничены ради безопасного запуска. При анализе представляйте масштабируемый вариант той же структуры; фиксированный тестовый предел не превращает любой алгоритм в полезное «O(1)».

## Cache locality и компромиссы

Два прохода по горячему массиву могут быть дешевле одного прохода по разрозненным узлам. Модель посещений не моделирует все задержки.

Счётчик воспроизводим, но упрощает оборудование; таймер реалистичен, но шумен. Используйте оба инструмента для разных вопросов.

Практическое применение: Оценка, выдержит ли обработчик пакет в тысячу или миллион измерений.

## Практическое задание

Ввод n (0…1000). Двумя последовательными циклами подсчитайте 2n посещений, затем вложенными циклами — n² пар (i,j). Выведите оба счётчика. Это измерение операций, а не времени.

В практике доступны стартовый код, примеры, публичные тесты и подсказки. Эталонное решение и разбор открываются по подтверждённому запросу. Оценивание не раскрывает входы скрытых тестов.

## Benchmark-задача

Ввод n (0…256) и target (−1…1000). Массив задан формулой a[i]=2\*i. Посчитайте сравнения a[i]==target линейного поиска с ранним выходом и сравнения a[mid]&lt;target в lower_bound. Финальную проверку равенства после lower_bound не учитывайте. Выведите два счётчика. Это воспроизводимая модель работы, не замер времени.

Выберите «Benchmark: сравнения линейного и двоичного поиска» среди заданий во вкладке «Практика». Сравните отсортированный, обратный, пустой и обычный вход там, где они применимы. Счётчик отвечает на вопрос об объёме работы; секунды зависят от машины и сборки.

Для отдельного эксперимента со временем подготовьте одинаковые входы до начала замера. Используйте clock() вокруг исследуемой операции, проверяйте результат на (clock_t)-1 и делите разницу на CLOCKS_PER_SEC с преобразованием к double. Выведите контрольную сумму результата, чтобы компилятор не мог просто удалить неиспользуемую работу. Короткую операцию повторяйте в пределах timeout: нулевой отсчёт может означать недостаточное разрешение часов.

Сделайте прогрев и несколько замеров с переменой порядка вариантов. Сравните медианы и разброс, запишите компилятор и режим сборки. Диагностику ASan/UBSan проверяйте отдельно: её накладные расходы искажают сравнение обычных реализаций. Поле времени всего запуска в интерфейсе не заменяет время операции. Никакое фиксированное ускорение не требуется для зачёта.
