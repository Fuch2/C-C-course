## Цели обучения

- Объяснить, почему ресурс освобождается парной операцией своего API.
- Проследить на MemoryDiagram вызов deleter ровно один раз при перемещении и reset.
- Реализовать deleter с заимствованным счётчиком и проверить порядок объявления жизней.

## Модель и назначение

Ресурс должен освобождаться парной операцией своего API: new/delete, new[]/delete[], malloc/free, fopen/fclose, библиотечные create/destroy. Пользовательский deleter сохраняет RAII для ресурса, который не удаляется обычным delete. В unique_ptr&lt;T, D> тип deleter входит в тип владельца — способ освобождения не может потеряться при передаче. Deleter может хранить состояние: счётчик закрытий, контекст библиотеки, аллокатор; это влияет на размер и перемещение владельца.

## Механика и гарантии

Для FILE определите Fclose с void operator()(FILE\*) const noexcept, вызывающим fclose, и храните unique_ptr&lt;FILE, Fclose>; результат fopen проверяйте через bool владельца — deleter не вызывается для null. shared_ptr принимает deleter при создании, но хранит его в блоке управления: тип не входит в shared_ptr&lt;T>; make_shared пользовательский deleter не принимает. Ошибку fflush/fclose, важную приложению, обрабатывайте явной close-операцией до деструктора: бросать из деструктора нельзя. Заимствованный контекст внутри deleter обязан пережить все пути освобождения: reset, присваивание, разрушение перемещённого владельца.

## Запускаемый пример

```cpp
#include <iostream>
#include <memory>
#include <vector>
#include <utility>
#include <string>

struct CountingDelete { int* count; void operator()(int* p) const noexcept { ++*count; delete p; } };
int main() { int count = 0; { std::unique_ptr<int, CountingDelete> p(new int(3), CountingDelete{&count}); auto q = std::move(p); std::cout << *q << " "; } std::cout << count << "\n"; }
```

Ожидаемый вывод:

```text
3 1
```

## Разбор и эксперимент

В практике deleter хранит указатель на счётчик. Переместите owner и убедитесь, что закрытие учитывается ровно один раз. Затем переставьте объявления счётчика и владельца на бумаге и объясните зависимость времени жизни.

### Ресурс освобождается парной операцией своего API

new ↔ delete, new[] ↔ delete[], malloc ↔ free, fopen ↔ fclose, библиотечные create ↔ destroy. RAII-обёртка обязана вызывать именно парную операцию; delete для FILE или free для new — undefined behavior даже если «обычно работает». Пользовательский deleter хранит эту пару вместе с ресурсом: struct Fclose &#123; void operator()(FILE\* f) const noexcept &#123; if (f) std::fclose(f); &#125; &#125;;

В unique_ptr&lt;T, D> тип deleter входит в тип владельца — два unique_ptr с разными D несовместимы, что и нужно: способ освобождения не может потеряться. В shared_ptr deleter сохраняется в блоке управления при создании и в тип не входит; make_shared пользовательский deleter не принимает.

Два подводных камня. Пустой deleter, который ничего не освобождает, маскирует утечку вместо владения. Заимствованный контекст (счётчик, пул, аллокатор внутри deleter) обязан пережить все пути освобождения: reset, присваивание, разрушение перемещённого владельца. Ошибку fclose, важную приложению, обрабатывайте явной close-операцией до деструктора: бросать из деструктора нельзя.

<CommonMistake title="Граница корректности">

Нельзя закрывать FILE через delete или освобождать память из new через free — несовместимые пары. Пустой deleter, который ничего не освобождает, маскирует утечку вместо владения.

</CommonMistake>
