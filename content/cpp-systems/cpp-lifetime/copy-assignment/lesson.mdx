## Модель и назначение

Присваивание заменяет состояние уже существующего объекта. В записи target = source у target может быть собственный ресурс, который нужно корректно освободить, — это первое отличие от конструктора копирования. Обычная сигнатура T&amp; operator=(const T&amp;) возвращает \*this для поддержки цепочек a = b = c. Помимо обычного случая нужно учесть самоприсваивание через ссылку-алиас и исключение при выделении нового ресурса.

## Механика и гарантии

Безопасная последовательность: сначала подготовить полную замену во временного владельца, затем заменить старый ресурс. Если выделение не удалось, назначение не изменено — это сильная гарантия исключений. Copy-and-swap обобщает идею: временная копия строится до любых изменений, обмен состояниями не бросает, прежнее состояние назначения уничтожает временный объект. Цена — возможно лишнее выделение: для больших буферов иногда нужна версия с переиспользованием ёмкости, но её доказательство заметно сложнее.

## Запускаемый пример

```cpp
#include <iostream>
#include <memory>
#include <vector>
#include <utility>
#include <string>

struct Cell { std::unique_ptr<int> p; explicit Cell(int x): p(std::make_unique<int>(x)) {} Cell(const Cell&) = delete; Cell& operator=(const Cell& x) { auto next = std::make_unique<int>(*x.p); p = std::move(next); return *this; } };
int main() { Cell a{3}, b{7}; a = b; *b.p = 9; std::cout << *a.p << " " << *b.p << "\n"; }
```

Ожидаемый вывод:

```text
7 9
```

## Разбор и эксперимент

Проверьте три сценария: присваивание разных объектов, самоприсваивание через alias и независимость после изменения источника. На бумаге вставьте bad_alloc между подготовкой и commit: старое состояние должно остаться целым.

### Присваивание сложнее конструктора

Конструктор копирования создаёт объект на пустом месте. Присваивание работает с уже живым target, у которого может быть собственный ресурс. Три дополнительные проблемы: куда деть старое состояние target; что делать при self-assignment (target = target через ссылку-алиас); что делать, если выделение нового ресурса бросит на середине.

Наивный порядок «сначала delete p, затем p = new ...» проваливается по всем трём пунктам: при самоприсваивании удаляется источник, из которого предстоит копировать; при bad_alloc объект назначения остаётся с удалённым указателем. Безопасный порядок обратный: сначала подготовить полную замену во временного владельца, затем обменять. Copy-and-swap формализует эту идею: временная копия строится до любых изменений target, обмен не бросает, старое состояние уничтожает временный объект.

Ценой может быть лишнее выделение, когда старый буфер target подошёл бы по размеру. Для критичных к производительности контейнеров пишут оптимизированную версию с переиспользованием ёмкости — но её доказательство заметно сложнее, и начинать следует с copy-and-swap.

<CommonMistake title="Граница корректности">

Порядок «delete p; p = new int(\*other.p)» опасен дважды: при самоприсваивании other.p указывает на уже удалённый int, а при исключении target остаётся повреждённым.

</CommonMistake>

## Что нужно унести из урока

Присваивание заменяет состояние уже существующего объекта. Порядок «delete p; p = new int(\*other.p)» опасен дважды: при самоприсваивании other.p указывает на уже удалённый int, а при исключении target остаётся повреждённым.
