## Цели обучения

- Объяснить, почему привязка ресурса к времени жизни объекта закрывает все пути выхода.
- Проследить на MemoryDiagram восстановление состояния при раскрутке исключения.
- Реализовать небросаемый guard с запретом копирования и проверить его на исключении.

## Модель и назначение

RAII связывает право владения ресурсом со временем жизни объекта стека. Ресурсом может быть память, файл, захваченный mutex или временно изменённое состояние. Конструктор приобретает ресурс либо сообщает о неуспехе; методы работают только с допустимым состоянием; деструктор освобождает ресурс на всех путях выхода — при обычном return, при раннем выходе и при раскрутке исключения. Клиенту больше не нужно дублировать cleanup перед каждым выходом: за него это делает область видимости.

## Механика и гарантии

У владельца нужно отдельно решить вопрос копирования и перемещения. Для guard, восстанавливающего настройку, копирование почти всегда ошибочно: два экземпляра восстановят одно значение дважды. Guard, заимствующий int&amp;, обязан жить меньше самого int — сначала объявляется защищаемое состояние, затем guard. Деструктор не должен бросать. RAII обеспечивает очистку ресурсов, но не откатывает предметные изменения: добавленная запись в журнал и незакрытый файл — разные обязательства; для транзакции нужен явный договор commit/rollback.

## Запускаемый пример

```cpp
#include <iostream>
#include <memory>
#include <vector>
#include <utility>
#include <string>

struct Restore { int& x; int old; Restore(int& v, int next): x(v), old(v) { x = next; } ~Restore() { x = old; } Restore(const Restore&) = delete; Restore& operator=(const Restore&) = delete; };
int main() { int level = 5; try { Restore g{level, 50}; std::cout << level << " "; throw 1; } catch (int) {} std::cout << level << "\n"; }
```

Ожидаемый вывод:

```text
50 5
```

## Разбор и эксперимент

Добавьте ранний return и throw внутрь защищённого блока: в обоих случаях настройка восстанавливается. Сравните с ручным присваиванием в конце блока — до него исполнение может не дойти.

### Три гарантии исключений и роль RAII

Базовая гарантия: при исключении нет утечек, объект остаётся в допустимом (возможно, изменённом) состоянии. Сильная гарантия: операция либо целиком выполняется, либо не меняет ничего — «как транзакция». Гарантия отсутствия исключений (noexcept): операция не бросает никогда.

RAII закрывает базовую гарантию почти автоматически: если каждый ресурс держит владеющий объект стека, раскрутка стека сама вызовет все деструкторы. Сильная гарантия требует уже проектирования: сначала подготовить новое состояние во временном владельце, и только затем зафиксировать его. noexcept деструктора — обязательство, за нарушение которого программа завершится через std::terminate.

Отдельная граница применимости: RAII работает при нормальном выходе и раскрутке исключений. Он не спасает от kill -9, abort или падения ядра — там ресурсы возвращает операционная система. Не обещайте в документации «гарантированное закрытие файла при любом завершении процесса»; обещайте закрытие на всех путях выхода из области видимости.

<CommonMistake title="Граница корректности">

Не разбрасывайте delete и unlock по веткам — но и не считайте RAII гарантией при kill процесса или abort: эти примеры относятся к нормальному выходу и раскрутке стека.

## Практика

Реализуйте Restore как в модели: конструктор сохраняет прежнее значение ссылки и записывает новое, деструктор восстанавливает, копирование запрещено. solve(a,b) временно заменяет a на b, сохраняет изменённое значение, бросает int и ловит его снаружи блока Restore; верните сумму сохранённого и восстановленного значений.
