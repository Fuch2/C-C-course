## Лучшая специальная функция — ненаписанная

**Правило нуля**: классы, которые не занимаются управлением ресурсами напрямую, не должны объявлять **ни одной** из пяти специальных функций. Вместо сырых указателей их поля — владельцы, которые сами умеют копироваться, перемещаться и освобождаться: `std::string`, `std::vector`, `std::map`, `std::unique_ptr`, `std::shared_ptr`. Неявные функции класса просто вызовут функции полей — и будут правильными.

Сравните. Класс отчёта по правилу пяти:

```cpp
class Report {
    std::size_t size_;
    double *values_;        // + деструктор, 2 копирования, 2 перемещения — ~40 строк
};
```

И тот же класс по правилу нуля:

```cpp
#include <print>
#include <string>
#include <utility>
#include <vector>

class Report {
public:
    explicit Report(std::string title) : title_(std::move(title)) {}

    void add(double v) {
        values_.push_back(v);
    }

    double total() const {
        double sum = 0;
        for (double v : values_) {
            sum += v;
        }
        return sum;
    }

    const std::string &title() const {
        return title_;
    }

private:
    std::string title_;
    std::vector<double> values_;
};

int main() {
    Report a("Январь");
    a.add(1.5);
    a.add(2.5);
    Report b = a;
    b.add(10);
    Report c = std::move(b);
    a = c;
    std::println("{}: {} | {}: {}", a.title(), a.total(), c.title(), c.total());
    return 0;
}
```

Вывод:

```text
Январь: 14 | Январь: 14
```

Копирование глубокое, перемещение забирает буферы, присваивание корректно при самоприсваивании, а утечки и двойные освобождения невозможны — без единой строки специальных функций. И если завтра в класс добавят поле, ничего не нужно обновлять.

## Разделение обязанностей

Правило нуля — следствие принципа единственной ответственности. Управление ресурсом — **отдельная** задача, и её решает отдельный маленький класс по правилу пяти (или готовый тип стандартной библиотеки). Все остальные классы собираются из таких владельцев и следуют правилу нуля.

| Слой               | Примеры                                            | Правило |
| ------------------ | -------------------------------------------------- | ------- |
| владельцы ресурсов | `std::vector`, `std::unique_ptr`, ваш `FileHandle` | пяти    |
| предметные классы  | `Report`, `Order`, `Scene`, `Session`              | нуля    |

Если для предметного класса понадобился деструктор, это сигнал: внутри прячется неоформленный ресурс. Вынесите его во владельца.

<MemoryDiagram title="Правило нуля: функции класса — это функции полей">

```text

~Report()              → ~vector()       + ~string()             — освобождение
```

## Когда поле запрещает копирование

Неявные функции наследуют ограничения полей. Класс с полем `std::unique_ptr` автоматически становится **только перемещаемым** — и это правильно: единоличного владельца нельзя скопировать.

```cpp
#include <memory>
#include <print>
#include <string>
#include <utility>
#include <vector>

class Playlist {
public:
    void add(std::string song) {
        songs_.push_back(std::make_unique<std::string>(std::move(song)));
    }
    std::size_t size() const {
        return songs_.size();
    }

private:
    std::vector<std::unique_ptr<std::string>> songs_;
};

int main() {
    Playlist mine;
    mine.add("Песня");
    Playlist yours = std::move(mine);
    std::println("{} {}", mine.size(), yours.size());
    return 0;
}
```

Вывод:

```text
0 1
```

`Playlist yours = mine;` не скомпилируется: компилятор сам понял, что копировать такой класс нельзя. Если копия всё-таки нужна, напишите явную функцию `clone()` или используйте поле, которое копирует объект глубоко. В C++26 для этого появятся `std::indirect<T>` и `std::polymorphic<T>` — владельцы объекта в куче с семантикой значения.

<Tip title="Полиморфная база">

Базовый класс иерархии нуждается в виртуальном деструкторе — и это единственное, ради чего правило нуля нарушают. C++ Core Guidelines (C.67) советуют заодно запретить базе публичное копирование, чтобы исключить срезку: `Base(const Base &) = delete;` и т. д. Наследники при этом снова следуют правилу нуля.

</Tip>

<Concept title="Правило нуля">

Предметные классы не объявляют ни деструктора, ни копирующих, ни перемещающих операций: их поля — владельцы ресурсов, и неявные функции класса вызывают функции полей. Управление каждым ресурсом выносят в отдельный класс по правилу пяти или берут готовый из стандартной библиотеки. Поле `unique_ptr` делает класс только перемещаемым автоматически. Исключение — полиморфная база с виртуальным деструктором.

</Concept>

## Частые ошибки

<CommonMistake title="Сырой указатель-владелец в предметном классе">

`Order` с полем `Item *items_` тянет за собой все пять функций. Замените на `std::vector<Item>` — и удалите их.

</CommonMistake>

<CommonMistake title="Поле-ссылка или представление вместо владельца">

`const std::string &name_` или `std::string_view name_` в поле — не владельцы: неявное копирование скопирует ссылку, и объект повиснет вместе с источником. Правило нуля работает, только если поля **владеют**.

</CommonMistake>

<CommonMistake title="Деструктор «на всякий случай»">

`~Report() { values_.clear(); }` ничего не добавляет — вектор очистится сам, — но отключает неявное перемещение.

</CommonMistake>

## Практика

1. **Журнал** — класс из владельцев без специальных функций.
2. **Сцена** — поле `unique_ptr` делает класс перемещаемым, `clone` даёт копию.
3. **Найди ошибку: ярлыки без владельца** — поле-ссылка вместо строки.
4. **Сессия** — маленький владелец ресурса по правилу пяти и класс по правилу нуля.

## Итоги

- Предметные классы не объявляют специальных функций: поля сами управляют ресурсами.
- Управление ресурсом — отдельный маленький класс по правилу пяти или готовый тип.
- Неявные функции наследуют ограничения полей: `unique_ptr` делает класс только перемещаемым.
- Поля-ссылки и представления не владеют — с ними правило нуля не работает.
- Исключение — полиморфная база с виртуальным деструктором.
