## Как устроен счётчик владельцев

`std::shared_ptr` — не магия. Это класс по правилу пяти, который делит с другими копиями **блок управления** со счётчиком. Чтобы понимать его цену и ограничения, полезно один раз написать упрощённую версию самим:

```cpp
#include <print>
#include <string>
#include <utility>

template <class T>
class RefPtr {
public:
    explicit RefPtr(T *p) : block_(new Block{p, 1}) {}
    RefPtr(const RefPtr &other) : block_(other.block_) {
        ++block_->count;
    }
    RefPtr &operator=(RefPtr other) noexcept {
        std::swap(block_, other.block_);
        return *this;
    }
    ~RefPtr() {
        if (--block_->count == 0) {
            delete block_->object;
            delete block_;
        }
    }

    T *operator->() const {
        return block_->object;
    }
    long use_count() const {
        return block_->count;
    }

private:
    struct Block {
        T *object;
        long count;
    };
    Block *block_;
};

struct Doc {
    std::string name;
    explicit Doc(std::string n) : name(std::move(n)) {}
    ~Doc() {
        std::println("удалён {}", name);
    }
};

int main() {
    RefPtr<Doc> a(new Doc("отчёт"));
    {
        RefPtr<Doc> b = a;
        RefPtr<Doc> c(new Doc("черновик"));
        c = b;
        std::println("владельцев {}", a.use_count());
    }
    std::println("владельцев {}, имя {}", a.use_count(), a->name);
    return 0;
}
```

Вывод:

```text
удалён черновик
владельцев 3
владельцев 1, имя отчёт
удалён отчёт
```

Копирование увеличивает счётчик, деструктор уменьшает, и тот, кто довёл его до нуля, удаляет объект и сам блок. Присваивание «по значению и обмен»: параметр `other` стал ещё одним владельцем «отчёта», а после обмена он уносит с собой старый блок `c` — и, будучи последним владельцем «черновика», удаляет его.

<MemoryDiagram title="Счётчик в общем блоке">

```text
a ─┐
b ─┼──▶ Block { object ─▶ [Doc "отчёт"], count = 3 }
c ─┘
выход из блока: ~c → 2, ~b → 1        a — последний владелец
конец main:     ~a → 0 → delete object, delete block
```

</MemoryDiagram>

## Чем настоящий shared_ptr сложнее

| Наша версия                   | `std::shared_ptr`                                                 |
| ----------------------------- | ----------------------------------------------------------------- |
| обычный `long`                | **атомарный** счётчик — копии можно создавать из разных потоков   |
| один счётчик                  | два: владельцев (strong) и наблюдателей (weak, для `weak_ptr`)    |
| объект и блок — два выделения | `make_shared` кладёт их в одно                                    |
| всегда `delete`               | хранит удалитель любого типа (урок о пользовательских удалителях) |
| указатель на объект в блоке   | указатель хранится в самом `shared_ptr`, что даёт **псевдонимы**  |

Два счётчика нужны потому, что блок управления должен пережить объект, пока на него смотрят слабые ссылки: объект удаляется, когда strong = 0, а блок — когда strong = 0 и weak = 0. Отсюда тонкость: при `make_shared` объект и блок выделены вместе, поэтому **память** объекта возвращается только после исчезновения последнего `weak_ptr`, хотя деструктор вызван раньше. Для огромных объектов с долгоживущими наблюдателями иногда предпочитают `shared_ptr<T>(new T)`.

## Псевдонимы

Конструктор-псевдоним `std::shared_ptr<U>(owner, ptr)` создаёт указатель, который **смотрит** на `ptr`, а **владеет** тем же, чем `owner`. Так можно отдать наружу указатель на поле объекта, и поле не повиснет, пока этот указатель жив:

```cpp
#include <memory>
#include <print>
#include <string>

struct Settings {
    int volume = 7;
    std::string theme = "тёмная";
    ~Settings() {
        std::println("настройки удалены");
    }
};

int main() {
    auto settings = std::make_shared<Settings>();
    std::shared_ptr<int> volume(settings, &settings->volume);
    settings.reset();
    std::println("громкость {}, владельцев {}", *volume, volume.use_count());
    volume.reset();
    std::println("конец");
    return 0;
}
```

Вывод:

```text
громкость 7, владельцев 1
настройки удалены
конец
```

`volume` указывает на `int`, но держит в живых весь объект `Settings`: после `settings.reset()` единственный владелец — он.

## Встроенный счётчик

Есть и другая схема — **встроенный** (intrusive) счётчик: он хранится в самом объекте, а умный указатель лишь вызывает `add_ref`/`release`. Так устроены COM-объекты Windows, `boost::intrusive_ptr`, объекты многих игровых движков. Блок управления не нужен, и из сырого указателя всегда можно получить нового владельца — но тип должен заранее поддерживать подсчёт.

<Concept title="Подсчёт ссылок">

`shared_ptr` хранит указатель на объект и на блок управления со счётчиками владельцев (strong) и наблюдателей (weak). Копирование атомарно увеличивает strong, уничтожение уменьшает; при strong = 0 объект удаляется, при strong = 0 и weak = 0 — блок. При `make_shared` память объекта освобождается только вместе с блоком. Конструктор-псевдоним разделяет «на что указываю» и «чем владею». Встроенный счётчик хранится в самом объекте.

</Concept>

## Частые ошибки

<CommonMistake title="Самоприсваивание в своём счётчике">

`release(); block_ = other.block_; ++block_->count;` при `p = p` удаляет объект, если владелец был один, и затем увеличивает счётчик в освобождённом блоке. Сначала запомните новый блок и увеличьте его счётчик, потом уменьшайте старый — или используйте обмен.

</CommonMistake>

<CommonMistake title="Указатель на поле без псевдонима">

`int *v = &settings->volume;` повиснет, когда `settings` отпустят. Если указатель на часть объекта должен держать объект живым — конструктор-псевдоним.

</CommonMistake>

<CommonMistake title="Подсчёт ссылок как бесплатная операция">

Каждая копия `shared_ptr` — атомарная операция, видимая всем ядрам процессора. В горячих циклах передавайте ссылки на объект, а не копии указателя.

</CommonMistake>

## Практика

1. **Свой счётчик** — минимальный умный указатель с подсчётом ссылок.
2. **Указатели на поля** — конструктор-псевдоним.
3. **Найди ошибку: самоприсваивание** — неверный порядок операций со счётчиком.
4. **Слабые ссылки своими руками** — два счётчика и раздельная жизнь объекта и блока.

## Итоги

- Счётчик владельцев живёт в блоке управления, общем для всех копий.
- Последний владелец удаляет объект; блок живёт, пока есть и слабые ссылки.
- Настоящий `shared_ptr` атомарный, хранит удалитель и два счётчика.
- Конструктор-псевдоним даёт указатель на часть объекта, владеющий всем объектом.
- Самоприсваивание счётчика: сначала увеличить новый, потом уменьшить старый.
