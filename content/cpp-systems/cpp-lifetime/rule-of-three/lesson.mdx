## Три функции — одно решение

**Правило трёх**: если классу понадобилось написать **хотя бы одну** из трёх специальных функций —

- деструктор,
- конструктор копирования,
- оператор копирующего присваивания, —

то почти наверняка нужны **все три**. Причина в том, что потребность в любой из них обычно возникает по одному поводу: класс сам управляет ресурсом. А раз так, ресурс нужно и освобождать, и правильно копировать при создании, и правильно заменять при присваивании.

Что происходит, если написать только часть:

| Написано                    | Что делает компилятор за вас             | Последствие                                     |
| --------------------------- | ---------------------------------------- | ----------------------------------------------- |
| только деструктор           | поверхностное копирование и присваивание | двойное освобождение после первой копии         |
| деструктор и копирование    | поверхностное присваивание               | утечка старого ресурса и двойное освобождение   |
| деструктор и присваивание   | поверхностный конструктор копирования    | двойное освобождение после передачи по значению |
| копирование без деструктора | деструктор ничего не освобождает         | утечка                                          |

С C++11 неявное копирование класса с пользовательским деструктором объявлено **устаревшим**: компилятор ещё создаёт его ради совместимости, но `-Wdeprecated-copy-dtor` (Clang) и `-Wdeprecated-copy` (GCC) предупреждают об этом.

## Полный набор

Строка, которая сама владеет буфером символов, — классический пример класса по правилу трёх:

```cpp
#include <algorithm>
#include <cstddef>
#include <print>
#include <string_view>
#include <utility>

class String {
public:
    explicit String(std::string_view s) : size_(s.size()), data_(new char[s.size()]) {
        std::copy_n(s.data(), size_, data_);
    }

    // 1. Конструктор копирования: свой буфер.
    String(const String &other) : size_(other.size_), data_(new char[other.size_]) {
        std::copy_n(other.data_, size_, data_);
    }

    // 2. Присваивание: копия и обмен.
    String &operator=(const String &other) {
        String copy(other);
        std::swap(size_, copy.size_);
        std::swap(data_, copy.data_);
        return *this;
    }

    // 3. Деструктор: освободить свой буфер.
    ~String() {
        delete[] data_;
    }

    void append(std::string_view tail) {
        char *bigger = new char[size_ + tail.size()];
        std::copy_n(data_, size_, bigger);
        std::copy_n(tail.data(), tail.size(), bigger + size_);
        delete[] data_;
        data_ = bigger;
        size_ += tail.size();
    }

    std::string_view view() const {
        return {data_, size_};
    }

private:
    std::size_t size_;
    char *data_;
};

int main() {
    String a("код");
    String b = a;
    b.append("-ревью");
    String c("тест");
    c = b;
    String &alias = c;
    c = alias;
    a.append("!");
    std::println("{} | {} | {}", a.view(), b.view(), c.view());
    return 0;
}
```

Вывод:

```text
код! | код-ревью | код-ревью
```

Три строки — три независимых буфера; копирование, присваивание (включая самоприсваивание) и разрушение работают корректно, и AddressSanitizer молчит.

operator=        │ копия → обмен → старый уходит с копией   │  замена содержимого

## Запретить — тоже решение

Правило трёх не требует, чтобы класс обязательно копировался. Если копия ресурса не имеет смысла — соединение с базой, уникальный дескриптор, мьютекс, — копирование **запрещают**:

```cpp
class Connection {
public:
    Connection(const Connection &) = delete;
    Connection &operator=(const Connection &) = delete;
    ~Connection();          // закрывает соединение
};
```

Это тоже полный ответ на все три вопроса: «как освободить» — в деструкторе, «как копировать» — никак. Такой класс можно будет **перемещать** — передавать владение без копирования; это следующие уроки и правило пяти.

<Tip title="Правило трёх в современном коде">

Сегодня правило трёх — скорее сигнал тревоги, чем инструкция. Если вы пишете деструктор, остановитесь и спросите: можно ли вместо сырого указателя взять `std::vector`, `std::string` или `std::unique_ptr`? Тогда все три функции не понадобятся — это правило нуля, о котором отдельный урок.

</Tip>

<Concept title="Правило трёх">

Если классу нужен свой деструктор, свой конструктор копирования или своё копирующее присваивание, ему почти всегда нужны все три — потому что он сам управляет ресурсом. Частичная реализация оставляет компилятору поверхностные версии остальных и приводит к утечкам и двойным освобождениям. Вместо реализации копирования его можно запретить через `= delete`. С C++11 неявное копирование при пользовательском деструкторе устарело.

</Concept>

## Частые ошибки

<CommonMistake title="Деструктор есть, копирования нет">

Самая частая форма нарушения: `delete` в деструкторе, а копирование неявное. Первая же копия — например, `push_back` в вектор — создаёт двух владельцев.

</CommonMistake>

<CommonMistake title="Копирование и присваивание не согласованы">

Конструктор копирования делает глубокую копию, а присваивание — поверхностную или наоборот. Реализуйте присваивание через конструктор копирования (copy-and-swap) — тогда логика копирования одна.

</CommonMistake>

<CommonMistake title="Правило трёх «на всякий случай»">

Класс без собственных ресурсов (строки, векторы, числа) не нуждается ни в одной из трёх функций. Лишний конструктор копирования — место для будущей ошибки.

</CommonMistake>

## Практика

1. **Стек на массиве** — класс по правилу трёх с растущим буфером.
2. **Кто вызван?** — какая из специальных функций работает в каждой ситуации.
3. **Найди ошибку: один деструктор** — класс без копирования в векторе.
4. **Кольцевой буфер** — копирование, сохраняющее логический порядок.

## Итоги

- Деструктор, конструктор копирования и копирующее присваивание пишут вместе или не пишут вовсе.
- Причина одна: класс сам управляет ресурсом.
- Неполный набор — утечки и двойные освобождения; компилятор лишь предупреждает об устаревшем неявном копировании.
- Запретить копирование (`= delete`) — тоже выполнение правила.
- Лучшее решение — поля, которые управляют ресурсами сами, и ни одной из трёх функций.
