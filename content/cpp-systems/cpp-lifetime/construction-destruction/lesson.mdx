## Цели обучения

- Объяснить порядок конструирования и разрушения сложного объекта через порядок объявления полей.
- Проследить на MemoryDiagram журнал создания и разрушения вложенных Guard.
- Реализовать Guard со счётчиком и запретом копирования, предсказав пиковое состояние.

## Модель и назначение

Сложный объект создаётся изнутри наружу: сначала базовые подобъекты, затем поля строго в порядке объявления, и только потом выполняется тело конструктора. Порядок записей в списке инициализации ничего не переставляет. Разрушение зеркально: тело деструктора, затем поля в обратном порядке объявления, затем базы. Объект считается полностью существующим лишь после завершения конструктора и перестаёт существовать в начале деструктора — это и есть формальные границы времени жизни.

## Механика и гарантии

Если конструктор бросает исключение, полного объекта нет и его деструктор не вызывается; уже созданные базы и поля разрушаются автоматически. Поэтому поле-владелец (unique_ptr, vector) безопаснее сырого указателя, которому присвоили new в теле конструктора: при последующем исключении сырой адрес не освободит никто. Деструктор не должен бросать: при раскрутке стека исключение из деструктора ведёт к terminate. Виртуальные вызовы в конструкторе и деструкторе не диспетчеризуются в производный класс — самого производного объекта в эти моменты ещё (или уже) нет.

<MemoryDiagram title="Время жизни и связи владения">

```text

Разрушение: тело ~Pair → second → first
Поле, объявленное первым, умирает последним
Если second бросает: first разрушается; ~Pair НЕ вызывается
```

</MemoryDiagram>

Схема показывает логические объекты и отношения, а не реальную раскладку ABI. Сплошная стрелка означает владение, пунктирная — заимствование. Исчезновение имени и уничтожение объекта проверяйте отдельно.

## Запускаемый пример

```cpp
#include <iostream>
#include <memory>
#include <vector>
#include <utility>
#include <string>

struct Guard { int id; explicit Guard(int n): id(n) { std::cout << "+" << n << " "; } ~Guard() { std::cout << "-" << id << " "; } };
int main() { { Guard a{1}; { Guard b{2}; Guard c{3}; } } std::cout << "\n"; }
```

Ожидаемый вывод:

```text
+1 +2 +3 -3 -2 -1
```

## Разбор и эксперимент

Добавьте исключение после создания первого Guard и предскажите журнал. Затем перенесите бросок внутрь конструктора второго Guard до его завершения: в журнале не появится парный минус второго объекта — его деструктор не вызывается.

### Конструктор — это порог, а не процесс

Пока конструктор не завершился, объекта класса не существует. Отсюда два следствия, которые часто проверяют на ревью. Первое: если конструктор бросил, деструктор этого класса не вызывается — нечему; но уже построенные базы и поля разрушаются автоматически. Второе: в теле конструктора виртуальные вызовы не диспетчеризуются в производный класс — самого производного объекта ещё нет.

Порядок инициализации полей задаётся порядком их объявления, а не порядком в списке инициализации. Поле, объявленное первым, умирает последним. Если Session в деструкторе обращается к Buffer, Buffer обязан быть объявлен раньше Session — иначе к моменту ~Session буфер уже мёртв. Это правило зеркально конструированию и ловит самые скрытые use-after-free в деструкторах.

Журнал вывода «+1 +2 -2 -1» — не украшение, а инструмент. Превратите порядок создания/разрушения в наблюдаемые события, и половина ошибок порядка полей станет видна без отладчика.

<CommonMistake title="Граница корректности">

Зависимость от поля, объявленного ниже, не лечится перестановкой инициализаторов: порядок задаёт объявление. Если Session в деструкторе обращается к Buffer, Buffer обязан быть объявлен раньше — иначе он уже мёртв.

## Практика

Создайте Guard(int&amp; count), увеличивающий count в конструкторе и уменьшающий в деструкторе; копирование запретите. solve(a,b) начинает с count=a, во вложенном блоке создаёт два Guard, сохраняет пиковое значение count, выходит из блока и возвращает peak + count + b.
