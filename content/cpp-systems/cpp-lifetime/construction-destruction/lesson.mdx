## Объект собирается по частям

Объект класса — это базовые части и поля. Конструктор не создаёт их «все сразу»: он строит их **по очереди**, в строго определённом порядке, и только потом выполняет своё тело. Деструктор разбирает объект в **обратном** порядке:

1. базовые классы — в порядке, в котором они перечислены после двоеточия;
2. поля — в порядке **объявления в классе**;
3. тело конструктора.

Разрушение: тело деструктора, затем поля с последнего к первому, затем базовые классы.

```cpp
#include <print>
#include <string>
#include <utility>

struct Part {
    std::string name;
    explicit Part(std::string n) : name(std::move(n)) {
        std::println("+{}", name);
    }
    ~Part() {
        std::println("-{}", name);
    }
};

struct Device {
    Device() {
        std::println("+устройство");
    }
    ~Device() {
        std::println("-устройство");
    }
};

class Computer : public Device {
public:
    Computer() : psu_("блок питания"), cpu_("процессор") {
        std::println("компьютер собран");
    }
    ~Computer() {
        std::println("компьютер разбирается");
    }

private:
    Part psu_;
    Part cpu_;
};

int main() {
    Computer pc;
    return 0;
}
```

Вывод:

```text
+устройство
+блок питания
+процессор
компьютер собран
компьютер разбирается
-процессор
-блок питания
-устройство
```

Симметрия не случайна: к моменту тела конструктора все поля и база уже готовы, и тело может ими пользоваться. А тело деструктора выполняется, пока поля ещё живы, — и может, например, сохранить их состояние.

## Порядок задаёт объявление, а не список инициализации

Список инициализации `: psu_(…), cpu_(…)` задаёт **как** строить поля, но не **когда**. Поля строятся в порядке объявления в классе, даже если в списке они написаны иначе. Это ловушка, если одно поле инициализируется через другое:

```cpp
class Range {
public:
    Range(int begin, int end) : begin_(begin), end_(end), length_(end_ - begin_) {}

private:
    int length_;  // объявлено первым — строится первым, когда begin_ и end_ ещё не готовы
    int begin_;
    int end_;
};
```

`length_` вычисляется из неинициализированных полей — неопределённое поведение. GCC и Clang предупреждают: `-Wreorder` (входит в `-Wall`) сообщает о расхождении порядка, а `-Wuninitialized` — о чтении неготового поля. Правило: пишите список инициализации в порядке объявления полей и не инициализируйте поле через поля, объявленные ниже.

## Исключение в конструкторе

Если конструктор бросает исключение, объект **не считается созданным**: его деструктор не вызывается. Но всё, что успело построиться — база и поля, — разрушается автоматически, в обратном порядке:

```cpp
#include <print>
#include <stdexcept>
#include <string>

struct Resource {
    std::string name;
    explicit Resource(const std::string &n) : name(n) {
        if (n.starts_with('!')) {
            throw std::runtime_error("не открыть " + n);
        }
        std::println("+{}", name);
    }
    ~Resource() {
        std::println("-{}", name);
    }
};

class Pair {
public:
    Pair(const std::string &a, const std::string &b) : first_(a), second_(b) {
        std::println("пара готова");
    }
    ~Pair() {
        std::println("пара закрыта");
    }

private:
    Resource first_;
    Resource second_;
};

int main() {
    try {
        Pair p("a", "!b");
    } catch (const std::exception &e) {
        std::println("ошибка: {}", e.what());
    }
    return 0;
}
```

Вывод:

```text
+a
-a
ошибка: не открыть !b
```

`first_` уже был готов — и разрушен. `second_` не построился — разрушать нечего. А «пара закрыта» не напечаталась: недостроенную пару нечем закрывать. Отсюда важное следствие: если ресурс захвачен **в теле** конструктора «вручную» (через `new` или `fopen`), а потом что-то бросило исключение, деструктор его не освободит. Поэтому каждый ресурс оборачивают в собственный объект-поле — об этом урок о RAII.

<Concept title="Порядок конструирования и разрушения">

Конструктор строит базовые классы (в порядке перечисления), затем поля (в порядке объявления в классе, независимо от порядка в списке инициализации), затем выполняет тело. Деструктор выполняет тело, затем разрушает поля в обратном порядке, затем базы. Если конструктор бросил исключение, деструктор объекта не вызывается, но уже построенные поля и базы разрушаются автоматически.

</Concept>

## Частые ошибки

<CommonMistake title="Поле инициализируется через поле ниже">

Порядок строительства — порядок объявления. `length_(end_ - begin_)` при `length_`, объявленном выше `begin_` и `end_`, читает мусор. Держите список инициализации в порядке объявления и включайте `-Wall`.

</CommonMistake>

<CommonMistake title="Ресурс в теле конструктора без защиты">

`data_ = new int[n]; open_file();` — если `open_file` бросит, деструктор не вызовется и память утечёт. Каждый ресурс — отдельное поле-владелец.

</CommonMistake>

<CommonMistake title="Расчёт на деструктор недостроенного объекта">

Код очистки в деструкторе не выполнится, если конструктор не завершился. Очищайте то, что успели сделать, или стройте объект из полей, которые очищают себя сами.

</CommonMistake>

## Практика

1. **Компьютер** — порядок построения полей и тела.
2. **Пара ресурсов** — исключение во время построения.
3. **Найди ошибку: полное имя** — поле, построенное раньше своих источников.
4. **Сборка с откатом** — разборка частично собранного объекта в правильном порядке.

## Итоги

- Сначала базы, затем поля в порядке объявления, затем тело конструктора; разрушение — в обратном порядке.
- Список инициализации не меняет порядок строительства; `-Wreorder` предупреждает о расхождении.
- Если конструктор бросил исключение, деструктор объекта не вызывается, а построенные части разрушаются автоматически.
- Ресурсы, захваченные в теле конструктора вручную, при исключении утекают — оборачивайте их в поля-владельцы.
