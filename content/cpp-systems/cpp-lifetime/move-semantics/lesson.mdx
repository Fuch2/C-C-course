## Цели обучения

- Объяснить перемещение как передачу права на ресурс при живом объекте-источнике.
- Проследить на MemoryDiagram, что адрес ресурса не меняется, меняется владелец.
- Проверить пустоту источника после передачи и восстановить его новым ресурсом.

## Модель и назначение

Перемещение позволяет новому владельцу принять ресурс, которым источник больше не пользуется в прежнем состоянии. Это семантика операции, а не перенос байтов на другой адрес: объект-источник продолжает существовать и будет разрушен своим деструктором. У unique_ptr после передачи владения источник пуст, а выделенный int остаётся на прежнем адресе — заёмщики самого int остаются корректными до удаления новым владельцем. Для других типов допустимое состояние после перемещения определяется их контрактом.

## Механика и гарантии

Копирование и перемещение отвечают на разные вопросы: копия сохраняет независимый источник, перемещение переиспользует его ресурс. Но move не обязательно дешевле и не обязательно перемещает: для int это фактически копирование, а при отсутствии move-конструктора std::move тихо выберет копию — компиляция успешна, выигрыша нет. У стандартных типов moved-from состояние допустимое, но не определённое заранее, если контракт не обещает большего: разрушить объект можно, вызвать front у потенциально пустого vector — нет.

## Запускаемый пример

```cpp
#include <iostream>
#include <memory>
#include <vector>
#include <utility>
#include <string>

int main() { auto src = std::make_unique<int>(15); auto dst = std::move(src); std::cout << (src ? 1 : 0) << " " << *dst << " " << (dst ? 1 : 0) << "\n"; }
```

Ожидаемый вывод:

```text
0 15 1
```

## Разбор и эксперимент

Сохраните сырой адрес до передачи и сравните с destination.get() после: адреса совпадут — сам int не переезжал. Затем назначьте source новый ресурс и убедитесь, что он снова полноценный владелец.

### Перемещение — это семантика, а не телепорт байтов

Move не переносит объект на другой адрес. Он разрешает новому владельцу забрать ресурс (буфер, файловый дескриптор, указатель), оставляя источник в допустимом, но обычно пустом состоянии. Сам объект-источник продолжает жить и будет разрушен своим деструктором — поэтому деструктор обязан корректно работать с moved-from состоянием.

«move всегда бесплатен» — миф. Для указателя это O(1); для маленького POD-типа move вырождается в копирование; для контейнеров с несовместимыми аллокаторами элементы могут переноситься поштучно. И наоборот: при отсутствии move-конструктора std::move тихо выберет копию — компиляция успешна, производительности нет.

Контракт moved-from состояния задаёт тип. unique_ptr обещает null — можно проверять. vector обещает лишь «допустимое состояние» — нельзя читать size и ожидать конкретное значение. Проектируя свой тип, опубликуйте постусловие перемещения явно: что разрешено делать с источником после передачи.

<CommonMistake title="Граница корректности">

Нельзя разыменовывать moved-from unique_ptr через \*source. Сам source можно проверять, сбрасывать и заполнять заново. Не переносите гарантию пустоты unique_ptr на произвольный класс.

</CommonMistake>
