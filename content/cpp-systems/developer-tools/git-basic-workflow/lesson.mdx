## Зачем контроль версий

Программа работала вчера, а сегодня после десятка правок перестала. Что именно изменилось? Можно ли вернуть вчерашнюю версию одного файла? Как двум людям одновременно править один проект и не затереть работу друг друга?

На эти вопросы отвечает **система контроля версий**. Git — самая распространённая из них: он хранит историю проекта как цепочку снимков, показывает разницу между любыми двумя состояниями и позволяет вести параллельные линии разработки. Сервисы GitHub, GitLab и Gitea хранят копии репозиториев и добавляют совместную работу — обсуждение изменений, проверку кода, CI.

Перед первым использованием Git нужно представиться — имя и почта попадут в каждый ваш коммит:

```text
$ git config --global user.name "Анна Петрова"
$ git config --global user.email "anna@example.com"
```

## Три места, где живут изменения

Главное, что нужно понять в Git, — у каждого изменения три возможных состояния:

| Место                     | Что это                                         | Как туда попасть   |
| ------------------------- | ----------------------------------------------- | ------------------ |
| **рабочий каталог**       | файлы, которые вы редактируете                  | правка в редакторе |
| **индекс** (staging area) | черновик следующего снимка: что войдёт в коммит | `git add`          |
| **история** (репозиторий) | сохранённые снимки — коммиты                    | `git commit`       |

Индекс позволяет собрать коммит **осознанно**: из пяти изменённых файлов отправить в снимок два, относящиеся к одной задаче, а остальное оставить на потом.

```text
$ mkdir calc && cd calc
$ git init
Initialized empty Git repository in /home/u/calc/.git/
$ git status
On branch main
No commits yet
Untracked files:
  main.c
  Makefile
$ git add main.c Makefile
$ git commit -m "Калькулятор: разбор чисел и сложение"
[main (root-commit) 3f2a1c9] Калькулятор: разбор чисел и сложение
 2 files changed, 41 insertions(+)
```

Каждый коммит получает **хеш** — уникальный идентификатор вроде `3f2a1c9…` (обычно хватает первых семи символов). Коммит хранит снимок всех файлов, автора, дату, сообщение и ссылку на предыдущий коммит — так получается история.

## Статус в короткой форме

После работы над кодом `git status --short` (или `-s`) показывает каждое изменение двумя буквами: первая — индекс относительно последнего коммита, вторая — рабочий каталог относительно индекса.

```text
$ git status -s
M  lexer.c
 M parser.c
MM main.c
A  eval.c
 D notes.txt
?? build/
```

| Запись | Значение                                                    |
| ------ | ----------------------------------------------------------- |
| `M `   | изменение добавлено в индекс — войдёт в коммит              |
| ` M`   | файл изменён, но не добавлен в индекс                       |
| `MM`   | часть изменений в индексе, после `git add` файл правили ещё |
| `A `   | новый файл добавлен в индекс                                |
| ` D`   | файл удалён в рабочем каталоге                              |
| `??`   | файл не отслеживается — Git о нём не знает                  |

## Что изменилось: git diff

```text
$ git diff              # рабочий каталог против индекса — ещё не добавленное
$ git diff --staged     # индекс против последнего коммита — то, что войдёт в коммит
$ git log --oneline     # краткая история
a91b07e Деление на ноль: сообщение вместо падения
3f2a1c9 Калькулятор: разбор чисел и сложение
```

Вывод `git diff` — в **унифицированном формате**:

```text
diff --git a/main.c b/main.c
--- a/main.c
+++ b/main.c
@@ -10,6 +10,10 @@ int main(void) {
     double a, b;
     char op;
     scanf("%lf %c %lf", &a, &op, &b);
+    if (op == '/' && b == 0) {
+        fprintf(stderr, "деление на ноль\n");
+        return 1;
+    }
     printf("%g\n", a / b);
     return 0;
 }
```

Строки с `-` удалены, с `+` добавлены, с пробелом — не изменились и показаны для контекста. Заголовок `@@ -10,6 +10,10 @@` означает: «фрагмент начинается в строке 10 и занимал 6 строк в старой версии, а в новой — 10». Изменённая строка выглядит как удаление старой версии (`-`) и добавление новой (`+`). **Перед каждым коммитом** просматривайте `git diff --staged`: так в историю не попадут отладочные `printf` и случайные правки.

## Что не хранить: .gitignore

В репозитории хранят **исходники** — то, что пишут люди. Всё, что получается из исходников автоматически, и всё личное в Git не кладут. Шаблоны таких файлов перечисляют в `.gitignore` в корне проекта:

```text
# результаты сборки
build/
*.o
*.a
*.so
/calc

# файлы редакторов и системы
.vscode/
.DS_Store

# локальные настройки и секреты
.env
config.local.h
!config.example.h
```

| Шаблон      | Что игнорирует                                                      |
| ----------- | ------------------------------------------------------------------- |
| `*.o`       | файлы с таким именем в любом каталоге                               |
| `build/`    | каталог `build` в любом месте вместе со всем содержимым             |
| `/calc`     | только `calc` в корне проекта (косая черта в начале — «от корня»)   |
| `src/gen.c` | путь от корня (шаблон с `/` внутри привязан к корню)                |
| `!файл`     | исключение: снова отслеживать файл, попавший под предыдущее правило |

Если файл подходит под несколько правил, действует **последнее**. Но исключение `!` не работает, если проигнорирован **каталог**, в котором лежит файл: Git не заглядывает в игнорируемые каталоги. `.gitignore` не действует на файлы, которые уже в репозитории, — их сначала убирают из индекса командой `git rm --cached`.

<Warning title="Секреты в истории">

Пароль или ключ, однажды попавший в коммит, остаётся в истории, даже если удалить его следующим коммитом: любой, кто скачал репозиторий, может открыть старый снимок. Такой ключ считается скомпрометированным — его нужно **отозвать и заменить**. Храните секреты вне репозитория и добавляйте их шаблоны в `.gitignore` с самого начала.

</Warning>

## Отмена изменений

| Ситуация                                              | Команда                       |
| ----------------------------------------------------- | ----------------------------- |
| убрать файл из индекса, сохранив правки               | `git restore --staged main.c` |
| выбросить правки файла в рабочем каталоге             | `git restore main.c`          |
| исправить сообщение или содержимое последнего коммита | `git commit --amend`          |
| отменить старый коммит новым «обратным» коммитом      | `git revert a91b07e`          |

`git restore main.c` безвозвратно удаляет несохранённые в коммитах правки — Git их не запоминал. `git commit --amend` переписывает коммит; не делайте этого с коммитами, которые уже отправлены коллегам.

## Ветки

**Ветка** — независимая линия разработки. Новую функцию делают в отдельной ветке, не ломая рабочую версию в `main`:

```text
$ git switch -c power          # создать ветку power и перейти в неё
$ # ... правки, git add, git commit ...
$ git switch main              # вернуться в main
$ git merge power              # влить изменения ветки power
```

Если в обеих ветках изменили одни и те же строки, Git не угадывает, какой вариант верный, и сообщает о **конфликте**, оставляя в файле оба варианта:

```text
<<<<<<< HEAD
    printf("%.2f\n", result);
=======
    printf("%g\n", result);
>>>>>>> power
```

Между `<<<<<<<` и `=======` — версия текущей ветки, ниже — вливаемой. Вы оставляете нужный код, удаляете маркеры, затем `git add` и `git commit`.

## Работа с удалённым репозиторием

```text
$ git clone https://github.com/user/calc.git    # скачать репозиторий с историей
$ git pull                                      # получить новые коммиты
$ git push                                      # отправить свои коммиты
```

Типичный цикл работы: `git pull` → ветка → правки и коммиты → `git push` → запрос на слияние (pull request), где коллеги и CI проверяют изменения перед вливанием в `main`.

<Concept title="Коммит — одна понятная мысль">

Хороший коммит — одно логическое изменение, которое собирается и проходит тесты, с сообщением, объясняющим **что и зачем**: «Деление на ноль: сообщение вместо падения», а не «правки» или «fix». Такую историю можно читать как журнал проекта, а виноватое изменение — найти и отменить одной командой.

</Concept>

## Частые ошибки

<CommonMistake title="git add . без просмотра">

Команда добавляет всё подряд — объектные файлы, исполняемые файлы, `.env`. Настройте `.gitignore` до первого коммита и смотрите `git status` и `git diff --staged` перед каждым коммитом.

</CommonMistake>

<CommonMistake title="Один коммит на день работы">

Коммит «много правок» из двадцати файлов нельзя ни понять, ни частично отменить. Делайте коммит, как только закончено одно законченное изменение.

</CommonMistake>

<CommonMistake title="Удалить секрет новым коммитом">

Старый снимок по-прежнему содержит ключ. Отзовите его у сервиса и выпустите новый.

</CommonMistake>

</TryIt>

## Практика

1. **git status --short** — вычислить двухбуквенный статус файлов.
2. **Шаблоны .gitignore** — определить, какие файлы будут проигнорированы.
3. **Построчный diff** — построить минимальную разницу между двумя версиями файла.

## Итоги

- Изменение проходит три места: рабочий каталог → индекс (`git add`) → история (`git commit`).
- `git status -s` показывает состояние двумя буквами: индекс и рабочий каталог; `git diff` и `git diff --staged` показывают сами изменения, `git log --oneline` — историю.
- `.gitignore` исключает результаты сборки и личные файлы: последнее подходящее правило побеждает, `!` возвращает файл, но не из игнорируемого каталога.
- `git restore` отменяет правки, `git revert` — коммит; секреты из истории не удаляются — их отзывают.
- Ветки (`git switch -c`, `git merge`) разделяют линии работы; конфликты решают вручную по маркерам `<<<<<<<`, `=======`, `>>>>>>>`.
