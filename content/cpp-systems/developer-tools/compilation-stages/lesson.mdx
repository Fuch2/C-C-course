## Что скрывает одна команда

Команда `gcc main.c -o app` выглядит как одно действие, но внутри это **четыре программы**, запущенные по очереди. Каждая получает файл от предыдущей и передаёт свой результат следующей:

| Стадия             | Кто работает                | Вход                  | Выход                     |
| ------------------ | --------------------------- | --------------------- | ------------------------- |
| 1. Препроцессор    | `cpp` (встроен в gcc/clang) | `main.c`              | раскрытый текст `main.i`  |
| 2. Компиляция      | `cc1` (gcc) или ядро clang  | `main.i`              | ассемблерный код `main.s` |
| 3. Ассемблирование | ассемблер `as`              | `main.s`              | объектный файл `main.o`   |
| 4. Линковка        | линковщик `ld`              | `main.o` и библиотеки | исполняемый файл `app`    |

Обычно промежуточные файлы создаются во временном каталоге и сразу удаляются. Но знать стадии нужно по очень практичной причине: **каждая ошибка сборки принадлежит одной стадии**, и по ней видно, где искать причину.

Флаг `-v` показывает реальные команды, которые запускает gcc: `gcc -v main.c -o app`. В длинном выводе вы найдёте строки с `cc1`, `as` и `collect2` (обёртка над `ld`).

## Стадия 1: препроцессор

Препроцессор работает с текстом, ничего не зная о C: выполняет директивы `#include`, `#define`, `#if`, удаляет комментарии. Остановить сборку после него можно флагом `-E`:

```c
#include <stdio.h>

#define WIDTH 8
#define AREA(w, h) ((w) * (h))

int main(void) {
    // комментарий исчезнет после препроцессора
    printf("%d\n", AREA(WIDTH, 5));
    return 0;
}
```

Вывод:

```text
40
```

Команда `gcc -E main.c` печатает результат препроцессора в терминал. Его конец выглядит так:

```text
# 6 "main.c"
int main(void) {

    printf("%d\n", ((8) * (5)));
    return 0;
}
```

Макросов и комментария больше нет, а вместо строки `#include <stdio.h>` в начало вставлено **всё содержимое** заголовка и тех, что он подключает, — сотни строк объявлений. Строки вида `# 6 "main.c"` — метки: они сообщают компилятору, из какого файла и строки пришёл текст, чтобы ошибки указывали на ваш исходник, а не на `main.i`.

## Стадия 2: компиляция в ассемблер

Это главная стадия: компилятор проверяет синтаксис и типы, оптимизирует и переводит программу в **ассемблер** — текстовую запись машинных команд конкретного процессора. Флаг `-S` останавливает сборку здесь и сохраняет `main.s`.

Для функции

```c
int square(int x) {
    return x * x;
}
```

команда `gcc -O2 -S square.c` на компьютере с процессором x86-64 даст примерно такой фрагмент:

```text
square:
        imull   %edi, %edi
        movl    %edi, %eax
        ret
```

Аргумент `x` пришёл в регистре `edi`, `imull` умножил его сам на себя, `movl` положил результат в `eax` — регистр, через который возвращается значение, `ret` вернул управление. На процессоре ARM (например, в Mac с чипом Apple) команды будут другими: ассемблер привязан к архитектуре, а код на C — нет.

Почти все ошибки, которые вы видели до сих пор, — пропущенная `;`, неизвестный тип, несовместимые типы — сообщает именно эта стадия.

## Стадия 3: ассемблирование

Ассемблер переводит текстовые команды в байты машинного кода и упаковывает их в **объектный файл**. Флаг `-c` означает «скомпилировать, но не линковать»:

```text
$ gcc -c main.c
$ ls
main.c  main.o
$ file main.o
main.o: ELF 64-bit LSB relocatable, x86-64, version 1 (SYSV), not stripped
```

Слово `relocatable` важно: объектный файл ещё **не программа**. В нём есть машинный код `main`, но на месте вызова `printf` стоит заглушка — адрес функции пока неизвестен. Подробно внутренности `.o` разберём в следующем уроке.

## Стадия 4: линковка

Линковщик собирает объектные файлы и библиотеки в исполняемый файл: подставляет вместо заглушек настоящие адреса функций, добавляет код запуска, который вызовет `main`.

```text
$ gcc main.o -o app
$ file app
app: ELF 64-bit LSB pie executable, x86-64, ...
$ ./app
40
```

Если линковщик не нашёл функцию, ошибка появится только здесь — хотя каждый файл по отдельности скомпилировался:

```c
#include <stdio.h>

int helper(int x);              // объявление есть, определения нет

int main(void) {
    printf("%d\n", helper(2));  // Ошибка компиляции: undefined reference на линковке
    return 0;
}
```

```text
/usr/bin/ld: /tmp/ccQ2xV1a.o: in function `main':
main.c:(.text+0xe): undefined reference to `helper'
collect2: error: ld returned 1 exit status
```

В сообщении нет номера строки исходника: линковщик работает с объектными файлами, где строк уже нет. `collect2` и `ld` в тексте — верный признак стадии линковки.

## Флаги остановки

| Флаг    | Последняя стадия | Результат по умолчанию                  |
| ------- | ---------------- | --------------------------------------- |
| `-E`    | препроцессор     | текст в stdout (с `-o file.i` — в файл) |
| `-S`    | компиляция       | `main.s`                                |
| `-c`    | ассемблирование  | `main.o`                                |
| без них | линковка         | `a.out` (с `-o app` — `app`)            |

Имя выходного файла образуется из имени исходника **без каталога**: `gcc -c src/util.c` создаст `util.o` в текущем каталоге. Флаг `-o` задаёт имя явно. Clang понимает те же флаги.

## Раздельная компиляция

Флаг `-c` — основа сборки больших проектов. Каждый `.c` компилируется в свой `.o` отдельно, а линковка собирает их вместе:

```text
$ gcc -c main.c          # main.o
$ gcc -c parser.c        # parser.o
$ gcc main.o parser.o -o calc
```

Если изменился только `parser.c`, достаточно перекомпилировать его и перелинковать — `main.c` не трогается. В проекте из тысячи файлов это разница между секундами и десятками минут. Следить, что именно устарело, будут Make и CMake из следующих уроков.

<Concept title="Ошибка показывает стадию">

Нет файла заголовка — препроцессор (`fatal error: … No such file or directory`). Синтаксис и типы — компилятор (`error:` с файлом, строкой и столбцом). Нет функции или она определена дважды — линковщик (`undefined reference`, `multiple definition`, `ld returned 1 exit status`). Определите стадию, прежде чем искать ошибку: от этого зависит, смотреть в код функции, в список файлов команды или в пути к заголовкам.

</Concept>

## Частые ошибки

<CommonMistake title="Искать undefined reference в коде вызова">

Вызов `helper(2)` написан правильно — иначе ошибку дал бы компилятор. Линковщику не хватает **определения**: функция не написана, файл с ней не передан в команду или имя записано по-разному.

</CommonMistake>

<CommonMistake title="Ждать файлы в каталоге исходника">

`gcc -c src/util.c` кладёт `util.o` в **текущий** каталог, а не в `src/`. Нужен другой путь — указывайте `-o build/util.o`.

</CommonMistake>

<CommonMistake title="Линковать .c и .o одной командой после правки">

`gcc main.o parser.o -o calc` после изменения `parser.c` соберёт **старую** версию: `parser.o` не пересобран. Сначала `gcc -c parser.c`, потом линковка.

</CommonMistake>

На своём компьютере выполните для любой программы `gcc -E`, `gcc -S`, `gcc -c` и откройте полученные файлы. Посчитайте строки результата препроцессора командой `gcc -E main.c | wc -l` — сравните с длиной вашего исходника.

</TryIt>

## Практика

1. **Имя выходного файла** — какую стадию выполнит команда gcc и какие файлы она создаст.

3. **Кто сообщил об ошибке** — определить стадию по тексту сообщения.

## Итоги

- Сборка — четыре стадии: препроцессор (`.i`), компиляция (`.s`), ассемблирование (`.o`), линковка (исполняемый файл).
- `-E`, `-S`, `-c` останавливают сборку после соответствующей стадии; `-o` задаёт имя результата, иначе оно берётся из имени исходника без каталога.
- Объектный файл содержит машинный код, но ещё не является программой: адреса внешних функций подставит линковщик.
- Раздельная компиляция (`-c` для каждого файла, затем линковка) позволяет пересобирать только изменённое.
- По тексту ошибки определяйте стадию: заголовки — препроцессор, синтаксис и типы — компилятор, отсутствующие и повторные определения — линковщик.
