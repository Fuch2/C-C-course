## Что делает линковщик

На вход линковщику приходят объектные файлы и библиотеки, на выходе — одна программа. Работа идёт в три шага:

1. **Разрешение символов.** Для каждого неопределённого символа (`U` в выводе `nm`) нужно найти ровно одно определение — в другом объектном файле или в библиотеке.
2. **Размещение и перемещение.** Секции всех файлов складываются вместе, каждая функция получает окончательный адрес, и заглушки на местах вызовов заполняются этими адресами.
3. **Код запуска.** Добавляется стартовый код из библиотеки C: именно он настраивает процесс, вызывает `main` и передаёт её результат в `exit`.

Почти все ошибки линковки — это сбой первого шага: определение не нашлось или нашлось дважды.

## undefined reference

```text
/usr/bin/ld: main.o: in function `main':
main.c:(.text+0x13): undefined reference to `area'
collect2: error: ld returned 1 exit status
```

Сообщение читается так: «в функции `main` из `main.o` есть обращение к `area`, но ни один файл её не определяет». Причины по частоте:

| Причина                                        | Как проверить                                  |
| ---------------------------------------------- | ---------------------------------------------- |
| файл с определением не передан в команду       | есть ли `geometry.c`/`geometry.o` в команде?   |
| имя определения отличается (опечатка, регистр) | `nm geometry.o` — какое имя там на самом деле? |
| функция объявлена `static` в другом файле      | `nm` показывает строчную `t area`              |
| не подключена библиотека                       | функция из `math.h` — нужен `-lm`              |
| библиотека указана раньше файла                | `-lcalc` должен стоять после `main.o`          |

Определение с опечаткой выглядит безобидно — объявление и вызов верны, и компилятор молчит:

```c
#include <stdio.h>

int area(int w, int h);

int main(void) {
    printf("%d\n", area(3, 4));
    return 0;
}

int aera(int w, int h) {        // Ошибка компиляции: undefined reference to `area'
    return w * h;
}
```

Если в сообщении упомянут `main`, а у вас его нет, вы, скорее всего, пытались собрать **исполняемый файл** из модуля без `main`: `gcc util.c -o util` вместо `gcc -c util.c`. Стартовому коду не к чему передать управление:

```text
/usr/bin/ld: .../crt1.o: in function `_start':
(.text+0x1b): undefined reference to `main'
```

## multiple definition

Обратная ситуация — одно имя определено в двух файлах:

```text
/usr/bin/ld: util.o: in function `log_line':
util.c:(.text+0x0): multiple definition of `log_line'; main.o:main.c:(.text+0x0): first defined here
```

Обычно виноват заголовок, в котором написано **определение** вместо объявления. `#include` вставляет текст в каждый `.c`, поэтому определение оказывается в каждом объектном файле:

```text
// log.h — неправильно
void log_line(const char *text) { printf("[log] %s\n", text); }
int log_level = 1;
```

Include guard здесь не поможет: он защищает от двойного включения в **один** файл, а `main.c` и `util.c` компилируются отдельно. Правильно — объявление в заголовке и одно определение в `.c`:

```text
// log.h
void log_line(const char *text);
extern int log_level;            // объявление переменной без определения

// log.c
#include "log.h"
int log_level = 1;               // единственное определение
void log_line(const char *text) { printf("[log] %s\n", text); }
```

Короткие функции, которые хочется держать в заголовке, объявляют `static inline` — тогда у каждого файла своя локальная копия, и конфликта нет.

## Линковщик C не проверяет типы

Линковщик сравнивает только **имена**. Если в одном файле `double scale(double)`, а в другом объявлено `int scale(int)`, программа соберётся и будет работать неправильно — это неопределённое поведение. Защита — один заголовок с объявлением, который подключают и файл с определением, и все пользователи: тогда несовпадение найдёт компилятор.

В C++ к имени добавляются типы параметров (так называемое декорирование имён), поэтому там такая ошибка превращается в `undefined reference to 'scale(int)'`.

## Библиотеки

**Статическая библиотека** `libNAME.a` — это архив объектных файлов. Её создаёт программа `ar`:

```text
$ gcc -c area.c square.c
$ ar rcs libgeometry.a area.o square.o
$ gcc main.o -L. -lgeometry -o app
```

`-L.` добавляет каталог поиска библиотек, `-lgeometry` означает «найди `libgeometry.so` или `libgeometry.a`». Из архива в программу копируются только **нужные** объектные файлы.

**Динамическая библиотека** `libNAME.so` (на macOS — `.dylib`, в Windows — `.dll`) не копируется в программу: её загружает в память загрузчик при каждом запуске. Одна копия используется всеми программами, а обновить библиотеку можно без пересборки. Библиотека C — динамическая, поэтому `printf` не нужно подключать явно.

```text
$ gcc -shared -fPIC area.c square.c -o libgeometry.so
$ gcc main.o -L. -lgeometry -o app
$ ./app
./app: error while loading shared libraries: libgeometry.so: cannot open shared object file
$ LD_LIBRARY_PATH=. ./app
12
$ ldd app
        libgeometry.so => ./libgeometry.so
        libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6
```

Ошибка `error while loading shared libraries` — уже **не ошибка сборки**: программа собрана, но при запуске загрузчик не нашёл библиотеку в стандартных каталогах. `ldd` показывает, какие библиотеки нужны программе и где они найдены.

## Порядок имеет значение

Линковщик GNU читает аргументы **слева направо** и из каждой статической библиотеки берёт только те объектные файлы, которые закрывают **уже известные** неопределённые символы. Поэтому:

```text
$ gcc -L. -lgeometry main.o -o app
main.c:(.text+0x13): undefined reference to `area'
$ gcc main.o -L. -lgeometry -o app      # работает
```

В первой команде к моменту чтения `libgeometry.a` ещё ничего не нужно — библиотека пропущена; потом `main.o` требует `area`, но к библиотеке линковщик уже не возвращается. Правило: **библиотеки — после файлов, которые их используют**, а библиотека, которая зависит от другой, — раньше неё: `-lnet -lcrypto`, если `libnet` вызывает функции `libcrypto`.

Математическая библиотека — частый случай: `sqrt`, `pow`, `sin` живут в `libm`, и на Linux нужен `-lm` в конце команды. Курсовой sandbox добавляет его сам.

<Concept title="Сначала nm, потом догадки">

При ошибке линковки не меняйте код наугад. Выпишите символ из сообщения и посмотрите `nm` каждого файла команды: где он `U`, где определён и какой буквой. Строчная буква — `static`, отсутствие — файл не тот или не передан, два определения — ищите заголовок с телом функции.

## Частые ошибки

<CommonMistake title="Определение функции в заголовке">

Всё работает, пока заголовок подключён в один `.c`. Второй `#include` — и `multiple definition`. В заголовке — объявления, `extern` для переменных и `static inline` для маленьких функций.

</CommonMistake>

<CommonMistake title="-lm в начале команды">

`gcc -lm main.c` может завершиться `undefined reference to 'sqrt'`: к моменту чтения библиотеки `sqrt` ещё никому не нужна. Пишите `gcc main.c -lm`.

</CommonMistake>

<CommonMistake title="Искать ошибку загрузки в коде">

`cannot open shared object file` при запуске — программа собрана верно, не найдена библиотека. Проверьте `ldd`, установите библиотеку в системный каталог или задайте `LD_LIBRARY_PATH` для проверки.

</CommonMistake>

1. **Разрешение символов** — смоделировать, какие ошибки выдаст линковщик для набора объектных файлов.

3. **Найди ошибку: имя определения** — исправить программу, которая не линкуется.

## Итоги

- Линковщик находит для каждого неопределённого символа одно определение, назначает адреса, заполняет заглушки и добавляет стартовый код, вызывающий `main`.
- `undefined reference` — определения нет: файл не передан, имя отличается, функция `static`, не подключена библиотека или нарушен порядок.
- `multiple definition` — определение попало в несколько файлов, обычно через заголовок; в заголовке оставляют объявления и `extern`.
- Линковщик C сравнивает только имена; согласованность типов обеспечивает общий заголовок.
- Статическая библиотека `.a` — архив `.o`, из которого копируются нужные файлы; динамическая `.so` загружается при запуске (`ldd`, `LD_LIBRARY_PATH`).
- Библиотеки указывают после файлов, которые их используют.
