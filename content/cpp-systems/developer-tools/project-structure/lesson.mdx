## Когда одного файла мало

Учебная задача помещается в один `main.c`. Настоящая программа — калькулятор выражений, игра, сервер — это десятки и сотни файлов, над которыми работают несколько человек. Без договорённостей о том, **что где лежит**, в проекте быстро становится невозможно ориентироваться: непонятно, какой файл подключать, что можно менять и что попадёт в сборку.

В C нет пакетов и пространств имён, как в других языках. Структуру проекта задают три простых инструмента, которые вы уже знаете: файлы `.h`/`.c`, флаг `-I` и `static`.

## Типичная раскладка

```text
calc/
├── include/
│   └── calc/
│       ├── lexer.h        публичные заголовки: ими пользуются другие
│       └── parser.h
├── src/
│   ├── lexer.c            реализация
│   ├── parser.c
│   ├── eval_internal.h    внутренний заголовок — только для src/
│   └── main.c             точка входа программы
├── tests/
│   ├── lexer_test.c       у тестов свой main
│   └── parser_test.c
├── build/                 результаты сборки — не хранятся в Git
├── Makefile               или CMakeLists.txt
├── README.md              что это, как собрать и запустить
└── .gitignore
```

| Каталог    | Содержимое                                        | Кто пользуется                     |
| ---------- | ------------------------------------------------- | ---------------------------------- |
| `include/` | заголовки — **интерфейс** библиотеки              | весь проект и внешние пользователи |
| `src/`     | файлы `.c` — **реализация**, внутренние заголовки | только сам модуль                  |
| `tests/`   | тестовые программы                                | разработчики, CI                   |
| `build/`   | `.o`, исполняемые файлы, сгенерированное          | никто не правит руками             |

Подкаталог `include/calc/` позволяет писать `#include "calc/parser.h"` — так сразу видно, из какой библиотеки заголовок, и не будет конфликта с чужим `parser.h`. Сборка передаёт компилятору `-Iinclude`.

## Модуль = заголовок + реализация

Модуль — пара файлов с одним именем. Заголовок отвечает на вопрос «**что** умеет модуль», файл `.c` — «**как**»:

```text
// include/calc/stack.h
#ifndef CALC_STACK_H
#define CALC_STACK_H

#include <stddef.h>          // только то, что нужно самим объявлениям

typedef struct {
    double items[64];
    size_t size;
} CalcStack;

void calc_stack_init(CalcStack *stack);
int calc_stack_push(CalcStack *stack, double value);   // 0 — успех, -1 — стек полон
int calc_stack_pop(CalcStack *stack, double *value);    // 0 — успех, -1 — стек пуст

#endif
```

```text
// src/stack.c
#include "calc/stack.h"      // свой заголовок — первым

static int is_full(const CalcStack *stack) {   // вспомогательная: не видна снаружи
    return stack->size == sizeof stack->items / sizeof stack->items[0];
}

void calc_stack_init(CalcStack *stack) { stack->size = 0; }
...
```

Правила, которые делают модуль надёжным:

- **В заголовке — только объявления**: прототипы функций, типы, `extern` для переменных, макросы. Определения функций в заголовке приводят к `multiple definition`.
- **Заголовок самодостаточен**: подключает всё, что нужно его объявлениям (здесь `stddef.h` ради `size_t`), и защищён include guard.
- **Свой заголовок — первым** в `.c`. Если заголовок забыл какой-то `#include`, ошибка проявится сразу здесь, а не у случайного пользователя, подключившего его после `stdio.h`.
- **Всё внутреннее — `static`**. Функция, которой нет в заголовке, не должна быть видна линковщику: иначе она может столкнуться с одноимённой функцией другого модуля.
- **Общий префикс имён**: `calc_stack_push`, а не `push`. В C все глобальные имена программы находятся в одном пространстве, и префикс заменяет пространства имён.

Вот как это выглядит в одном файле — секции помечены комментариями там, где в проекте прошли бы границы файлов:

```c
#include <stdio.h>

/* ---- stack.h: интерфейс ---- */
typedef struct {
    double items[4];
    int size;
} CalcStack;

void calc_stack_init(CalcStack *stack);
int calc_stack_push(CalcStack *stack, double value);
int calc_stack_pop(CalcStack *stack, double *value);

/* ---- stack.c: реализация ---- */
static int is_full(const CalcStack *stack) {
    return stack->size == 4;
}

void calc_stack_init(CalcStack *stack) {
    stack->size = 0;
}

int calc_stack_push(CalcStack *stack, double value) {
    if (is_full(stack)) {
        return -1;
    }
    stack->items[stack->size++] = value;
    return 0;
}

int calc_stack_pop(CalcStack *stack, double *value) {
    if (stack->size == 0) {
        return -1;
    }
    *value = stack->items[--stack->size];
    return 0;
}

/* ---- main.c: пользователь знает только интерфейс ---- */
int main(void) {
    CalcStack stack;
    calc_stack_init(&stack);
    for (int i = 1; i <= 5; i++) {
        if (calc_stack_push(&stack, i * 1.5) != 0) {
            printf("стек полон на %d\n", i);
        }
    }
    double value;
    while (calc_stack_pop(&stack, &value) == 0) {
        printf("%.1f\n", value);
    }
    return 0;
}
```

Вывод:

```text
стек полон на 5
6.0
4.5
3.0
1.5
```

`main` пользуется только тремя функциями из «заголовка» и кодом возврата. Как устроен стек внутри — массив или список — можно поменять, не трогая `main`.

## Зависимости между модулями

Модули образуют граф: `parser` подключает `lexer.h`, `eval` подключает `parser.h`. Хорошая структура — **слои без циклов**: нижние модули ничего не знают о верхних.

```text
main ──> eval ──> parser ──> lexer
                        └──> util
```

Если `lexer.h` начнёт подключать `parser.h`, появится цикл: модули нельзя будет понять, протестировать и переиспользовать по отдельности, а заголовки начнут требовать странного порядка включения. Обычно цикл разрывают, вынося общее (типы, константы) в отдельный нижний модуль.

## Сборка вне исходников

Объектные и исполняемые файлы складывают в отдельный каталог `build/`:

```text
$ mkdir -p build
$ gcc -Iinclude -c src/lexer.c -o build/lexer.o
$ gcc -Iinclude -c src/parser.c -o build/parser.o
$ gcc -Iinclude -c src/main.c -o build/main.o
$ gcc build/lexer.o build/parser.o build/main.o -o build/calc
```

Так исходники не смешиваются с результатами, «чистая» сборка — это `rm -r build`, а в Git попадает одна строка `build/` в `.gitignore`. Набирать такие команды вручную утомительно — их запишет Make в следующем уроке.

<Concept title="Заголовок — это договор">

Заголовок — обещание модуля остальному проекту: «эти функции существуют, принимают такие аргументы и ведут себя так». Всё, чего нет в заголовке, — внутреннее дело модуля, которое можно менять свободно. Чем меньше заголовок, тем меньше обещаний и тем легче развивать код.

</Concept>

## Частые ошибки

<CommonMistake title="Всё в одном заголовке">

Один `common.h`, который подключают все файлы и который подключает всё подряд, превращает любую правку в пересборку всего проекта и скрывает реальные зависимости. У каждого модуля — свой заголовок.

</CommonMistake>

<CommonMistake title="Вспомогательная функция без static">

`int is_full(...)` без `static` в `stack.c` и такая же в `queue.c` дадут `multiple definition`. Всё, чего нет в заголовке, объявляйте `static`.

</CommonMistake>

<CommonMistake title="Относительные пути вверх">

`#include "../../include/calc/stack.h"` ломается при переносе файла. Пишите `#include "calc/stack.h"` и задавайте каталог флагом `-Iinclude`.

</CommonMistake>

<TryIt title="Попробуйте сами">

Разделите пример со стеком на три файла — `stack.h`, `stack.c`, `main.c` — и соберите командами из раздела «Сборка вне исходников». Затем уберите `static` у `is_full` и добавьте функцию `is_full` в `main.c`: посмотрите на ошибку линковщика.

</TryIt>

## Практика

1. **Ревизия модуля** — проверить, согласованы ли заголовок и реализация.
2. **Относительный путь** — вычислить путь от одного каталога до файла.
3. **Циклические зависимости** — найти цикл в графе модулей или порядок сборки.

## Итоги

- Типичная раскладка: `include/` — интерфейс, `src/` — реализация, `tests/` — тесты, `build/` — результаты сборки вне Git.
- Модуль — пара `.h`/`.c`: в заголовке объявления, include guard и нужные ему `#include`; в `.c` свой заголовок подключается первым.
- Внутренние функции и переменные — `static`; публичные имена — с префиксом модуля.
- Зависимости модулей должны образовывать слои без циклов.
- Подкаталог `include/имя/` и флаг `-Iinclude` дают однозначные `#include "имя/модуль.h"`.
