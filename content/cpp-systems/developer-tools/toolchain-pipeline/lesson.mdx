## Два промежуточных файла, которые стоит уметь читать

В прошлом уроке сборка разделилась на стадии. Два их результата особенно полезны в работе:

- **вывод препроцессора** (`gcc -E`) отвечает на вопросы «какой заголовок на самом деле подключился», «во что раскрылся макрос», «почему компилятор видит не тот код»;
- **объектный файл** (`gcc -c`) отвечает на вопрос «что этот файл определяет и чего ему не хватает» — с этим вопросом приходит каждая ошибка линковки.

## Где препроцессор ищет заголовки

Запись `#include` бывает двух видов, и ищутся файлы по-разному:

| Запись               | Порядок поиска                                                                  |
| -------------------- | ------------------------------------------------------------------------------- |
| `#include "util.h"`  | каталог файла, в котором стоит `#include`; затем каталоги `-I`; затем системные |
| `#include <stdio.h>` | каталоги `-I`; затем системные (`/usr/include` и каталоги компилятора)          |

Кавычки — для заголовков вашего проекта, угловые скобки — для стандартной библиотеки и установленных библиотек. Флаг `-I` добавляет каталог поиска:

```text
$ ls
include/  src/
$ ls include src
include:
calc.h
src:
main.c
$ gcc -c src/main.c
src/main.c:2:10: fatal error: calc.h: No such file or directory
$ gcc -Iinclude -c src/main.c
$ ls
include/  main.o  src/
```

Без `-Iinclude` препроцессор искал `calc.h` в `src/` и в системных каталогах — и не нашёл. Флаг `-H` печатает дерево подключённых заголовков: точки показывают глубину вложенности.

```text
$ gcc -H -Iinclude -c src/main.c
. include/calc.h
.. include/types.h
. /usr/include/stdio.h
.. /usr/include/x86_64-linux-gnu/bits/libc-header-start.h
...
```

## Макросы из командной строки

Макрос можно определить, не трогая исходник: `-DNAME` — как `#define NAME 1`, `-DNAME=value` — как `#define NAME value`. Так включают отладочный код и задают параметры сборки:

```c
#include <stdio.h>

#ifndef LIMIT
#define LIMIT 100
#endif

int main(void) {
#ifdef DEBUG
    printf("отладочная сборка\n");
#endif
    printf("лимит: %d\n", LIMIT);
    return 0;
}
```

Вывод:

```text
лимит: 100
```

Это вывод обычной сборки. С флагами поведение меняется без правки кода:

```text
$ gcc main.c -o app && ./app
лимит: 100
$ gcc -DDEBUG -DLIMIT=5 main.c -o app && ./app
отладочная сборка
лимит: 5
```

Компилятор определяет и свои макросы. Самые полезные:

```c
#include <stdio.h>

int main(void) {
    printf("C23 или новее: %s\n", __STDC_VERSION__ > 201710L ? "да" : "нет");
    printf("файл: %s, строка: %d\n", __FILE__, __LINE__);
    printf("функция: %s\n", __func__);
    return 0;
}
```

Вывод:

```text
C23 или новее: да
файл: main.c, строка: 5
функция: main
```

`__STDC_VERSION__` — число вида «год и месяц стандарта»: `201710` для C17, `201112` для C11, `202311` для C23 (GCC 14 в режиме `-std=c23` пока выдаёт промежуточное `202000`, поэтому версии сравнивают через `>`). `__FILE__` и `__LINE__` подставляются там, где стоят, — на них построены `assert` и сообщения об ошибках с местом. `__func__` — не макрос, а переменная с именем текущей функции, но используется вместе с ними. Список всех предопределённых макросов показывает `gcc -dM -E - < /dev/null`.

## Зависимости: -MM

Флаг `-MM` печатает, от каких файлов проекта зависит объектный файл, — без системных заголовков:

```text
$ gcc -MM -Iinclude src/main.c
main.o: src/main.c include/calc.h include/types.h
```

Строка готова для Make: «`main.o` нужно пересобрать, если изменился любой из этих файлов». Особенно важна информация о заголовках: правка `types.h` должна пересобрать все `.c`, которые подключают его хоть через цепочку. Вернёмся к этому в уроке о Make.

## Что внутри объектного файла

Объектный файл разделён на **секции**:

| Секция    | Что в ней                                                                    |
| --------- | ---------------------------------------------------------------------------- |
| `.text`   | машинный код функций                                                         |
| `.data`   | глобальные и `static` переменные с начальным значением                       |
| `.bss`    | такие же переменные, равные нулю (место не хранится в файле — только размер) |
| `.rodata` | константы и строковые литералы                                               |

А ещё в нём есть **таблица символов** — список имён, которые файл определяет или использует. Её показывает команда `nm`. Возьмём файл:

```c
#include <stdio.h>

int counter = 5;                  // D: данные с начальным значением
int total;                        // B: данные, равные нулю
const int limits[3] = {1, 2, 3};  // R: только для чтения
static int cache[16];             // b: виден только в этом файле

static int twice(int x) {         // t: функция только этого файла
    return 2 * x;
}

int main(void) {                  // T: глобальная функция
    total = twice(counter) + limits[1] + cache[0];
    printf("%d\n", total);        // U: printf определена где-то ещё
    return 0;
}
```

Вывод:

```text
12
```

```text
$ gcc -c main.c && nm main.o
0000000000000020 b cache
0000000000000000 D counter
0000000000000000 R limits
0000000000000014 T main
                 U printf
0000000000000000 B total
0000000000000000 t twice
```

Число слева — смещение внутри секции (у вас может отличаться), буква — вид символа:

| Буква | Значение                                                              |
| ----- | --------------------------------------------------------------------- |
| `T`   | функция (секция `.text`)                                              |
| `D`   | инициализированные данные (`.data`)                                   |
| `B`   | нулевые данные (`.bss`)                                               |
| `R`   | данные только для чтения (`.rodata`)                                  |
| `U`   | **не определён** здесь — должен найтись в другом файле или библиотеке |

**Заглавная** буква — глобальный символ, виден другим файлам. **Строчная** — локальный: так выглядят `static`-функции и переменные. Линковщик никогда не свяжет чужой `U` с локальным символом — в этом и смысл `static` на уровне файла. На macOS `nm` добавляет к именам подчёркивание: `_main`, `_printf`.

## Заглушки на месте вызовов

Как выглядит вызов `printf` в машинном коде, если адрес функции неизвестен? Команда `objdump -d -r main.o` показывает код вместе с **записями о перемещении** (relocations):

```text
  3c:   e8 00 00 00 00          call   41 <main+0x2d>
                        3d: R_X86_64_PLT32      printf-0x4
```

`e8` — код команды `call`, а четыре нулевых байта — место для адреса. Строка ниже — запись для линковщика: «в байты по смещению `3d` впиши адрес `printf`». Линковка — это и есть сопоставление всех `U` с определениями и заполнение таких мест. Нет определения — нечего вписать, отсюда `undefined reference`.

<Concept title="Объектный файл — деталь с разъёмами">

Определённые символы (`T`, `D`, `B`, `R`) — выступы детали, неопределённые (`U`) — гнёзда. Линковщик вставляет каждый выступ в подходящее гнездо. Гнездо без выступа — `undefined reference`; два одинаковых выступа — `multiple definition`. `nm` показывает разъёмы, не открывая исходник.

</Concept>

## Частые ошибки

<CommonMistake title="Править путь в #include вместо флага -I">

`#include "../../include/calc.h"` ломается, как только файл переезжает в другой каталог. Пишите `#include "calc.h"` и передавайте каталог флагом `-Iinclude` — его задаст система сборки.

</CommonMistake>

<CommonMistake title="Искать static-функцию из другого файла">

`nm util.o` показывает `t parse` — строчная буква. Функция объявлена `static` и снаружи недоступна, сколько бы её ни объявляли в заголовке: линковщик сообщит `undefined reference to 'parse'`.

</CommonMistake>

<CommonMistake title="Ждать от -D изменения уже собранной программы">

Макрос из `-D` действует при **компиляции**. Запуск `./app` с другими флагами ничего не меняет — нужна пересборка.

</CommonMistake>

<TryIt title="Попробуйте сами">

Соберите пример с `nm` на своём компьютере и уберите `static` у `twice`: буква сменится с `t` на `T`. Затем удалите тело `twice`, оставив объявление, — в `nm` появится `U twice`, а линковка завершится ошибкой.

</TryIt>

## Практика

1. **Подстановка #define** — раскрыть макросы-константы в тексте программы.
2. **Таблица символов** — разобрать вывод `nm`.
3. **Дерево включений** — построить вывод `gcc -H`.
4. **Зависимости для make** — построить вывод `gcc -MM` для нескольких файлов.

## Итоги

- `#include "…"` ищет сначала рядом с файлом, `<…>` — только в каталогах `-I` и системных; `-I` добавляет каталог поиска, `-H` показывает дерево заголовков.
- `-DNAME=value` определяет макрос при сборке; `__STDC_VERSION__`, `__FILE__`, `__LINE__` определяет компилятор.
- `-MM` выводит зависимости объектного файла от файлов проекта — основа для Make.
- Объектный файл состоит из секций `.text`, `.data`, `.bss`, `.rodata` и таблицы символов; `nm` показывает её: `T`, `D`, `B`, `R` — определённые, `U` — нужные извне, строчные буквы — локальные (`static`).
- На местах вызовов внешних функций стоят заглушки с записями о перемещении; линковщик заполняет их адресами.
