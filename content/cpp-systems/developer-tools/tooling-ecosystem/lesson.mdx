## Инструменты вокруг компилятора

Компилятор, Make или CMake и отладчик — основа. Но в современном проекте на C и C++ вокруг них работает ещё несколько инструментов, которые берут на себя рутину и ловят ошибки раньше, чем их увидит человек:

| Задача                           | Инструменты                            | Когда работает                |
| -------------------------------- | -------------------------------------- | ----------------------------- |
| единый стиль кода                | clang-format                           | при сохранении файла и в CI   |
| поиск ошибок без запуска         | clang-tidy, GCC `-fanalyzer`, cppcheck | в редакторе и в CI            |
| подсказки и переходы в редакторе | clangd (языковой сервер)               | постоянно, пока вы пишете     |
| сторонние библиотеки             | vcpkg, Conan, CMake `FetchContent`     | при настройке сборки          |
| одинаковые настройки сборки      | CMake Presets                          | `cmake --preset …`            |
| проверка каждого изменения       | CI: GitHub Actions, GitLab CI          | на каждый push и pull request |

Почти все они получают сведения о проекте из одного файла — **базы команд компиляции**.

## compile_commands.json

Инструментам анализа нужно знать, с какими флагами компилируется каждый файл: стандарт, каталоги заголовков, макросы. Файл `compile_commands.json` перечисляет команду компиляции для каждого исходника:

```json
[
  {
    "directory": "/home/u/calc/build",
    "file": "/home/u/calc/src/parser.c",
    "command": "cc -std=c23 -Wall -I/home/u/calc/include -c /home/u/calc/src/parser.c"
  }
]
```

CMake создаёт его сам, если включить переменную при настройке:

```text
cmake -S . -B build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
```

clangd, clang-tidy и многие редакторы ищут этот файл в корне проекта или в каталоге `build`. Без него они «угадывают» флаги и выдают ложные ошибки вроде «не найден заголовок».

## clang-format: стиль без споров

`clang-format` переписывает код в едином стиле по правилам из файла `.clang-format` в корне проекта:

```yaml
BasedOnStyle: LLVM
IndentWidth: 4
ColumnLimit: 100
PointerAlignment: Right
```

Его запускают при сохранении в редакторе, а в CI — в режиме проверки, который ничего не меняет, но завершается ошибкой при нарушениях:

```text
clang-format --dry-run --Werror src/*.c include/*.h
```

Стиль перестаёт быть темой обсуждений на ревью: им занимается программа.

## clang-tidy: анализ без запуска

`clang-tidy` разбирает код так же, как компилятор, и проверяет сотни правил, сгруппированных по темам: `bugprone-*` (вероятные ошибки), `performance-*` (лишние копии), `modernize-*` (устаревшие конструкции), `cppcoreguidelines-*`, `cert-*` (безопасность). Настройки — в `.clang-tidy`:

```yaml
Checks: 'bugprone-*,performance-*,modernize-*,-modernize-use-trailing-return-type'
WarningsAsErrors: 'bugprone-*'
```

Статический анализ дополняет санитайзеры: санитайзер находит ошибку, только если тест выполнил ошибочную строку, а анализатор рассуждает обо всех путях выполнения сразу — но иногда ошибается в обе стороны. Для C у GCC есть встроенный анализатор `-fanalyzer`, который ищет утечки, двойные освобождения и использование после освобождения.

## clangd: редактор, который понимает проект

`clangd` — языковой сервер (LSP): редактор VS Code, Neovim, CLion или Zed спрашивает у него, где объявлена функция, какие у неё параметры, какие ошибки в файле. clangd использует ту же базу команд и тот же разбор, что и компилятор Clang, поэтому подсказки совпадают с тем, что скажет сборка, а встроенный clang-tidy показывает предупреждения прямо при наборе.

## Зависимости: vcpkg и Conan

В C и C++ нет единого стандартного менеджера пакетов, но два стали де-факто стандартом:

- **vcpkg** — список зависимостей в `vcpkg.json` рядом с `CMakeLists.txt`; при настройке CMake с toolchain-файлом vcpkg библиотеки собираются и становятся доступны через `find_package`;
- **Conan** — `conanfile.txt` или `conanfile.py`, профили компилятора и готовые двоичные пакеты.

```json
{
  "name": "calc",
  "version": "1.0.0",
  "dependencies": ["fmt", "catch2"]
}
```

Небольшие библиотеки можно подключить и средствами самого CMake — `FetchContent` скачивает исходники при настройке. В любом варианте важно фиксировать **версии**: сборка сегодня и через год должна получить одни и те же зависимости. Для этого служат ограничения версий и файлы блокировки.

## CMake Presets

Длинные команды настройки с десятком `-D` переезжают в `CMakePresets.json` — общий для команды, редактора и CI:

```json
{
  "version": 6,
  "configurePresets": [
    {
      "name": "debug",
      "binaryDir": "build/debug",
      "cacheVariables": {
        "CMAKE_BUILD_TYPE": "Debug",
        "CMAKE_EXPORT_COMPILE_COMMANDS": "ON",
        "CMAKE_C_FLAGS": "-fsanitize=address,undefined"
      }
    }
  ],
  "buildPresets": [{ "name": "debug", "configurePreset": "debug" }],
  "testPresets": [{ "name": "debug", "configurePreset": "debug" }]
}
```

Теперь `cmake --preset debug`, `cmake --build --preset debug` и `ctest --preset debug` одинаково работают у всех.

## Непрерывная интеграция

CI выполняет на сервере то, что разработчик мог забыть сделать локально: собирает проект **несколькими компиляторами** и в разных режимах, запускает тесты, санитайзеры, форматирование и статический анализ. Набор вариантов задаётся **матрицей**:

```yaml
jobs:
  build:
    strategy:
      matrix:
        compiler: [gcc, clang]
        build: [Debug, Release]
        exclude:
          - compiler: clang
            build: Release
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: cmake -S . -B build -DCMAKE_C_COMPILER=${{ matrix.compiler }} -DCMAKE_BUILD_TYPE=${{ matrix.build }}
      - run: cmake --build build
      - run: ctest --test-dir build --output-on-failure
```

Матрица из двух компиляторов и двух режимов без исключений даёт четыре задания; исключение убирает одно. Разные компиляторы находят разные ошибки и предупреждения — поэтому их и сочетают.

Вокруг компилятора работают: clang-format (единый стиль, в CI — `--dry-run --Werror`), clang-tidy и `-fanalyzer` (статический анализ), clangd (языковой сервер для редактора), vcpkg и Conan (зависимости с зафиксированными версиями), CMake Presets (общие настройки сборки) и CI с матрицей компиляторов и режимов. ## Частые ошибки

<CommonMistake title="Нет compile_commands.json">

clangd и clang-tidy без базы команд не знают каталогов заголовков и стандарта и показывают ложные ошибки. Включите `CMAKE_EXPORT_COMPILE_COMMANDS` или пресет с ним.

</CommonMistake>

<CommonMistake title="Форматирование вручную на ревью">

Замечания о пробелах в ревью тратят время людей. Настройте `.clang-format` и проверку в CI — и не обсуждайте стиль.

</CommonMistake>

<CommonMistake title="Незафиксированные версии зависимостей">

«Последняя версия» сегодня и через полгода — разные библиотеки. Указывайте ограничения версий и храните файлы блокировки в репозитории.

</CommonMistake>

## Попробуйте сами

1. Включите `CMAKE_EXPORT_COMPILE_COMMANDS` в проекте из урока о CMake и откройте получившийся файл.
2. Создайте `.clang-format` с `BasedOnStyle: LLVM` и выполните `clang-format -i` для одного файла. Что изменилось?
3. Опишите матрицу CI из трёх компиляторов и двух режимов и исключите одно сочетание. Сколько заданий получится?

## Практика

1. **Проверка форматирования** — простой вариант `clang-format --dry-run`.
2. **Подбор версии зависимости** — ограничения версий, как в менеджерах пакетов.
3. **Найди ошибку: база команд** — переполнение буфера при сборке команды компиляции.
4. **Матрица CI** — раскрытие матрицы с исключениями и дополнениями.

## Итоги

- Инструменты анализа и редакторы берут флаги из `compile_commands.json`.
- clang-format поддерживает единый стиль; в CI он проверяет его без изменений.
- clang-tidy и `-fanalyzer` ищут ошибки без запуска, дополняя санитайзеры и тесты.
- vcpkg и Conan подключают библиотеки; версии зависимостей нужно фиксировать.
- CMake Presets хранят настройки сборки, CI проверяет каждое изменение на матрице компиляторов и режимов.
