## «Является» или «содержит»

Вы знаете два способа построить класс из других: **наследование** («кошка является животным») и **композицию** («машина содержит двигатель»). Оба переиспользуют код, и новичку часто кажется, что наследование короче: унаследовал — и все методы базы уже есть. Этот урок о том, как выбирать, и о совете, который повторяют почти все руководства по C++: **предпочитайте композицию наследованию**.

Проверка простая — подстановка из урока о SOLID. Наследование уместно, если объект наследника можно передать **везде**, где ждут базу, и он выполнит все её обещания. Если нет — нужна композиция.

| Связь                                         | Пример                               | Средство                             |
| --------------------------------------------- | ------------------------------------ | ------------------------------------ |
| ведёт себя как база, подставляется вместо неё | `TemperatureSensor` — это `Sensor`   | открытое наследование от интерфейса  |
| состоит из части, владеет ею                  | процессор содержит фильтр            | поле по значению                     |
| владеет набором полиморфных частей            | процессор владеет датчиками          | `std::vector<std::unique_ptr<База>>` |
| пользуется чужим объектом                     | счёт пишет в общий журнал            | ссылка или указатель (агрегация)     |
| поведение меняется во время работы            | стратегия округления, шаги обработки | поле-интерфейс или `std::function`   |

## Наследование ради кода

Самая частая ошибка — наследовать, чтобы «получить методы бесплатно». Стек хочет хранить числа в векторе — почему бы не унаследовать вектор?

```cpp
#include <print>
#include <vector>

class Stack : public std::vector<int> {
public:
    void push(int x) {
        push_back(x);
    }
    int pop() {
        const int x = back();
        pop_back();
        return x;
    }
};

int main() {
    Stack s;
    s.push(1);
    s.push(2);
    s.insert(s.begin(), 99);  // стек так не умеет, но метод открыт
    s[1] = 42;                // и так тоже
    const int a = s.pop();
    const int b = s.pop();
    const int c = s.pop();
    std::println("{} {} {}", a, b, c);
    return 0;
}
```

Вывод:

```text
2 42 99
```

Вместе с нужными методами наследник получил **все** открытые методы вектора: вставку в середину, доступ по индексу, `clear`, `erase`. Через них любой может нарушить правило стека «работаем только с вершиной». Кроме того, у `std::vector` нет виртуального деструктора — удаление `Stack` через `std::vector<int> *` было бы неопределённым поведением. Стандартные контейнеры не предназначены для наследования.

С композицией стек сам решает, что открыть:

```cpp
#include <optional>
#include <print>
#include <vector>

class Stack {
public:
    void push(int x) {
        items_.push_back(x);
    }

    std::optional<int> pop() {
        if (items_.empty()) {
            return std::nullopt;
        }
        const int x = items_.back();
        items_.pop_back();
        return x;
    }

    std::size_t size() const {
        return items_.size();
    }

private:
    std::vector<int> items_;
};

int main() {
    Stack s;
    s.push(1);
    s.push(2);
    const auto a = s.pop();
    const auto b = s.pop();
    const auto c = s.pop();
    std::println("{} {} {}", *a, *b, c.has_value());
    return 0;
}
```

Вывод:

```text
2 1 false
```

Три открытых метода — и нарушить порядок стека невозможно. Делегирование (`push` вызывает `items_.push_back`) стоит пары строк, а охраняемый инвариант — дороже.

## Взрыв комбинаций

Наследование фиксирует поведение **при компиляции** и в одном направлении. Если объект различается по нескольким независимым признакам, наследование умножает классы. Датчик бывает температурным или давления, фильтр — диапазоном или порогом, отчёт — текстом или CSV. Иерархия на каждую комбинацию — это 2 · 2 · 2 = 8 классов вроде `TemperatureRangeCsvSensor`, и каждый новый признак удваивает их число.

Композиция собирает объект из независимых частей: 2 + 2 + 2 = 6 маленьких классов, которые комбинируются как угодно, в том числе **во время работы**:

```cpp
#include <functional>
#include <print>
#include <utility>
#include <vector>

class Pipeline {
public:
    Pipeline &then(std::function<int(int)> step) {
        steps_.push_back(std::move(step));
        return *this;
    }

    int run(int x) const {
        for (const auto &step : steps_) {
            x = step(x);
        }
        return x;
    }

private:
    std::vector<std::function<int(int)>> steps_;
};

int main() {
    Pipeline calibrate;
    calibrate.then([](int x) { return x + 2; }).then([](int x) { return x > 10 ? 10 : x; });

    Pipeline doubled;
    doubled.then([](int x) { return x * 2; }).then([](int x) { return x + 2; });

    std::println("{} {} {}", calibrate.run(4), calibrate.run(20), doubled.run(4));
    return 0;
}
```

Вывод:

```text
6 10 10
```

`Pipeline` содержит шаги, а не наследует их. Шаги можно добавлять в любом порядке, и порядок входит в договор: «сначала смещение, потом ограничение» и «наоборот» дают разные результаты. Такой приём — объект хранит подменяемое поведение — называют **стратегией**.

## Когда наследование правильно

Наследование не плохо само по себе. Оно нужно, когда код работает с **разными видами через общий интерфейс** и новые виды будут добавлять: датчики, фигуры в редакторе, способы оплаты. Лучше всего работает наследование **от интерфейса** — без данных и реализаций в базе. Глубокие иерархии с полями и кодом в каждом уровне хрупки: изменение базы ломает наследников, которых автор базы не видел.

| Вопрос                                                              | Если «да»                  |
| ------------------------------------------------------------------- | -------------------------- |
| Нужен ли объект там, где ждут базу, с выполнением всех её обещаний? | наследование от интерфейса |
| Нужны ли только некоторые методы другого класса?                    | композиция и делегирование |
| Поведение различается по нескольким независимым признакам?          | композиция частей          |
| Поведение меняется во время работы?                                 | поле-стратегия             |
| Набор видов закрыт, а операций много?                               | `std::variant`             |
| Тип известен при компиляции, нужна скорость?                        | шаблон с концептом         |

## Проект: процессор телеметрии

Третий этап проекта собирает всё вместе. `TemperatureSensor` и `PressureSensor` **являются** датчиками — наследуют интерфейс `Sensor`. `TelemetryProcessor` **содержит** фильтр (поле по значению) и **владеет** датчиками (`std::vector<std::unique_ptr<Sensor>>`). Процессор не является датчиком, хотя у обоих есть «обработка», и не наследует фильтр, хотя пользуется его проверкой.

<Concept title="Композиция или наследование">

Наследование выражает «является»: наследник подставляется везде, где ждут базу, и выполняет её обещания; лучше всего — наследование от интерфейса. Композиция выражает «содержит»: части — поля, класс открывает только нужные операции и делегирует им работу. Наследование ради повторного использования кода открывает лишние методы и ломает инварианты; стандартные контейнеры не наследуют. Независимые признаки и поведение, меняющееся во время работы, собирают композицией (стратегия). По умолчанию выбирайте композицию.

</Concept>

## Частые ошибки

<CommonMistake title="Наследование от std::vector или std::string">

Наследник получает все открытые методы и может нарушить свой инвариант через любой из них, а невиртуальный деструктор делает удаление через базу неопределённым. Храните контейнер полем.

</CommonMistake>

<CommonMistake title="Процессор — это датчик">

Если у двух классов есть похожие методы, это ещё не повод наследовать. Процессор пользуется датчиками, а не подставляется вместо них.

</CommonMistake>

<CommonMistake title="Иерархия на каждую комбинацию">

Классы вида `TemperatureRangeCsvSensor` — признак того, что независимые признаки нужно вынести в отдельные части и собирать композицией.

</CommonMistake>

## Практика

1. **Стек с ограничением** — композиция над `std::vector` и только нужные операции.
2. **Конвейер** — шаги обработки собираются во время работы.
3. **Найди ошибку: наследование ради кода** — отсортированный список, унаследованный от вектора.
4. **Проект, этап 3: процессор телеметрии** — датчики, фильтр и процессор вместе.

## Итоги

- Наследование — «является и подставляется»; композиция — «содержит и делегирует».
- Наследование ради повторного использования кода открывает лишние методы и ломает инварианты.
- Стандартные контейнеры не предназначены для наследования — храните их полями.
- Независимые признаки и сменное поведение собирают композицией, а не иерархией комбинаций.
- По умолчанию — композиция; наследование — от интерфейса, когда нужна подстановка разных видов.
