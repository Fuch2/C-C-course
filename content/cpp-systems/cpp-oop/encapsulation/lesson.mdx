## Договор класса

Теперь у вас есть всё, чтобы класс защищал свои правила: закрытые поля, конструкторы, которые сразу создают допустимый объект, и методы, которые проверяют каждое изменение. Этот урок собирает инструменты в систему. Каждая операция класса — небольшой **договор** из трёх частей:

- **предусловие** — что должно быть верно **до** вызова: «стек не пуст» для `pop`, «индекс меньше размера» для `at`;
- **постусловие** — что метод гарантирует **после**: «размер увеличился на единицу»;
- **инвариант** — что верно до и после **любого** открытого метода: «размер не больше ёмкости».

Инкапсуляция — это умение класса выполнять договор при любом поведении клиента: клиент может передать что угодно и вызывать методы в любом порядке, но объект всё равно останется допустимым.

## Кто проверяет предусловие

Нарушить предусловие можно по двум причинам, и реагировать на них нужно по-разному:

| Причина                                               | Пример                                        | Реакция                                                   |
| ----------------------------------------------------- | --------------------------------------------- | --------------------------------------------------------- |
| ожидаемая ситуация, которую клиент не может исключить | ввод пользователя, нехватка места             | результат-отказ: `bool`, `std::optional`, `std::expected` |
| ошибка в программе клиента                            | `pop` у пустого стека после проверки `size()` | `assert` или исключение                                   |

```cpp
#include <cassert>
#include <optional>
#include <print>
#include <vector>

class BoundedStack {
public:
    explicit BoundedStack(std::size_t capacity) : capacity_(capacity) {}

    bool push(int value) {
        if (items_.size() == capacity_) {
            return false;                     // нет места — ожидаемая ситуация
        }
        items_.push_back(value);
        return true;
    }

    std::optional<int> pop() {
        if (items_.empty()) {
            return std::nullopt;
        }
        int top = items_.back();
        items_.pop_back();
        return top;
    }

    int top() const {
        assert(!items_.empty() && "top() у пустого стека");
        return items_.back();
    }

    std::size_t size() const {
        return items_.size();
    }

private:
    std::size_t capacity_;
    std::vector<int> items_;
};

int main() {
    BoundedStack s(2);
    bool first = s.push(1);
    bool second = s.push(2);
    bool third = s.push(3);
    std::println("{} {} {}", first, second, third);
    std::println("{} {}", s.top(), s.size());
    int a = s.pop().value_or(-1);
    int b = s.pop().value_or(-1);
    std::println("{} {}", a, b);
    std::println("{}", s.pop().has_value());
    return 0;
}
```

Вывод:

```text
true true false
2 2
2 1
false
```

Вызовы записаны отдельными строками не случайно: порядок вычисления аргументов функции в C++ не определён, и `std::println("{} {}", s.pop()…, s.pop()…)` мог бы снять элементы в любом порядке.

`push` в полный стек и `pop` из пустого — обычные ситуации, и метод сообщает о них результатом. А `top()` у пустого стека — ошибка клиента, который должен был проверить `size()`. Её ловит `assert`: в отладочной сборке программа остановится с понятным сообщением, а не вернёт мусор.

## Строгая гарантия: всё или ничего

Самая коварная ошибка инкапсуляции — метод, который начал менять объект, обнаружил проблему на полпути и вернул отказ. Объект оказывается в промежуточном состоянии, которого договор не предусматривает:

```cpp
#include <map>
#include <print>
#include <string>
#include <vector>

struct Request {
    std::string item;
    int quantity;
};

class Warehouse {
public:
    void add(const std::string &item, int quantity) {
        stock_[item] += quantity;
    }

    bool take_all(const std::vector<Request> &order) {
        for (const Request &r : order) {             // сначала проверяем всё
            auto it = stock_.find(r.item);
            if (it == stock_.end() || it->second < r.quantity) {
                return false;
            }
        }
        for (const Request &r : order) {             // потом меняем всё
            stock_[r.item] -= r.quantity;
        }
        return true;
    }

    int count(const std::string &item) const {
        auto it = stock_.find(item);
        return it == stock_.end() ? 0 : it->second;
    }

private:
    std::map<std::string, int> stock_;
};

int main() {
    Warehouse w;
    w.add("болт", 10);
    w.add("гайка", 3);
    bool ok = w.take_all({{"болт", 4}, {"гайка", 5}});
    std::println("{} {} {}", ok, w.count("болт"), w.count("гайка"));
    ok = w.take_all({{"болт", 4}, {"гайка", 3}});
    std::println("{} {} {}", ok, w.count("болт"), w.count("гайка"));
    return 0;
}
```

Вывод:

```text
false 10 3
true 6 0
```

Метод устроен в две фазы: **проверка** без изменений и **применение** без отказов. Если бы проверка и списание шли в одном цикле, неудачный заказ успел бы списать 4 болта, прежде чем обнаружить нехватку гаек. Такое поведение называют **строгой гарантией**: операция либо выполняется целиком, либо не меняет объект вовсе — как транзакция в базе данных.

## Проверка инварианта

Сложный инвариант удобно записать отдельным закрытым методом и проверять `assert` в конце каждой изменяющей операции. В выпускной сборке с `-DNDEBUG` проверки исчезнут и ничего не будут стоить, а при разработке поймают ошибку **в том методе, который её внёс**:

```cpp
#include <cassert>
#include <print>

class Interval {
public:
    Interval(int low, int high) : low_(low), high_(high) {
        if (low_ > high_) {
            int t = low_;
            low_ = high_;
            high_ = t;
        }
        assert(invariant());
    }

    void extend_to(int x) {
        if (x < low_) {
            low_ = x;
        }
        if (x > high_) {
            high_ = x;
        }
        assert(invariant());
    }

    int length() const {
        return high_ - low_;
    }

private:
    bool invariant() const {
        return low_ <= high_;
    }

    int low_;
    int high_;
};

int main() {
    Interval i(5, 2);
    i.extend_to(10);
    i.extend_to(-1);
    std::println("{}", i.length());
    return 0;
}
```

Вывод:

```text
11
```

Это тот же приём, что в модуле «Углублённый C» для структур данных: функция проверки инварианта после каждого изменения. Внутри класса он особенно удобен — проверка находится рядом с данными и вызывается из всех методов одинаково.

## Контракты в C++26

Предусловия и постусловия так важны, что следующий стандарт, C++26, добавляет для них синтаксис: `int top() const pre(!empty());` — условие становится частью объявления функции, его видят и читатель, и инструменты, а компилятор может проверять его при вызове. GCC 14 и Clang 19 из песочницы курса контрактов ещё не поддерживают, поэтому в примерах мы пишем `assert`; но идея та же — договор, записанный явно.

<Concept title="Инкапсуляция">

Каждая операция класса — договор: предусловие, постусловие и общий для всех методов инвариант. Ожидаемые нарушения предусловий метод обрабатывает результатом (`bool`, `std::optional`, `std::expected`), ошибки клиента — `assert` или исключением. Строгая гарантия: операция выполняется целиком или не меняет объект — сначала все проверки, потом все изменения. Сложный инвариант проверяют закрытым методом через `assert` в конце изменяющих операций.

</Concept>

## Частые ошибки

<CommonMistake title="Изменение до проверки">

Метод меняет поля, а потом обнаруживает, что операция невозможна, и возвращает `false`. Объект остаётся наполовину изменённым. Сначала все проверки, потом все изменения.

</CommonMistake>

<CommonMistake title="assert для ввода пользователя">

`assert(age >= 0)` для числа, введённого пользователем, исчезнет в выпускной сборке, и проверки не останется. `assert` — только для ошибок в программе; данные снаружи проверяют явно.

</CommonMistake>

<CommonMistake title="Отказ без сообщения">

Метод молча ничего не делает при недопустимом вызове, и клиент не знает, что операция не выполнена. Сообщите об отказе результатом или исключением.

</CommonMistake>

## Практика

1. **Ограниченный стек** — отказ при переполнении и `std::optional` при пустом стеке.
2. **Бронирование** — интервалы без пересечений.
3. **Найди ошибку: заказ наполовину** — изменение до завершения проверок.
4. **Касса** — инвариант баланса и операции со строгой гарантией.

## Итоги

- Договор операции — предусловие, постусловие и инвариант класса.
- Ожидаемые нарушения сообщают результатом (`bool`, `optional`, `expected`), ошибки в программе ловят `assert` или исключение.
- Строгая гарантия: сначала все проверки, потом все изменения; неудачная операция не меняет объект.
- Сложный инвариант проверяют закрытым методом через `assert` в конце каждой изменяющей операции.
- C++26 добавляет контракты `pre` и `post` — тот же договор в синтаксисе языка.
