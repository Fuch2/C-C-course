## Зачем прятать представление

Закрытые поля защищают инвариант — это вы уже видели. Вторая, не менее важная причина: **закрытое можно менять**. Если клиенты не знают, как устроен объект внутри, его устройство можно переделать — ради скорости, точности или новой задачи, — и ни одной строки клиентского кода не придётся трогать.

Способ хранения данных внутри объекта называют **представлением**. Хороший класс отделяет «что объект умеет» (интерфейс) от «как он это хранит» (представление).

## Пример: деньги

Первая версия класса денег хранит сумму в рублях типом `double`:

```cpp
#include <print>

class Money {
public:
    explicit Money(double rubles) : rubles_(rubles) {}

    void add(Money other) {
        rubles_ += other.rubles_;
    }

    void print() const {
        std::println("{:.2f} руб.", rubles_);
    }

    bool equals(Money other) const {
        return rubles_ == other.rubles_;
    }

private:
    double rubles_;
};

int main() {
    Money a(0.1);
    a.add(Money(0.2));
    a.print();
    std::println("{}", a.equals(Money(0.3)));
    return 0;
}
```

Вывод:

```text
0.30 руб.
false
```

Печать выглядит правильно, но `0.1 + 0.2` в `double` не равно `0.3` — и сравнение сумм врёт. Для денег `double` не годится. Поскольку поле закрыто, представление можно заменить на целое число копеек, **не меняя интерфейс**:

```cpp
#include <cmath>
#include <print>

class Money {
public:
    explicit Money(double rubles) : kopecks_(std::llround(rubles * 100)) {}

    void add(Money other) {
        kopecks_ += other.kopecks_;
    }

    void print() const {
        std::println("{}.{:02} руб.", kopecks_ / 100, kopecks_ % 100);
    }

    bool equals(Money other) const {
        return kopecks_ == other.kopecks_;
    }

private:
    long long kopecks_;
};

int main() {
    Money a(0.1);
    a.add(Money(0.2));
    a.print();
    std::println("{}", a.equals(Money(0.3)));
    return 0;
}
```

Вывод:

```text
0.30 руб.
true
```

`main` не изменился ни на символ, а ошибка исчезла. Если бы клиенты обращались к полю `rubles_` напрямую, пришлось бы искать и исправлять каждое обращение во всём проекте. `std::llround` округляет до ближайшего целого и возвращает `long long`. (Печать здесь рассчитана на неотрицательные суммы — чтобы не отвлекаться от главного.)

## Доступ — для класса, а не для объекта

Обратите внимание на `other.kopecks_` в методе `add`: метод одного объекта читает закрытое поле **другого** объекта. Это разрешено: `private` ограничивает доступ для **кода других классов и функций**, а не для других экземпляров того же класса. Методы `Money` видят закрытые поля любого `Money`. Именно поэтому сравнение и сложение удобно писать методами.

## Закрытые методы

Закрытыми бывают не только поля, но и методы: вспомогательные операции, которые нужны реализации, но не клиенту. Закрытый метод можно переписать, переименовать или удалить, никого не задев:

```cpp
#include <print>
#include <string>
#include <string_view>
#include <utility>

class Password {
public:
    explicit Password(std::string text) : text_(std::move(text)) {}

    int strength() const {
        return long_enough() + has_any("0123456789") + has_any("ABCDEFGHIJKLMNOPQRSTUVWXYZ") +
               has_any("!@#$%^&*?.,-_");
    }

private:
    bool long_enough() const {
        return text_.size() >= 8;
    }

    bool has_any(std::string_view chars) const {
        return text_.find_first_of(chars) != std::string::npos;
    }

    std::string text_;
};

int main() {
    for (const char *p : {"qwerty", "qwerty123", "Qwerty123!"}) {
        std::println("{}: {}", p, Password(p).strength());
    }
    return 0;
}
```

Вывод:

```text
qwerty: 0
qwerty123: 2
Qwerty123!: 4
```

Клиент видит только `strength()`. Как пароль проверяется по частям — дело класса: `long_enough` и `has_any` можно переписать или заменить, не тронув ни одного клиента. Сумма `bool` даёт число: `true` превращается в 1, `false` — в 0.

## Что открыть, а что спрятать

Помогает простой вопрос: **понадобится ли это клиенту, если представление поменяется?**

| Скорее открыть                                                          | Скорее закрыть                                       |
| ----------------------------------------------------------------------- | ---------------------------------------------------- |
| операции предметной области                                             | поля                                                 |
| запросы, ответ на которые не зависит от хранения: `size()`, `balance()` | вспомогательные методы и промежуточные вычисления    |
| константы, которые входят в договор: `max_items`                        | детали формата хранения: «в копейках», «в кельвинах» |

Если сомневаетесь — закрывайте. Открыть закрытое позже легко и безопасно; закрыть открытое — значит сломать клиентов.

## `friend` — исключение из правила

Иногда закрытые данные нужны функции, которая не может быть методом класса. Такую функцию можно объявить **другом** класса — `friend`. Друг видит закрытые члены, как метод:

```cpp
#include <print>

class Vector2 {
public:
    Vector2(double x, double y) : x_(x), y_(y) {}
    friend double dot(Vector2 a, Vector2 b);

private:
    double x_;
    double y_;
};

double dot(Vector2 a, Vector2 b) {
    return a.x_ * b.x_ + a.y_ * b.y_;
}

int main() {
    std::println("{}", dot(Vector2(1, 2), Vector2(3, 4)));
    return 0;
}
```

Вывод:

```text
11
```

`friend` — часть интерфейса класса: дружбу объявляет сам класс, и чужой код её себе не присвоит. Но каждый друг — ещё одно место, которое придётся переписать при смене представления. Применяйте его редко: главным образом для операторов, о которых будет отдельный урок. Если функции хватает открытых методов — дружба не нужна.

<Concept title="Закрытое представление">

Представление — способ хранения данных внутри объекта. Закрытые поля и методы можно менять, не трогая клиентов, — это вторая причина закрывать данные, наряду с защитой инварианта. Доступ `private` проверяется по классу: методы видят закрытые члены любого объекта своего класса. Вспомогательные операции делают закрытыми методами; `friend` открывает закрытое для конкретной внешней функции и применяется редко.

</Concept>

## Частые ошибки

<CommonMistake title="Интерфейс, повторяющий представление">

`double rubles() const` и `void set_rubles(double)` привязывают клиентов к хранению в рублях. После перехода на копейки эти методы придётся либо сохранить с потерей точности, либо сломать клиентов. Открывайте операции, а не форму хранения.

</CommonMistake>

<CommonMistake title="Деньги в double">

Двоичная дробь не может точно хранить 0.1, поэтому суммы перестают сравниваться и накапливают погрешность. Деньги хранят в целых минимальных единицах (копейках, центах) или в специальном десятичном типе.

</CommonMistake>

<CommonMistake title="friend вместо продуманного интерфейса">

Если внешней функции нужны внутренности класса, сначала подумайте, не нужен ли классу открытый метод. Дружба для удобства размывает границу, ради которой поля закрывали.

</CommonMistake>

## Практика

1. **Температура** — интерфейс в градусах Цельсия, хранение в кельвинах.
2. **Время в секундах** — представление, удобное для арифметики.
3. **Найди ошибку: деньги в double** — смена представления без смены интерфейса.
4. **Множество малых чисел** — битовое представление за простым интерфейсом.

## Итоги

- Закрытое представление можно заменить, не трогая клиентов; открытое — нельзя.
- Интерфейс описывает операции, а не форму хранения.
- `private` проверяется по классу: методы видят закрытые поля других объектов того же класса.
- Вспомогательные методы делают закрытыми.
- Деньги хранят в целых минимальных единицах, а не в `double`.
- `friend` даёт внешней функции доступ к закрытому; применяется редко.
