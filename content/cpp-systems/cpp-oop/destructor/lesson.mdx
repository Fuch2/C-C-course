## Последний метод объекта

Конструктор вызывается, когда объект появляется. Его пара — **деструктор** — вызывается, когда объект исчезает. Имя деструктора — имя класса с тильдой, у него нет ни параметров, ни возвращаемого значения:

```cpp
#include <print>
#include <string>
#include <utility>

class Guard {
public:
    explicit Guard(std::string name) : name_(std::move(name)) {
        std::println("вход: {}", name_);
    }

    ~Guard() {
        std::println("выход: {}", name_);
    }

private:
    std::string name_;
};

int main() {
    Guard a("main");
    {
        Guard b("блок");
        std::println("работа в блоке");
    }
    Guard c("после блока");
    std::println("конец main");
    return 0;
}
```

Вывод:

```text
вход: main
вход: блок
работа в блоке
выход: блок
вход: после блока
конец main
выход: после блока
выход: main
```

Деструктор вызывает **компилятор**, а не программист: для локального объекта — в момент, когда выполнение покидает его блок. Никакой строки `b.destroy()` в программе нет, и забыть её невозможно. Объекты блока уничтожаются в порядке, **обратном** созданию: `c` создан последним — уничтожен первым. Так позднее созданный объект, который мог зависеть от ранних, исчезает раньше них.

## Когда заканчивается жизнь объекта

| Объект                             | Деструктор вызывается                                                 |
| ---------------------------------- | --------------------------------------------------------------------- |
| локальная переменная               | при выходе из блока — обычном, через `return`, `break` или исключение |
| поле другого объекта               | после деструктора объекта-владельца                                   |
| элемент контейнера                 | при удалении элемента или уничтожении контейнера                      |
| временный объект `Guard("x")`      | в конце полного выражения — обычно в конце строки                     |
| глобальная или `static` переменная | после завершения `main`                                               |

Выход «через исключение» особенно важен. В уроке об исключениях вы видели **раскрутку стека**: при броске исключения все локальные объекты по пути до `catch` уничтожаются. Деструкторы вызываются и тогда — поэтому работа, записанная в деструкторе, выполняется при любом пути выхода.

## Порядок разрушения полей

Поля объекта уничтожаются **после** тела деструктора, в порядке, обратном объявлению. Конструирование идёт в прямом порядке: сначала поля (в порядке объявления), потом тело конструктора.

```cpp
#include <print>
#include <string>
#include <utility>

class Part {
public:
    explicit Part(std::string name) : name_(std::move(name)) {
        std::println("+ {}", name_);
    }
    ~Part() {
        std::println("- {}", name_);
    }

private:
    std::string name_;
};

class Car {
public:
    Car() : engine_("двигатель"), wheels_("колёса") {
        std::println("+ машина");
    }
    ~Car() {
        std::println("- машина");
    }

private:
    Part engine_;
    Part wheels_;
};

int main() {
    Car car;
    std::println("едем");
    return 0;
}
```

Вывод:

```text
+ двигатель
+ колёса
+ машина
едем
- машина
- колёса
- двигатель
```

Картина зеркальная: машина собирается из готовых частей и разбирается, пока части ещё целы. В теле деструктора `Car` можно пользоваться всеми полями — они уничтожатся только после него.

## RAII: ресурс в руках объекта

Главное применение деструктора — **освобождение ресурсов**: памяти из кучи, открытых файлов, сетевых соединений, блокировок. Приём называется **RAII** (Resource Acquisition Is Initialization — «получение ресурса есть инициализация»): ресурс захватывается в конструкторе и освобождается в деструкторе. Тогда владелец ресурса — объект, и время жизни ресурса совпадает со временем жизни объекта.

```cpp
#include <print>

class IntBuffer {
public:
    explicit IntBuffer(int size) : data_(new int[size]{}), size_(size) {}

    ~IntBuffer() {
        delete[] data_;
    }

    IntBuffer(const IntBuffer &) = delete;
    IntBuffer &operator=(const IntBuffer &) = delete;

    void set(int i, int value) {
        data_[i] = value;
    }

    long long sum() const {
        long long s = 0;
        for (int i = 0; i < size_; i++) {
            s += data_[i];
        }
        return s;
    }

private:
    int *data_;
    int size_;
};

int main() {
    IntBuffer buffer(5);
    for (int i = 0; i < 5; i++) {
        buffer.set(i, i * i);
    }
    std::println("{}", buffer.sum());
    return 0;
}
```

Вывод:

```text
30
```

`new int[size]{}` — C++-аналог `calloc`: выделяет массив в куче и обнуляет его; `delete[]` — аналог `free` для массивов. В C каждый `malloc` требовал парного `free` на каждом пути выхода из функции — вспомните `goto cleanup` из модуля «Углублённый C». Здесь освобождение записано **один раз**, в деструкторе, и выполнится при любом выходе из `main`. Утечка невозможна, пока объект владеет памятью.

## Запрет копирования

Две странные строки с `= delete` в `IntBuffer` защищают от серьёзной ошибки. По умолчанию C++ умеет копировать любой объект, копируя его поля. Копия `IntBuffer` получила бы **тот же указатель** `data_`, и в конце оба объекта вызвали бы `delete[]` для одного массива — двойное освобождение. Объявление `= delete` запрещает копирование: строка `IntBuffer b2 = buffer;` перестаёт компилироваться.

Правило на будущее: если класс владеет ресурсом и вы пишете ему деструктор, решите, что делать с копированием, — запретить его или реализовать правильно. Подробно об этом — в модуле «Время жизни объектов»: правило трёх, правило пяти и перемещение. А в реальном коде память почти никогда не держат «голым» указателем: для этого есть `std::vector` и умные указатели, которые уже реализуют RAII.

## Деструктор не должен бросать исключений

Деструктор вызывается в том числе во время раскрутки стека, когда одно исключение уже летит. Если в этот момент деструктор бросит второе, программа немедленно завершится через `std::terminate`. Поэтому деструкторы в C++ по умолчанию помечены `noexcept`, а ошибки при освобождении ресурса в деструкторе только записывают в журнал или игнорируют.

<Concept title="Деструктор">

Деструктор `~Класс()` вызывается автоматически, когда кончается жизнь объекта: при выходе из блока (в том числе через исключение), при удалении из контейнера, в конце выражения для временных объектов. Локальные объекты уничтожаются в порядке, обратном созданию, поля — после тела деструктора в порядке, обратном объявлению. RAII связывает ресурс с объектом: захват в конструкторе, освобождение в деструкторе. Класс, владеющий ресурсом, должен запретить или правильно реализовать копирование; деструктор не бросает исключений.

</Concept>

## Частые ошибки

<CommonMistake title="Захват без освобождения">

Класс выделяет память в конструкторе, но у него нет деструктора. Каждый объект оставляет утечку; LeakSanitizer сообщит о ней при завершении программы.

</CommonMistake>

<CommonMistake title="Копирование класса с ресурсом">

Класс с `new` в конструкторе и `delete` в деструкторе, но без запрета копирования: копия разделит указатель, и программа освободит память дважды. Пишите `= delete` для копирования или храните ресурс в стандартном типе.

</CommonMistake>

<CommonMistake title="delete вместо delete[]">

Память из `new T[n]` освобождают только `delete[]`, а из `new T` — только `delete`. Перепутанная пара — неопределённое поведение; AddressSanitizer сообщает `alloc-dealloc-mismatch`.

</CommonMistake>

<CommonMistake title="Явный вызов деструктора">

`b.~Guard();` для обычного объекта — ошибка: компилятор всё равно вызовет деструктор при выходе из блока, и он выполнится дважды. Деструктор вызывают явно только в редких низкоуровневых случаях.

</CommonMistake>

## Итоги

- Деструктор `~Класс()` вызывается автоматически в конце жизни объекта — при любом выходе из блока, включая исключения.
- Локальные объекты уничтожаются в обратном порядке; поля — после тела деструктора, в порядке, обратном объявлению.
- RAII: ресурс захватывается в конструкторе и освобождается в деструкторе — забыть освобождение невозможно.
- Класс, владеющий ресурсом, запрещает копирование (`= delete`) или реализует его правильно.
- `new T[n]` освобождают `delete[]`; деструктор не бросает исключений.
