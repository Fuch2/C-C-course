## Наследник там, где ждут базу

Главная сила наследования — не в экономии строк. Объект наследника можно передать **туда, где ожидают базовый класс**: функция, принимающая `const Employee &`, примет и `Manager`, и `Intern`, и любого будущего наследника, о котором автор функции ничего не знал.

```cpp
#include <print>
#include <string>
#include <utility>

class Employee {
public:
    Employee(std::string name, int salary) : name_(std::move(name)), salary_(salary) {}

    const std::string &name() const {
        return name_;
    }

    int salary() const {
        return salary_;
    }

private:
    std::string name_;
    int salary_;
};

class Manager : public Employee {
public:
    Manager(std::string name, int salary, int team) : Employee(std::move(name), salary), team_(team) {}

    int team() const {
        return team_;
    }

private:
    int team_;
};

void print_badge(const Employee &e) {
    std::println("[{} | {}]", e.name(), e.salary());
}

int main() {
    Employee ada("Ада", 120000);
    Manager alan("Алан", 150000, 4);
    print_badge(ada);
    print_badge(alan);
    const Employee &ref = alan;
    std::println("{}", ref.name());
    return 0;
}
```

Вывод:

```text
[Ада | 120000]
[Алан | 150000]
Алан
```

Ссылка (или указатель) на базовый класс может указывать на объект наследника: внутри `Manager` есть базовая часть `Employee`, и ссылка указывает на неё. Такое преобразование «вверх по иерархии» происходит **неявно**. Через ссылку на базу видно только то, что есть у базы: `ref.team()` не скомпилируется, хотя объект — руководитель.

## Виды наследования

Слово перед именем базового класса — вид наследования. Оно определяет, кто **снаружи** знает, что `Manager` — это `Employee`:

| Запись                  | Открытые члены базы в наследнике | Преобразование в `Base &` снаружи |
| ----------------------- | -------------------------------- | --------------------------------- |
| `class D : public B`    | остаются открытыми               | разрешено                         |
| `class D : protected B` | становятся защищёнными           | только внутри иерархии            |
| `class D : private B`   | становятся закрытыми             | только внутри `D`                 |

Почти всегда нужно `public`: оно и выражает отношение «является». Закрытое наследование означает «реализовано с помощью» — то же, что композиция, только запутаннее; в современном коде вместо него используют поле.

Ловушка: у `class` наследование по умолчанию **закрытое**. `class Manager : Employee` без слова `public` — и `print_badge(alan)` перестаёт компилироваться с сообщением `'Employee' is an inaccessible base of 'Manager'`. У `struct` наследование по умолчанию открытое, но писать `public` явно стоит всегда.

## Принцип подстановки

Если функция работает с `Employee`, она должна правильно работать с **любым** наследником — не зная, какой именно ей достался. Это **принцип подстановки Лисков** (буква L в SOLID): объект наследника должен годиться везде, где годится объект базы, и не преподносить сюрпризов.

Формально: наследник выполняет договор базы. Он не требует от клиента большего (предусловия не строже) и не обещает меньшего (постусловия не слабее). Компилятор проверить это не может — это ответственность автора класса.

Классический пример нарушения — «квадрат является прямоугольником»:

```cpp
#include <print>

class Rectangle {
public:
    Rectangle(int w, int h) : w_(w), h_(h) {}

    void set_width(int w) {
        w_ = w;
    }

    void set_height(int h) {
        h_ = h;
    }

    int area() const {
        return w_ * h_;
    }

protected:
    int w_;
    int h_;
};

class Square : public Rectangle {
public:
    explicit Square(int side) : Rectangle(side, side) {}

    void set_width(int w) {           // поддерживаем инвариант квадрата
        w_ = h_ = w;
    }
};

void stretch(Rectangle &r) {
    r.set_width(10);
    r.set_height(5);
    std::println("ожидаем 50, получили {}", r.area());
}

int main() {
    Rectangle r(1, 1);
    Square s(1);
    stretch(r);
    stretch(s);
    s.set_width(10);
    std::println("квадрат: {}", s.area());
    return 0;
}
```

Вывод:

```text
ожидаем 50, получили 50
ожидаем 50, получили 50
квадрат: 100
```

Через ссылку на `Rectangle` вызывается `Rectangle::set_width`, и «квадрат» становится прямоугольником 10 × 5 — его инвариант нарушен. А если сделать `set_width` выбираемым по объекту (урок о `virtual`), сломается уже `stretch`: она получит 25 вместо 50. Выхода нет, потому что договор прямоугольника — «ширина и высота меняются независимо» — квадрат выполнить не может. В геометрии квадрат — прямоугольник, а в программе с изменяемыми сторонами — нет. Решения: не наследовать (`Square` — отдельный класс) или сделать фигуры неизменяемыми.

`protected` в этом примере — третий уровень доступа: поля видны наследникам, но не внешнему коду. Ему посвящён следующий урок.

## Проверка «является» по договору

Перед тем как наследовать, спросите не «похожи ли объекты», а «может ли наследник выполнить **все обещания** базы». Типичные признаки нарушения:

- метод наследника бросает исключение там, где база работает («пингвин — птица, но `fly()` бросает»);
- наследник требует от аргументов больше, чем база («база принимает любую сумму, наследник — только кратную 100»);
- наследник «отключает» метод базы пустой реализацией.

<Concept title="Публичное наследование">

При открытом наследовании ссылка или указатель на базу может указывать на объект наследника (неявное преобразование вверх), и функции для базы работают с любыми наследниками. Через ссылку на базу виден только интерфейс базы. У `class` наследование по умолчанию закрытое — пишите `public` явно. Принцип подстановки Лисков: наследник выполняет договор базы — предусловия не строже, постусловия не слабее; иначе наследование ошибочно, даже если объекты «похожи».

</Concept>

## Частые ошибки

<CommonMistake title="Забытое public">

`class Manager : Employee` — закрытое наследование. Снаружи `Manager` больше не `Employee`: его нельзя передать в функцию для сотрудников, а открытые методы базы недоступны.

</CommonMistake>

<CommonMistake title="Наследник, который не выполняет договор базы">

Квадрат с изменяемыми сторонами, «птица», которая не летает, «список только для чтения», бросающий исключение из `add`. Клиенты базы сломаются на таком наследнике. Выбирайте композицию или другую иерархию.

</CommonMistake>

<CommonMistake title="Обращение к членам наследника через ссылку на базу">

`const Employee &e = manager; e.team();` — ошибка компиляции: через ссылку на базу виден только её интерфейс. Если функции нужно что-то от наследника, она должна принимать наследника — или поведение должно быть в интерфейсе базы (урок о `virtual`).

</CommonMistake>

## Практика

1. **Бейджи** — одна функция для базы и разных наследников.
2. **Документы в архиве** — архив принимает любой документ через базовый класс.
3. **Найди ошибку: закрытый наследник** — наследование без `public`.
4. **Подстановка счётчиков** — наследник, сохраняющий договор базы.

## Итоги

- Ссылка или указатель на базу может указывать на объект наследника; функции для базы работают с любыми наследниками.
- Через ссылку на базу виден только интерфейс базы.
- Вид наследования: `public` — «является», `private` — «реализовано с помощью» (лучше композиция); у `class` по умолчанию `private`.
- Принцип подстановки Лисков: наследник выполняет договор базы — не требует больше и не обещает меньше.
- Похожесть объектов — не повод наследовать; повод — способность выполнить все обещания базы.
