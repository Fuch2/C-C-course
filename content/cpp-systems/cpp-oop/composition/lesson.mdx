## Объект из объектов

Сложные вещи собирают из простых. Автомобиль состоит из двигателя, колёс и кузова; документ — из страниц; заказ — из позиций и адреса доставки. В программе это выражается **композицией**: объект содержит другие объекты как свои поля.

Вы уже встречали композицию много раз: класс с полем `std::string` или `std::vector` — это композиция. Этот урок — о том, как проектировать такие классы: кто за что отвечает, как части создаются и уничтожаются, как внешний класс пользуется частями, не раскрывая их клиентам.

## Части — поля

```cpp
#include <print>
#include <string>
#include <utility>
#include <vector>

class Address {
public:
    Address(std::string city, std::string street) : city_(std::move(city)), street_(std::move(street)) {}

    std::string text() const {
        return city_ + ", " + street_;
    }

private:
    std::string city_;
    std::string street_;
};

class Line {
public:
    Line(std::string item, int price, int quantity)
        : item_(std::move(item)), price_(price), quantity_(quantity) {}

    int cost() const {
        return price_ * quantity_;
    }

private:
    std::string item_;
    int price_;
    int quantity_;
};

class Order {
public:
    explicit Order(Address address) : address_(std::move(address)) {}

    void add(Line line) {
        lines_.push_back(std::move(line));
    }

    int total() const {
        int sum = 0;
        for (const Line &line : lines_) {
            sum += line.cost();
        }
        return sum;
    }

    void print() const {
        std::println("{} позиции на {} руб., доставка: {}", lines_.size(), total(), address_.text());
    }

private:
    Address address_;
    std::vector<Line> lines_;
};

int main() {
    Order order(Address("Казань", "Баумана, 1"));
    order.add(Line("книга", 450, 2));
    order.add(Line("лампа", 1200, 1));
    order.print();
    return 0;
}
```

Вывод:

```text
2 позиции на 2100 руб., доставка: Казань, Баумана, 1
```

Каждый класс отвечает за своё: `Line` знает, сколько стоит позиция, `Address` — как выглядит адрес, `Order` — как из позиций получается сумма. `Order` не лезет в поля `Line`, а спрашивает `line.cost()`. Если завтра у позиции появится скидка, изменится только `Line::cost`.

## Владение и время жизни

При композиции внешний объект **владеет** частями: части создаются вместе с ним и уничтожаются вместе с ним. Как вы видели в уроке о деструкторе, поля конструируются до тела конструктора и уничтожаются после тела деструктора, в обратном порядке. Отдельно освобождать части не нужно — у `Order` нет деструктора, но адрес, все позиции и сам вектор будут уничтожены вовремя.

Владение означает и то, что части **копируются вместе** с владельцем: копия заказа получает свои адрес и позиции, независимые от оригинала.

```cpp
#include <print>
#include <string>
#include <vector>

class Playlist {
public:
    void add(const std::string &song) {
        songs_.push_back(song);
    }

    std::size_t size() const {
        return songs_.size();
    }

private:
    std::vector<std::string> songs_;
};

int main() {
    Playlist morning;
    morning.add("Утро");
    Playlist copy = morning;
    copy.add("День");
    std::println("{} {}", morning.size(), copy.size());
    return 0;
}
```

Вывод:

```text
1 2
```

Копирование класса из стандартных частей работает правильно само: вектор копирует строки, строки копируют символы. Вот почему классы стоит собирать из стандартных типов, а не хранить «голые» указатели на память — в уроке о деструкторе такой класс пришлось защищать запретом копирования.

## Делегирование

Внешний объект часто открывает клиентам операции, которые сам выполняет руками частей. Это называют **делегированием**:

```cpp
#include <print>
#include <string>

class Engine {
public:
    bool start() {
        if (fuel_ <= 0) {
            return false;
        }
        running_ = true;
        return true;
    }

    void refuel(int liters) {
        fuel_ += liters;
    }

    bool running() const {
        return running_;
    }

private:
    int fuel_ = 0;
    bool running_ = false;
};

class Car {
public:
    explicit Car(std::string model) : model_(std::move(model)) {}

    void refuel(int liters) {
        engine_.refuel(liters);
    }

    void start() {
        std::println("{}: {}", model_, engine_.start() ? "поехали" : "нет топлива");
    }

private:
    std::string model_;
    Engine engine_;
};

int main() {
    Car car("Нива");
    car.start();
    car.refuel(40);
    car.start();
    return 0;
}
```

Вывод:

```text
Нива: нет топлива
Нива: поехали
```

Клиент `Car` не знает об `Engine` — он видит `refuel` и `start`. Двигатель можно поменять (электромотор, гибрид), не трогая клиентов. Плохая альтернатива — метод `Engine &engine()`, отдающий двигатель наружу: тогда клиенты начнут вызывать `car.engine().refuel(…)`, и замена двигателя затронет их всех. Это нарушение принципа, который называют **законом Деметры**: «разговаривай только с непосредственными друзьями» — не тянитесь через объект к его частям.

## Инвариант целого

Части могут быть допустимыми каждая по отдельности, а целое — нет. Например, у прямоугольной комнаты на плане ширина и длина положительные, но в квартире суммарная площадь комнат не может превышать площадь квартиры. Такой инвариант охраняет **внешний** класс, потому что только он видит все части:

```cpp
#include <print>
#include <string>
#include <utility>
#include <vector>

class Room {
public:
    Room(std::string name, double area) : name_(std::move(name)), area_(area > 0 ? area : 1) {}

    double area() const {
        return area_;
    }

private:
    std::string name_;
    double area_;
};

class Flat {
public:
    explicit Flat(double total) : total_(total) {}

    bool add(Room room) {
        if (used() + room.area() > total_) {
            return false;
        }
        rooms_.push_back(std::move(room));
        return true;
    }

    double used() const {
        double s = 0;
        for (const Room &r : rooms_) {
            s += r.area();
        }
        return s;
    }

private:
    double total_;
    std::vector<Room> rooms_;
};

int main() {
    Flat flat(50);
    bool a = flat.add(Room("кухня", 12));
    bool b = flat.add(Room("спальня", 20));
    bool c = flat.add(Room("гостиная", 25));
    std::println("{} {} {} {}", a, b, c, flat.used());
    return 0;
}
```

Вывод:

```text
true true false 32
```

<Concept title="Композиция">

Композиция — объект, состоящий из других объектов-полей. Внешний объект владеет частями: они создаются, копируются и уничтожаются вместе с ним. Каждый класс отвечает за своё, а внешний открывает клиентам операции, выполняемые частями (делегирование), не отдавая самих частей. Инвариант, связывающий части, охраняет внешний класс.

</Concept>

## Частые ошибки

<CommonMistake title="Метод, отдающий часть целиком">

`Engine &engine()` превращает внутреннюю деталь в часть интерфейса: клиенты начнут пользоваться ею напрямую, и заменить двигатель станет невозможно. Открывайте операции, а не части.

</CommonMistake>

<CommonMistake title="Внешний класс считает за часть">

`Order::total` складывает `line.price_ * line.quantity_` сам — и при появлении скидки придётся менять `Order`. Спрашивайте у части результат (`line.cost()`), а не её данные.

</CommonMistake>

<CommonMistake title="Части в «голых» указателях">

`Engine *engine_ = new Engine;` вместо поля `Engine engine_;` — лишняя куча, ручной `delete` и сломанное копирование. Если часть не нужна отдельно от целого, храните её полем.

</CommonMistake>

## Итоги

- Композиция — объект из объектов-полей; внешний объект владеет частями.
- Части создаются, копируются и уничтожаются вместе с владельцем; классы из стандартных частей копируются правильно сами.
- Каждый класс отвечает за своё; внешний спрашивает у частей результаты, а не данные.
- Делегирование открывает клиентам операции, а не части (закон Деметры).
- Инвариант, связывающий части, охраняет внешний класс.
