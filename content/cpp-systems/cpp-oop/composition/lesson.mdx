## Задача и модель

Композиция означает владение частью. Если Calibration хранится полем Sensor, она создаётся и уничтожается вместе с ним. Такой объект физически содержит подобъект, а доступ к его поведению осуществляется обычным вызовом метода. Наследование для этого не требуется: датчик имеет калибровку, но не является калибровкой.

## Как это работает в C++

Поля создаются после баз и разрушаются до баз, в обратном порядке объявления. Владение значением обычно проще динамического выделения: нет отдельного new, меньше косвенных обращений и ясна независимость копий. Если часть крупная или полиморфная, композиция может использовать unique_ptr; смысл владения сохраняется. В проекте TelemetryProcessor будет владеть фильтром и коллекцией датчиков. Пока достаточно обычного поля, чтобы отработать направление зависимостей.

## Запускаемый пример

```cpp
#include <iostream>
#include <memory>
#include <vector>

struct Scale { int factor; int apply(int x) const { return factor*x; } };
class Meter { Scale scale_{3}; public: int read(int raw) const { return scale_.apply(raw); } };
int main() { Meter m; std::cout << m.read(7) << '\n'; }
```

Ожидаемый вывод:

```text
21
```

## Разбор и эксперимент

Скопируйте Meter и измените калибровку копии через новую контролируемую операцию. Исходный Meter должен остаться независимым. Это семантика значения. Если заменить поле на разделяемый указатель, ожидаемая независимость исчезнет и потребуется другой договор с клиентом.

<CommonMistake title="Ошибка, которую нужно заметить">

Не используйте указатель лишь потому, что объект «сложный». Поле по значению уже имеет автоматическое время жизни и не требует ручного delete.

</CommonMistake>

## Практика

Реализуйте Calibration&#123;int offset&#125; с int apply(int) const, возвращающим raw+offset. Meter владеет private Calibration по значению; explicit Meter(int offset) создаёт её, read(int) const делегирует apply. solve(a,b) возвращает Meter&#123;b&#125;.read(a). Аргументы a,b — целые −1000…1000. Не добавляйте main: его создаёт система.
