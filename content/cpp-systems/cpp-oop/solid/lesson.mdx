## Пять вопросов к дизайну

**SOLID** — пять принципов объектного проектирования, которые сформулировал Роберт Мартин. Это не законы языка и не обязательный ритуал, а вопросы, которые помогают заметить, где программу будет больно менять. Два принципа вы уже применяли в уроке об интерфейсах:

| Буква | Принцип                      | Вопрос к коду                                                |
| ----- | ---------------------------- | ------------------------------------------------------------ |
| S     | единственной ответственности | сколько разных причин заставят меня менять этот класс?       |
| O     | открытости/закрытости        | можно ли добавить новый вид, не правя работающий код?        |
| L     | подстановки Лисков           | везде ли наследник работает там, где ожидают базу?           |
| I     | разделения интерфейсов       | не заставляю ли я класс реализовывать ненужные методы?       |
| D     | инверсии зависимостей        | зависит ли логика от абстракций, а не от конкретных деталей? |

## S: одна причина для изменений

Класс или функция должны отвечать за одно дело — так, чтобы их меняли по одной причине. Функция, которая читает заказы, считает статистику и печатает отчёт, придётся править и когда изменится формат ввода, и когда добавят новую метрику, и когда потребуется отчёт в CSV. Разделим её:

```cpp
#include <print>
#include <string>
#include <vector>

struct Order {
    std::string customer;
    int amount;
};

struct Stats {
    int count = 0;
    long long total = 0;
};

// Только вычисления: ничего не читает и не печатает.
Stats compute(const std::vector<Order> &orders) {
    Stats s;
    for (const Order &o : orders) {
        s.count++;
        s.total += o.amount;
    }
    return s;
}

// Только оформление.
void print_text(const Stats &s) {
    std::println("заказов {}, сумма {}", s.count, s.total);
}

void print_csv(const Stats &s) {
    std::println("count,total\n{},{}", s.count, s.total);
}

int main() {
    const std::vector<Order> orders{{"Ада", 300}, {"Алан", 120}};
    const Stats s = compute(orders);
    print_text(s);
    print_csv(s);
    return 0;
}
```

Вывод:

```text
заказов 2, сумма 420
count,total
2,420
```

`compute` можно проверить без ввода и вывода, а новый формат отчёта не трогает вычислений. «Одна ответственность» — не «один метод»: класс `std::string` умеет многое, но всё это — работа со строкой.

## O: расширять, не переписывая

Код открыт для расширения и закрыт для изменения: новый вид поведения добавляется **новым кодом**, а не правкой проверенного. Типичный признак нарушения — `switch` по виду объекта, повторённый в нескольких местах:

```cpp
// Каждая новая скидка — правка этой функции и всех похожих.
long long apply(DiscountKind kind, long long price, long long value) {
    switch (kind) {
    case DiscountKind::Percent: return price * (100 - value) / 100;
    case DiscountKind::Minus: return price > value ? price - value : 0;
    }
}
```

С интерфейсом каждая скидка — свой класс, а код, который их применяет, не меняется:

```cpp
#include <algorithm>
#include <memory>
#include <print>
#include <vector>

class Discount {
public:
    virtual ~Discount() = default;
    virtual long long apply(long long price) const = 0;
};

class Percent final : public Discount {
public:
    explicit Percent(long long p) : p_(p) {}
    long long apply(long long price) const override {
        return price * (100 - p_) / 100;
    }

private:
    long long p_;
};

class Minus final : public Discount {
public:
    explicit Minus(long long x) : x_(x) {}
    long long apply(long long price) const override {
        return std::max(0LL, price - x_);
    }

private:
    long long x_;
};

long long checkout(long long price, const std::vector<std::unique_ptr<Discount>> &discounts) {
    for (const auto &d : discounts) {
        price = d->apply(price);
    }
    return price;
}

int main() {
    std::vector<std::unique_ptr<Discount>> discounts;
    discounts.push_back(std::make_unique<Percent>(10));
    discounts.push_back(std::make_unique<Minus>(50));
    std::println("{}", checkout(1000, discounts));
    return 0;
}
```

Вывод:

```text
850
```

Новая скидка «не больше N» — ещё один класс; `checkout` остаётся прежним. Если же видов немного, набор закрыт и операций над ним много, тот же принцип выполняет `std::variant`: закрытым оказывается набор видов, а открытым — набор операций.

## L: наследник держит обещания базы

Принцип подстановки Лисков: код, написанный для базового класса, должен правильно работать с **любым** наследником. Наследник может делать больше, но не может нарушать обещания базы: требовать больше на входе, гарантировать меньше на выходе, бросать там, где база не бросает.

Знаменитый пример — квадрат, унаследованный от прямоугольника. «Квадрат — это прямоугольник» звучит верно, но изменяемый прямоугольник обещает: ширину и высоту можно задавать независимо.

```cpp
#include <print>

class Rect {
public:
    Rect(int w, int h) : w_(w), h_(h) {}
    virtual ~Rect() = default;
    virtual void set_width(int w) {
        w_ = w;
    }
    virtual void set_height(int h) {
        h_ = h;
    }
    int area() const {
        return w_ * h_;
    }

protected:
    int w_, h_;
};

class Square final : public Rect {
public:
    explicit Square(int a) : Rect(a, a) {}
    void set_width(int w) override {
        w_ = h_ = w;
    }
    void set_height(int h) override {
        w_ = h_ = h;
    }
};

void make_banner(Rect &r) {
    r.set_width(10);
    r.set_height(2);
    std::println("ожидаю 20, получил {}", r.area());
}

int main() {
    Rect r(1, 1);
    Square s(1);
    make_banner(r);
    make_banner(s);
    return 0;
}
```

Вывод:

```text
ожидаю 20, получил 20
ожидаю 20, получил 4
```

`make_banner` написана честно, по обещаниям `Rect`, но квадрат их не выполняет. Компилятор здесь не поможет: типы сходятся, нарушен **смысл**. Выход — не наследовать: квадрат как прямоугольник с равными сторонами (`Rect(a, a)`) или неизменяемые фигуры, у которых нет `set_width`. Наследование должно означать «ведёт себя как», а не «в жизни называется так же».

## I и D: коротко

- **Разделение интерфейсов.** Маленькие интерфейсы вместо одного толстого: `Readable` и `Writable` вместо `Storage` с методами-заглушками.
- **Инверсия зависимостей.** `OrderService` зависит от интерфейса `Sender`, а конкретный отправитель передаётся в конструкторе. Логику можно проверить с подставной реализацией.

Оба принципа подробно разобраны в уроке об интерфейсах.

<Warning title="Принципы — не цель">

SOLID легко превратить в лишнюю сложность: интерфейс с единственной реализацией «на будущее», фабрика фабрик, десять файлов вместо одной функции. Абстракцию вводят, когда появилась **реальная** вторая реализация, тест или ожидаемое изменение. Простой код, который легко переписать, лучше гибкого кода, который трудно понять.

</Warning>

<Concept title="SOLID">

S — у класса одна причина для изменений; вычисления, ввод и оформление разделены. O — новые виды добавляются новым кодом (наследник интерфейса, альтернатива `variant`, запись в таблице), без правки работающего. L — наследник выполняет все обещания базы, иначе наследование неверно, даже если компилируется. I — маленькие интерфейсы без методов-заглушек. D — логика зависит от абстракций, реализации передаются снаружи. Принципы — вопросы к дизайну, а не обязательные шаблоны.

</Concept>

## Частые ошибки

<CommonMistake title="Наследование по названию">

«Квадрат — это прямоугольник», «пингвин — это птица (которая летает)». Если наследник не может выполнить обещание базы, наследование неверно. Проверяйте поведение, а не названия.

</CommonMistake>

<CommonMistake title="switch по виду в нескольких местах">

Один и тот же `switch (kind)` в печати, расчёте и сохранении — каждый новый вид требует правки всех мест. Соберите поведение вида в одном классе или используйте `variant` с `visit`, где компилятор проверит полноту.

</CommonMistake>

<CommonMistake title="Абстракции на вырост">

Интерфейс ради интерфейса делает код длиннее, а не гибче. Вводите абстракцию, когда появилась вторая реализация или тест, которому она нужна.

</CommonMistake>

## Практика

1. **Отчёт по заказам** — разделение чтения, вычислений и оформления; форматы через интерфейс.
2. **Скидки из таблицы** — новые виды без правки кода применения.
3. **Найди ошибку: растянутый квадрат** — нарушение подстановки Лисков.
4. **Оплата** — способы оплаты за интерфейсом и `std::expected` для отказов.

## Итоги

- SOLID — пять вопросов к дизайну: одна ответственность, расширение без правки, подстановка наследников, маленькие интерфейсы, зависимость от абстракций.
- Разделяйте ввод, вычисления и оформление — их меняют по разным причинам.
- Повторяющийся `switch` по виду — сигнал собрать поведение в классы или в `variant`.
- Наследник обязан выполнять обещания базы; компилятор этого не проверяет.
- Абстракции вводят по реальной необходимости, а не «на будущее».
