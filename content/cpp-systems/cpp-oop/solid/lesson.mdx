## Задача и модель

SRP помогает разделить причины изменения: Sensor получает измерение, Filter решает допуск, TelemetryProcessor организует проход. OCP означает, что новый датчик добавляется реализацией контракта, без правки цикла обработки. Это полезно при ожидаемом расширении, но не требует интерфейса для каждой арифметической функции.

## Как это работает в C++

LSP требует сохранять обещания базы: если read(raw) принимает отрицательное raw, наследник не может молча запретить его. ISP удерживает интерфейс узким: читающему клиенту не нужны reset и save. DIP направляет зависимость алгоритма к Sensor, а конкретный TemperatureSensor выбирает внешний код сборки. Передача зависимости через конструктор — обычный C++ вызов, специальный контейнер зависимостей не нужен. Начинайте с реальной причины изменения и измеримого теста, а не с пяти новых уровней абстракции.

## Запускаемый пример

```cpp
#include <iostream>
#include <memory>
#include <vector>

struct Filter { virtual bool accept(int x) const = 0; virtual ~Filter() = default; };
struct Positive : Filter { bool accept(int x) const override { return x > 0; } };
int select(int x,const Filter& f) { return f.accept(x) ? x : 0; }
int main() { Positive f; std::cout << select(-3,f) << ' ' << select(4,f) << '\n'; }
```

Ожидаемый вывод:

```text
0 4
```

## Разбор и эксперимент

Замените Positive на фильтр, принимающий только отрицательные значения, и оставьте select без правок. Затем представьте, что новый Sensor отвергает разрешённое базой значение: это нарушение подстановки, даже если его сигнатуры правильны. Проверяйте семантику всех реализаций одинаковыми тестами.

## Практика

Filter задаёт virtual bool accept(int) const = 0 и виртуальный деструктор. NonNegative принимает x>=0. Функция int sum_selected(int a,int b,const Filter&amp;) проверяет каждое значение и суммирует принятые. solve(a,b) использует NonNegative; sum_selected не должна проверять конкретный тип фильтра. Аргументы a,b — целые −1000…1000. Не добавляйте main: его создаёт система.
