## Полиморфизм без базового класса

Виртуальные функции выбирают реализацию **во время работы** программы, и для этого всем видам нужна общая база. Шаблоны дают другой полиморфизм — **статический**: компилятор создаёт отдельную версию функции для каждого типа и выбирает её **при компиляции**. Общая база не нужна, достаточно, чтобы у типа были нужные операции.

```cpp
#include <print>
#include <string>

struct Cat {
    std::string text() const {
        return "кошка Мурка";
    }
};

struct Invoice {
    int number;
    std::string text() const {
        return "счёт №" + std::to_string(number);
    }
};

template <typename T>
void show(const T &item) {
    std::println("> {}", item.text());
}

int main() {
    show(Cat{});
    show(Invoice{17});
    return 0;
}
```

Вывод:

```text
> кошка Мурка
> счёт №17
```

`Cat` и `Invoice` ничего не знают друг о друге и не наследуют интерфейс. `show` работает с любым типом, у которого есть `text()`. Такой подход называют «утиной типизацией»: если умеет `text()`, значит, подходит.

Но требование «нужен `text()`» нигде не записано. Передайте неподходящий тип — и ошибка появится **внутри** шаблона, в строке, которую писал не вызывающий:

```cpp
#include <print>

template <typename T>
void show(const T &item) {
    std::println("> {}", item.text());
}

int main() {
    show(42); // Ошибка компиляции
    return 0;
}
```

Компилятор сообщит что-то вроде «у `const int` нет члена `text`» и покажет цепочку подстановок. В настоящих библиотеках такие сообщения занимают сотни строк.

## Концепт — требования к типу

**Концепт** (C++20) — именованное требование к типу, которое проверяется при компиляции. Его записывают выражением `requires`: «для объекта `x` такого типа должно компилироваться вот это».

```cpp
#include <concepts>
#include <print>
#include <string>

template <typename T>
concept Printable = requires(const T &x) {
    { x.text() } -> std::convertible_to<std::string>;
};

struct Cat {
    std::string text() const {
        return "кошка Мурка";
    }
};

void show(const Printable auto &item) {
    std::println("> {}", item.text());
}

int main() {
    show(Cat{});
    std::println("{} {}", Printable<Cat>, Printable<int>);
    return 0;
}
```

Вывод:

```text
> кошка Мурка
true false
```

Теперь `show(42)` даёт короткое сообщение в месте вызова: «ограничения не выполнены: `int` не удовлетворяет `Printable`». Концепт — это и документация, и проверка: из сигнатуры видно, что функция требует от типа. Сам `Printable<T>` — значение `bool`, вычисляемое при компиляции.

Ограничение можно записать тремя равносильными способами:

| Запись                                                                 | Когда удобна                    |
| ---------------------------------------------------------------------- | ------------------------------- |
| `void show(const Printable auto &item)`                                | короткие функции, один параметр |
| `template <Printable T> void show(const T &item)`                      | тип `T` нужен по имени в теле   |
| `template <typename T> requires Printable<T> void show(const T &item)` | сложные условия: `A<T> && B<T>` |

## Стандартные концепты

Заголовок `<concepts>` содержит готовые концепты: `std::integral`, `std::floating_point`, `std::same_as<T, U>`, `std::convertible_to<From, To>`, `std::totally_ordered` (есть `<`, `>`, `==`…), `std::invocable<F, Args...>`. Диапазоны описаны концептами `std::ranges::range`, `std::ranges::sized_range` и другими из `<ranges>`.

Функции можно **перегружать по концептам** — выбирается версия, чьё ограничение выполнено:

```cpp
#include <concepts>
#include <print>

void describe(std::integral auto x) {
    std::println("целое {}", x);
}

void describe(std::floating_point auto x) {
    std::println("дробное {:.2f}", x);
}

template <std::totally_ordered T>
const T &clamp_to(const T &value, const T &low, const T &high) {
    return value < low ? low : (high < value ? high : value);
}

int main() {
    describe(7);
    describe(2.5);
    describe(true);
    std::println("{}", clamp_to(15, 0, 10));
    return 0;
}
```

Вывод:

```text
целое 7
дробное 2.50
целое true
10
```

Обратите внимание на третью строку: `bool` в C++ — **целый** тип, и `std::integral<bool>` истинно. То же относится к `char`. Если `bool` нужно обрабатывать иначе, это приходится проверять явно.

## if constexpr и requires внутри функции

Внутри шаблона можно ветвиться по свойствам типа. `if constexpr` вычисляет условие при компиляции, и **отброшенная ветка не компилируется** для этого типа — поэтому в ней можно вызывать то, чего у типа нет:

```cpp
#include <concepts>
#include <print>
#include <string>

struct Cat {
    std::string text() const {
        return "кошка Мурка";
    }
};

template <typename T>
std::string to_text(const T &value) {
    if constexpr (std::integral<T>) {
        return std::to_string(value);
    } else if constexpr (requires(const T &v) { v.text(); }) {
        return value.text();
    } else {
        return "?";
    }
}

int main() {
    std::println("{} | {} | {}", to_text(5), to_text(Cat{}), to_text(2.5));
    return 0;
}
```

Вывод:

```text
5 | кошка Мурка | ?
```

Выражение `requires(const T &v) { v.text(); }` прямо в условии проверяет «есть ли у значений типа `T` метод `text()`». Ветки проверяются по порядку — первая подходящая выигрывает.

## Статический или динамический полиморфизм

|                       | Шаблоны и концепты                           | Виртуальные функции                         |
| --------------------- | -------------------------------------------- | ------------------------------------------- |
| Выбор реализации      | при компиляции                               | во время работы                             |
| Общая база            | не нужна                                     | нужна                                       |
| Разнотипный контейнер | напрямую нельзя: `variant` или стирание типа | `std::vector<std::unique_ptr<База>>`        |
| Скорость вызова       | прямой вызов, возможна подстановка тела      | косвенный вызов через таблицу               |
| Размер программы      | своя копия функции для каждого типа          | одна функция                                |
| Код                   | обычно целиком в заголовке                   | реализацию можно скрыть, подключать плагины |

Статический полиморфизм выбирают для алгоритмов и библиотек, где тип известен в месте вызова: `std::ranges::sort` работает с любым подходящим диапазоном без единой виртуальной функции. Динамический — когда набор объектов собирается во время работы: датчики из файла конфигурации, фигуры, нарисованные пользователем.

## Стирание типа

Иногда нужно и то и другое: хранить в одном векторе объекты **несвязанных** типов, но не заставлять их наследовать общий интерфейс. Приём называется **стиранием типа** (type erasure): внутренний интерфейс с виртуальными функциями и шаблонная обёртка, которая подходит любому типу с нужными операциями. Самый известный пример в стандартной библиотеке — `std::function`:

```cpp
#include <functional>
#include <print>
#include <vector>

int twice(int x) {
    return 2 * x;
}

struct AddN {
    int n;
    int operator()(int x) const {
        return x + n;
    }
};

int main() {
    const std::vector<std::function<int(int)>> steps{twice, AddN{3}, [](int x) { return x * x; }};
    int value = 2;
    for (const auto &step : steps) {
        value = step(value);
    }
    std::println("{}", value);
    return 0;
}
```

Вывод:

```text
49
```

Обычная функция, объект с `operator()` и лямбда — три разных типа без общей базы, а вектор один. В C++23 добавлен `std::move_only_function` — вариант для некопируемых объектов, в C++26 — лёгкая невладеющая ссылка `std::function_ref`. В последней задаче урока вы напишете собственную обёртку со стиранием типа.

<Concept title="Шаблоны и концепты">

Шаблон с ограничениями — статический полиморфизм: реализация выбирается при компиляции, общая база не нужна. Концепт (`template <typename T> concept C = requires(...) {...};`) — именованное требование к типу; нарушение даёт короткую ошибку в месте вызова. Ограничение пишут как `template <C T>`, `requires C<T>` или `C auto`. Стандартные концепты — в `<concepts>`; по концептам можно перегружать функции; `if constexpr` отбрасывает ветки для неподходящих типов. Разнотипные коллекции требуют `variant`, иерархии или стирания типа.

</Concept>

## Частые ошибки

<CommonMistake title="Забытый bool и char">

`std::integral` истинно для `bool` и `char`. Если они требуют отдельной обработки, проверьте `std::same_as<T, bool>` раньше общего случая.

</CommonMistake>

<CommonMistake title="Шаблон вместо иерархии для коллекции">

`std::vector<Printable>` невозможен: концепт — не тип, а требование. Для разнотипной коллекции нужен `variant`, общий интерфейс или стирание типа.

</CommonMistake>

<CommonMistake title="Слишком слабый концепт">

Концепт, который требует только `text()`, пропустит любой тип с методом `text()`, даже если тот возвращает число. Указывайте и тип результата: `{ x.text() } -> std::convertible_to<std::string>`.

</CommonMistake>

## Практика

1. **Фигуры по концепту** — концепт с двумя требованиями и функция, ограниченная им.
2. **Одна функция для чисел и слов** — `std::totally_ordered` и свой концепт сложения.
3. **Найди ошибку: bool тоже целый** — порядок веток `if constexpr`.
4. **Стирание типа** — своя обёртка `AnyPrintable` для несвязанных типов.

## Итоги

- Шаблоны дают статический полиморфизм: реализация выбирается при компиляции, общая база не нужна.
- Концепт описывает требования к типу и превращает ошибки в шаблонах в понятные сообщения в месте вызова.
- `<concepts>` содержит готовые требования; по концептам можно перегружать функции.
- `bool` и `char` — целые типы для `std::integral`.
- Статический полиморфизм быстрее и проверяется при компиляции, динамический позволяет собирать объекты во время работы; стирание типа совмещает оба подхода.
