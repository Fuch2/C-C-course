## Договор без реализации

**Интерфейс** в C++ — это класс, в котором нет ничего, кроме открытых чисто виртуальных функций и виртуального деструктора. Ни полей, ни реализаций, ни конструкторов с параметрами: только обещание «умею вот это». В языке нет отдельного слова `interface`, как в Java или C#, — интерфейсом класс делает его устройство.

```cpp
#include <format>
#include <print>
#include <string>

class Printable {
public:
    virtual ~Printable() = default;
    virtual std::string text() const = 0;
};

class Temperature final : public Printable {
public:
    explicit Temperature(double c) : c_(c) {}
    std::string text() const override {
        return std::format("{:.1f} °C", c_);
    }

private:
    double c_;
};

class Greeting final : public Printable {
public:
    std::string text() const override {
        return "Привет!";
    }
};

void show(const Printable &p) {
    std::println("> {}", p.text());
}

int main() {
    show(Temperature(21.5));
    show(Greeting());
    return 0;
}
```

Вывод:

```text
> 21.5 °C
> Привет!
```

`Temperature` и `Greeting` ничем не похожи — у них нет общих данных и общего смысла, кроме одного: оба умеют превратиться в текст. Интерфейс описывает именно такую **способность**, а не родство. Функции `show` больше ничего и не нужно.

## Несколько интерфейсов сразу

Класс может реализовать несколько интерфейсов — это множественное наследование, но безопасное: у интерфейсов нет данных, и конфликтовать нечему.

```cpp
#include <print>
#include <string>
#include <utility>
#include <vector>

class Printable {
public:
    virtual ~Printable() = default;
    virtual std::string text() const = 0;
};

class Priced {
public:
    virtual ~Priced() = default;
    virtual long long price() const = 0;
};

class Book final : public Printable, public Priced {
public:
    Book(std::string title, long long price) : title_(std::move(title)), price_(price) {}

    std::string text() const override {
        return "книга «" + title_ + "»";
    }

    long long price() const override {
        return price_;
    }

private:
    std::string title_;
    long long price_;
};

class Delivery final : public Priced {
public:
    long long price() const override {
        return 300;
    }
};

long long total(const std::vector<const Priced *> &items) {
    long long sum = 0;
    for (const Priced *p : items) {
        sum += p->price();
    }
    return sum;
}

int main() {
    Book book("Дюна", 900);
    Delivery delivery;
    std::println("{}", book.text());
    std::println("итого {}", total({&book, &delivery}));
    return 0;
}
```

Вывод:

```text
книга «Дюна»
итого 1200
```

Функции `total` нужна только цена; она принимает `Priced` и ничего не знает о книгах. Доставку можно оплатить, но печатать её не нужно — она реализует один интерфейс, а не оба.

## Маленькие интерфейсы

Интерфейс с десятью методами «на все случаи» заставляет каждый класс реализовать все десять — даже те, что ему не подходят. Тогда появляются методы-заглушки, которые бросают исключение «не поддерживается», и программа падает во время работы там, где могла бы не скомпилироваться. Это **принцип разделения интерфейсов** (буква I в SOLID): много маленьких интерфейсов лучше одного большого. Клиент зависит только от того, чем пользуется.

| Толстый интерфейс                            | Разделённые интерфейсы                           |
| -------------------------------------------- | ------------------------------------------------ |
| `Storage`: `read`, `write`, `remove`, `size` | `Readable`: `read`; `Writable`: `write`, …       |
| файл только для чтения бросает в `write`     | файл только для чтения реализует лишь `Readable` |
| ошибка — во время работы                     | ошибка — при компиляции                          |

## Зависеть от абстракции

Самое важное применение интерфейсов — **развязать** части программы. Класс, который отправляет уведомления, не должен знать, как именно они уходят — по почте, в мессенджер или в журнал:

```cpp
#include <print>
#include <string>

class Sender {
public:
    virtual ~Sender() = default;
    virtual void send(const std::string &to, const std::string &text) = 0;
};

class ConsoleSender final : public Sender {
public:
    void send(const std::string &to, const std::string &text) override {
        std::println("для {}: {}", to, text);
    }
};

class CountingSender final : public Sender {
public:
    void send(const std::string &, const std::string &) override {
        count_++;
    }

    int count() const {
        return count_;
    }

private:
    int count_ = 0;
};

class OrderService {
public:
    explicit OrderService(Sender &sender) : sender_(sender) {}

    void place(const std::string &customer, int amount) {
        if (amount > 0) {
            sender_.send(customer, "заказ на " + std::to_string(amount) + " принят");
        }
    }

private:
    Sender &sender_;
};

int main() {
    ConsoleSender console;
    OrderService shop(console);
    shop.place("Ада", 1500);

    CountingSender counter;
    OrderService test(counter);
    test.place("a", 1);
    test.place("b", 0);
    test.place("c", 5);
    std::println("отправлено в тесте: {}", counter.count());
    return 0;
}
```

Вывод:

```text
для Ада: заказ на 1500 принят
отправлено в тесте: 2
```

`OrderService` — логика магазина — зависит от интерфейса `Sender`, а не от конкретной отправки. В программе ему дают настоящий отправитель, в тесте — «подставной» `CountingSender`, который только считает вызовы. Это **принцип инверсии зависимостей** (буква D в SOLID): код верхнего уровня и детали зависят от абстракции, а не детали диктуют устройство логики. Вместе с внедрением зависимости через конструктор (урок об агрегации) это основной способ писать тестируемый код.

<Concept title="Интерфейсы">

Интерфейс — класс только из открытых чисто виртуальных функций и виртуального деструктора: договор о способности без данных и реализаций. Класс может реализовать несколько интерфейсов. Интерфейсы делают маленькими (принцип разделения интерфейсов), чтобы классы не реализовывали ненужные методы-заглушки. Код зависит от интерфейсов, а не от конкретных классов (принцип инверсии зависимостей); реализацию передают в конструкторе и подменяют, например, в тестах.

</Concept>

## Частые ошибки

<CommonMistake title="Интерфейс без виртуального деструктора">

Объекты часто удаляют через `std::unique_ptr<Интерфейс>`. Без `virtual ~Интерфейс() = default;` это неопределённое поведение.

</CommonMistake>

<CommonMistake title="Метод-заглушка «не поддерживается»">

Класс реализует интерфейс частично и бросает исключение из лишних методов. Разделите интерфейс: пусть класс реализует только то, что умеет.

</CommonMistake>

<CommonMistake title="Данные в интерфейсе">

Поле в «интерфейсе» превращает его в абстрактный класс и навязывает данные всем реализациям, а при множественном наследовании может появиться в объекте дважды. Интерфейсы держите пустыми.

</CommonMistake>

## Итоги

- Интерфейс — только открытые чисто виртуальные функции и виртуальный деструктор; он описывает способность, а не родство.
- Класс может реализовать несколько интерфейсов — у них нет данных, и конфликтовать нечему.
- Маленькие интерфейсы лучше толстых: класс реализует только то, что умеет (принцип разделения интерфейсов).
- Логика зависит от интерфейсов, конкретные реализации передаются снаружи и подменяются в тестах (принцип инверсии зависимостей).
