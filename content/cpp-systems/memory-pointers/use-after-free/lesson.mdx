## Самая опасная ошибка памяти

**Use-after-free** (использование после освобождения) — чтение или запись через указатель на блок, который уже отдан `free`. Это частный случай висячего указателя, но настолько важный, что заслуживает отдельного урока: в отчётах о безопасности браузеров и операционных систем use-after-free годами входит в число самых частых причин уязвимостей.

Почему он так опасен:

- после `free` распределитель памяти может **отдать тот же блок** следующему `malloc`. Тогда старый указатель смотрит на чужой объект, и запись через него портит чужие данные;
- если злоумышленник управляет тем, что окажется в переиспользованном блоке, он может подменить, например, адрес функции и захватить управление программой;
- без инструментов ошибка проявляется далеко от места, где она совершена, и не всегда.

## Как это выглядит

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

struct Session {
    char user[16];
    int requests;
};

struct Session *session_open(const char *user) {
    struct Session *s = malloc(sizeof *s);
    if (s != NULL) {
        snprintf(s->user, sizeof s->user, "%s", user);
        s->requests = 0;
    }
    return s;
}

void session_close(struct Session *s) {
    printf("закрыта сессия %s\n", s->user);
    free(s);
}

int main(void) {
    struct Session *s = session_open("anna");
    if (s == NULL) {
        return 1;
    }
    s->requests += 3;
    session_close(s);
    printf("запросов: %d\n", s->requests);   // Ошибка памяти: s уже освобождена
    return 0;
}
```

Без санитайзера программа, скорее всего, напечатает «запросов: 3» — освобождённый блок ещё не переиспользован. Ошибку легко не заметить: она «работает». AddressSanitizer останавливает программу на первом же обращении.

Ниже в полном отчёте идут «Shadow bytes» — карта служебной памяти санитайзера. Значение `fd` означает «освобождённая область кучи», `fa` — защитная зона вокруг блока. Читать её обычно не нужно: главное уже сказано в первых строках.

<UnderTheHood title="Как санитайзер узнаёт об освобождении">

AddressSanitizer заменяет `malloc` и `free` своими версиями. Для каждых 8 байтов памяти программы он хранит 1 байт **теневой памяти** с состоянием: доступно, недоступно, освобождено. Компилятор перед каждым чтением и записью вставляет проверку теневого байта. Освобождённые блоки не возвращаются в оборот сразу, а попадают в **карантин** — поэтому обращение к ним надёжно обнаруживается, даже если программа успела сделать новые выделения.

</UnderTheHood>

## Где прячется use-after-free

**1. Порядок операций.** Использование после освобождения в одной функции: сначала `free`, потом последний `printf` с данными. Исправление — переставить строки: освобождение должно быть **последним** обращением к блоку.

**2. Функция освобождает переданный объект.** Как `session_close` выше. Вызывающий код должен знать, что после вызова объект мёртв. Хорошее имя (`close`, `destroy`, `release`) — главный сигнал.

**3. Освобождение в цикле.** Классика со связанными структурами:

```c
for (struct Node *n = head; n != NULL; n = n->next) {
    free(n);                 // шаг n = n->next прочитает освобождённый узел
}
```

**4. Две ссылки на один объект.** Объект зарегистрирован в двух местах (например, в списке и в словаре). Одно место его удалило, другое продолжает пользоваться.

**5. Указатели на элементы растущего массива.** После `realloc` старый блок освобождён — это тоже use-after-free, как вы видели в уроке о `realloc`.

## Как исправлять

Не «добавить проверку на `NULL`» и не «убрать `free`». Правильное исправление отвечает на вопрос **кто владеет объектом и когда его время жизни заканчивается**:

- если объект ещё нужен после вызова — освобождение переносится туда, где он действительно больше не нужен;
- если нужны лишь данные — копируйте их до освобождения (`int total = s->requests; session_close(s); printf(…, total);`);
- если ссылок несколько — назначьте одного владельца, остальные должны узнавать об удалении (или хранить дескрипторы с поколением);
- после `free` обнуляйте указатель, если переменная продолжает жить.

<Concept title="free — последнее, что происходит с объектом">

Между `malloc` и `free` объект живёт. После `free` его нет — даже если байты на месте и программа «работает». Проверяя код, найдите `free` и убедитесь, что после него к объекту не обращается ни одна строка — ни в этой функции, ни в вызывающих.

</Concept>

## Частые ошибки

<CommonMistake title="Исправление удалением free">

Если убрать `free`, санитайзер замолчит, но появится утечка. Use-after-free исправляют перемещением освобождения или копированием нужных данных, а не отказом от освобождения.

</CommonMistake>

<CommonMistake title="Проверка указателя на NULL после free">

`free(p); if (p != NULL) use(p);` — `free` не обнуляет указатель, проверка всегда истинна. Обнулять нужно явно, и только эта переменная станет безопасной.

</CommonMistake>

<CommonMistake title="«У меня всё работает»">

Use-after-free без санитайзера часто даёт правильный результат — до тех пор, пока блок не займёт новый объект. Проверяйте программы с AddressSanitizer или Valgrind, особенно код, который освобождает память.

</CommonMistake>

## Практика

1. **Найди ошибку: итог после закрытия** — данные читаются после функции, которая освобождает объект.
2. **Найди ошибку: удаление в цикле** — освобождение узлов списка, удовлетворяющих условию.
3. **Найди ошибку: два владельца** — объект удаляется из реестра, но остаётся в очереди.
4. **Удаление из списка по значению** — корректная версия без обращений к освобождённым узлам.

## Итоги

- Use-after-free — обращение к блоку после `free`; без инструментов часто «работает», но может портить чужие данные и приводить к уязвимостям.
- Отчёт ASan содержит три стека: где произошло обращение, где блок освобождён и где выделен, — а также смещение внутри блока.
- Типичные места: неверный порядок операций, функции-«закрыватели», освобождение в цикле, несколько ссылок на объект, `realloc`.
- Исправление — изменить время жизни или скопировать данные до освобождения, а не убрать `free`.
