## Что значит «поведение не определено»

Во всех уроках модуля повторялась фраза «неопределённое поведение». Пора разобраться, что за ней стоит. Стандарт C делит поведение программ на несколько категорий:

| Категория                          | Что обещает стандарт                              | Пример                                     |
| ---------------------------------- | ------------------------------------------------- | ------------------------------------------ |
| определённое                       | результат однозначен                              | `2 + 3`                                    |
| определяемое реализацией           | результат выбирает компилятор и **документирует** | `sizeof(int)`, сдвиг вправо отрицательного |
| неуточнённое (unspecified)         | один из нескольких вариантов, без документации    | порядок вычисления аргументов функции      |
| **неопределённое (undefined, UB)** | **никаких требований** к программе                | выход за массив, переполнение `int`        |

«Никаких требований» — буквально. Программа с UB может выдать правильный ответ, неправильный ответ, упасть, зависнуть — и вести себя по-разному при каждой компиляции. Стандарт не обязывает компилятор предупреждать об UB или как-то его обрабатывать.

## Почему UB существует

C создавался для разных процессоров, и стандарт не хотел навязывать проверки, которые на каком-то из них дороги. Проверять каждый индекс, каждое сложение на переполнение, каждый указатель на `NULL` — значит замедлить любую программу. Поэтому язык перекладывает обязанность на программиста: «если вы не нарушаете правил, код будет быстрым».

Есть и вторая сторона: **оптимизатор считает, что UB не происходит**, и строит на этом выводы. Если в коде есть `a[i]`, компилятор вправе считать, что `i` в границах массива; если есть `x + 1` для `int`, — что переполнения нет. Поэтому ошибка с UB иногда «исправляется» при отладке и снова появляется в оптимизированной сборке, а проверка, написанная после UB, может быть выброшена из кода целиком.

## Переполнение знаковых целых

Переполнение `int` (и других знаковых типов) — UB, в отличие от беззнаковых, где результат определён как остаток по модулю 2ⁿ:

```c
#include <stdio.h>

int main(void) {
    int views = 2000000000;
    int extra = 500000000;
    int total = views + extra;            // Ошибка памяти: переполнение int
    printf("%d\n", total);
    return 0;
}
```

Без инструментов на проверочной машине программа печатает `-1794967296` — процессор «заворачивает» результат. Но рассчитывать на это нельзя. UndefinedBehaviorSanitizer останавливает программу с точным описанием:

```text
main.c:6:23: runtime error: signed integer overflow: 2000000000 + 500000000 cannot be represented in type 'int'
```

Исправления: взять тип пошире (`long long`), проверить возможность переполнения **до** операции или использовать беззнаковый тип, если «заворачивание» — желаемое поведение (например, в хешах).

Проверка до операции выглядит так:

```c
#include <limits.h>
#include <stdio.h>

// Складывает a и b в *out. Возвращает -1, если сумма не помещается в int.
int add_checked(int a, int b, int *out) {
    if ((b > 0 && a > INT_MAX - b) || (b < 0 && a < INT_MIN - b)) {
        return -1;
    }
    *out = a + b;
    return 0;
}

int main(void) {
    int result = 0;
    printf("%d\n", add_checked(2000000000, 500000000, &result));
    int status = add_checked(-5, 7, &result);
    printf("%d %d\n", status, result);
    return 0;
}
```

Вывод:

```text
-1
0 2
```

Проверка `a + b > INT_MAX` бессмысленна: если сумма переполнилась, UB уже произошло, а компилятор вправе считать условие всегда ложным. Сравнивать нужно так, чтобы само сравнение не переполнялось: `a > INT_MAX - b`.

## Сдвиги

Сдвиг на число битов, не меньшее ширины типа, или на отрицательное число — UB. Сдвиг влево отрицательного числа или сдвиг, при котором единица уходит в знаковый бит, — тоже:

```c
#include <stdio.h>

int main(void) {
    int bits = 32;
    unsigned mask = 1u << bits;          // Ошибка памяти: сдвиг на ширину типа
    printf("%u\n", mask);
    return 0;
}
```

Многие ожидают `0`, но процессор x86 берёт от величины сдвига только младшие 5 битов, и программа печатает `1`. UBSan сообщает `shift exponent 32 is too large for 32-bit type 'unsigned int'`. Если нужна маска «все биты до n», пишите проверку: `n >= 32 ? 0xFFFFFFFFu : (1u << n) - 1`.

## Деление

Деление на ноль — UB для целых чисел. Менее известный случай: `INT_MIN / -1`. Результат, `2 147 483 648`, не помещается в `int`, и процессор x86 аварийно завершает программу так же, как при делении на ноль. Остаток `INT_MIN % -1` — тоже UB.

## Неинициализированные значения

Чтение неинициализированной локальной переменной или байтов из `malloc` не даёт «случайного числа» — это UB (для большинства типов). Компилятор может, например, считать, что `if (x)` и `if (!x)` для неинициализированного `x` оба ложны. Санитайзеры AddressSanitizer и UBSan этого не ловят; поможет Valgrind (урок «Valgrind») и предупреждения компилятора `-Wall -Wextra`.

## Карта UB, изученного в модуле

| Ошибка                                     | Где разбиралась       | Кто находит                                     |
| ------------------------------------------ | --------------------- | ----------------------------------------------- |
| выход за границы массива                   | «Выход за границы»    | ASan, UBSan (для массивов с известным размером) |
| use-after-free, double free                | уроки 18–19           | ASan, Valgrind                                  |
| переполнение буфера строкой                | «Переполнение буфера» | ASan, Valgrind                                  |
| висячий указатель на стек                  | «Время жизни»         | ASan                                            |
| разыменование `NULL`                       | «Основы C»            | UBSan, аварийное завершение                     |
| переполнение `int`, сдвиги, `INT_MIN / -1` | этот урок             | UBSan                                           |
| неинициализированное значение              | этот урок, «malloc»   | Valgrind, предупреждения                        |
| запись в строковый литерал                 | «Карта памяти»        | аварийное завершение                            |
| нарушение выравнивания                     | следующий урок        | UBSan                                           |
| перекрытие в `memcpy`                      | «memcpy, memmove»     | ASan                                            |

<Concept title="UB — это договор, а не случайность">

Неопределённое поведение — не «редкий сбой», а нарушение договора между программистом и компилятором. Компилятор обещает быструю программу, вы обещаете не нарушать правил. Нарушили — компилятор свободен от обязательств, и «работает у меня» ничего не доказывает. Защищают от UB три вещи: знание правил, предупреждения компилятора и запуск тестов с санитайзерами.

</Concept>

## Частые ошибки

<CommonMistake title="Проверка переполнения после операции">

`int s = a + b; if (s < a) …` — переполнение уже произошло, а компилятор может удалить проверку как «невозможную». Проверяйте до операции или вычисляйте в более широком типе.

</CommonMistake>

<CommonMistake title="«На моём компьютере работает»">

UB может давать ожидаемый результат при `-O0` и другой при `-O2`, на GCC и на Clang, на x86 и на ARM. Правильность программы доказывается правилами языка, а не одним запуском.

</CommonMistake>

<CommonMistake title="Произведение int в выражении с long long">

`long long area = width * height;` для `int width, height` перемножает в `int` и переполняется **до** присваивания. Приведите один множитель: `(long long)width * height`.

</CommonMistake>

## Практика

1. **Найди ошибку: сумма продаж** — переполнение `int` при накоплении.
2. **Безопасное сложение** — проверка переполнения до операции.
3. **Найди ошибку: битовая маска** — сдвиг на ширину типа.
4. **Найди ошибку: площадь участков** — произведение двух `int` до приведения.

## Итоги

- Неопределённое поведение означает отсутствие любых требований к программе; результат может меняться от сборки к сборке.
- UB существует ради скорости: язык не проверяет операции, а оптимизатор предполагает, что UB не происходит.
- Переполнение знаковых целых, сдвиг на ширину типа и больше, деление на ноль и `INT_MIN / -1` — UB; UBSan находит их во время выполнения.
- Проверку переполнения делают до операции (`a > INT_MAX - b`) или вычисляют в более широком типе.
- Неинициализированные значения не ловят ASan и UBSan — их находят Valgrind и предупреждения компилятора.
