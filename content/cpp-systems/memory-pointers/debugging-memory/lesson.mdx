## Итоговый практикум модуля

За 27 уроков вы разобрали, как программа размещает данные, как работают указатели и куча, какие ошибки памяти бывают и как их находить инструментами. Этот урок собирает всё вместе в **метод**: как действовать, когда программа ведёт себя странно, и как писать код, в котором ошибки памяти маловероятны.

## Симптомы и вероятные причины

Ошибка памяти редко сообщает о себе прямо. Обычно вы видите симптом:

| Симптом                                                   | Вероятные причины                                                                  |
| --------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| `Segmentation fault` сразу                                | разыменование `NULL` или мусорного указателя, переполнение стека, запись в литерал |
| `free(): double free detected`, `free(): invalid pointer` | двойное освобождение, `free` середины блока или не-кучи                            |
| результат «плавает» от запуска к запуску                  | неинициализированные значения, чтение за границей                                  |
| программа работает, пока не добавили `printf`             | порча памяти: выход за границу или use-after-free                                  |
| правильно в отладке, неправильно с `-O2`                  | неопределённое поведение (переполнение, выравнивание, aliasing)                    |
| память процесса растёт со временем                        | утечка в повторяющемся коде                                                        |
| у разных объектов одинаковые данные                       | указатель на общий буфер вместо копии                                              |

## Метод: семь шагов

**1. Воспроизвести.** Найдите вход, на котором ошибка проявляется всегда. Уменьшайте его: убирайте половину данных и проверяйте, осталась ли ошибка. Маленький пример экономит часы.

**2. Запустить с инструментом.** Сначала AddressSanitizer и UBSan — они быстрые и точные. Если санитайзеры молчат, а поведение по-прежнему странное, — Valgrind: он находит неинициализированные значения.

**3. Прочитать первый отчёт.** Четыре вопроса: что случилось, какая операция, где в коде, какой объект и какова его история (выделение, освобождение). Остальные отчёты пока игнорируйте — они могут быть следствием первого.

**4. Найти причину, а не место.** Строка отчёта — место, где ошибка **проявилась**. Причина обычно раньше: неверно вычисленный размер, забытый `+ 1`, лишний `free` в другой функции, указатель, сохранённый дольше жизни объекта. Спросите: кто владеет этим объектом? Сколько он должен жить? Какие индексы допустимы?

**5. Исправить причину.** Не «заглушайте» симптом: удаление `free` убирает use-after-free, но создаёт утечку; лишний байт в `malloc` «на всякий случай» прячет неверную формулу. Исправление должно делать код **правильным**, а не тихим.

**6. Добавить тест.** Вход, на котором ошибка проявлялась, становится тестом. Тогда она не вернётся незамеченной.

**7. Перезапустить всё.** Исправив одну ошибку, снова запустите программу с инструментами на всех тестах: вторая ошибка могла прятаться за первой.

## Вспомогательные приёмы

**Проверки инвариантов.** Макрос `assert` из `<assert.h>` останавливает программу, если условие ложно, и печатает его текст и строку. Он превращает «где-то испортилось» в «испортилось здесь»:

```c
#include <assert.h>
#include <stdio.h>

struct IntVec {
    int *data;
    size_t length;
    size_t capacity;
};

int vec_get(const struct IntVec *v, size_t i) {
    assert(v->length <= v->capacity);          // инвариант вектора
    assert(i < v->length);                      // предусловие функции
    return v->data[i];
}

int main(void) {
    int storage[4] = {10, 20, 30, 0};
    struct IntVec v = {storage, 3, 4};
    printf("%d\n", vec_get(&v, 2));
    return 0;
}
```

Вывод:

```text
30
```

Вызов `vec_get(&v, 3)` завершил бы программу сообщением `Assertion 'i < v->length' failed`. Проверки `assert` отключаются при сборке с `-DNDEBUG`, поэтому в них нельзя писать код с побочными эффектами.

**Отладочный вывод в stderr.** `fprintf(stderr, …)` не смешивается с основным выводом программы и не буферизуется — сообщение появится, даже если программа сразу после этого упадёт.

**Отладчик.** GDB или LLDB показывают стек вызовов в момент падения (`bt`) и значения переменных. Работе с отладчиками посвящены уроки модуля «Инструменты разработчика».

## Код, в котором ошибкам трудно появиться

Лучшая отладка — та, которая не понадобилась. Правила, которые вы изучили в модуле, складываются в короткий список:

- **Инициализируйте при объявлении.** `int count = 0;`, `char *name = NULL;`, `struct T t = {0};`, `calloc` для счётчиков.
- **Размер считайте от переменной:** `malloc(n * sizeof *p)`, `snprintf(buf, sizeof buf, …)`; проверяйте `n * size` на переполнение.
- **Передавайте размер вместе с буфером** — в каждую функцию, которая пишет в массив.
- **Один владелец у каждого блока.** Пары `create`/`destroy`, глубокое копирование, явная передача владения; `const` у заимствованных указателей.
- **Индексы вместо долгоживущих указателей** на элементы растущих контейнеров.
- **После `free` — `NULL`** для переменных, которые продолжают жить.
- **Проверяйте каждый внешний индекс** с обеих сторон.
- **Сборка с предупреждениями** `-Wall -Wextra` и **тесты с санитайзерами**, включая ветки ошибок.

<Concept title="Ошибка памяти — нарушенный договор">

Каждая ошибка модуля — нарушение одного из трёх договоров: **время жизни** (обращение к объекту, который не существует), **границы** (обращение вне объекта), **владение** (освобождение не тем, не тогда или не один раз). Отладка — это поиск, какой договор и где нарушен; хороший код — это код, в котором договоры видны.

</Concept>

## Практика

Задачи практикума собраны из ошибок разных уроков. В некоторых программах больше одной ошибки — действуйте по методу: первый отчёт, причина, исправление, повторный запуск.

1. **Найди ошибку: телефонная книга** — две ошибки в работе со строками и владением.
2. **Найди ошибку: кольцевой буфер** — индекс, вышедший за ёмкость.
3. **Найди ошибку: разбор CSV** — поля, указывающие в переиспользуемый буфер.
4. **Мини-словарь** — хранилище строковых ключей без единой ошибки памяти.

## Итоги

- Ошибки памяти проявляются симптомами: падения, «плавающие» результаты, сообщения `free()`, рост памяти; таблица симптомов подсказывает, что искать.
- Метод: воспроизвести на минимальном входе, запустить с ASan/UBSan (затем Valgrind), прочитать первый отчёт, найти причину, исправить причину, добавить тест, перезапустить всё.
- `assert` превращает нарушенный инвариант в немедленную понятную остановку; отладочный вывод — в `stderr`.
- Код без ошибок памяти строится на инициализации при объявлении, размерах от переменных, едином владельце, индексах вместо указателей и тестах с санитайзерами.
- Каждая ошибка — нарушение договора о времени жизни, границах или владении.
