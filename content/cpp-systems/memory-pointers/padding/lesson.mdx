## Откуда в структуре лишние байты

В уроке о байтах вы видели, что `struct { char tag; int value; }` занимает 8 байтов, хотя поля вместе — 5. Теперь, зная о выравнивании, можно объяснить, откуда берутся три лишних байта, и научиться управлять размером структур.

Компилятор раскладывает поля по трём правилам:

1. Поля идут **в порядке объявления** — менять порядок компилятор не имеет права.
2. Каждое поле размещается по смещению, кратному **его** выравниванию; если нужно, перед полем вставляются байты-заполнители (**padding**).
3. Выравнивание всей структуры равно наибольшему выравниванию её полей, а размер структуры округляется **вверх** до кратного этому выравниванию — чтобы в массиве структур каждый элемент тоже был выровнен (это **хвостовой** padding).

## Смотрим на раскладку: `offsetof`

Макрос `offsetof(тип, поле)` из `<stddef.h>` возвращает смещение поля от начала структуры:

```c
#include <stddef.h>
#include <stdio.h>

struct Sample {
    char kind;       // 1 байт
    double value;    // 8 байтов, выравнивание 8
    short code;      // 2 байта, выравнивание 2
};

int main(void) {
    printf("kind   %zu\n", offsetof(struct Sample, kind));
    printf("value  %zu\n", offsetof(struct Sample, value));
    printf("code   %zu\n", offsetof(struct Sample, code));
    printf("size   %zu\n", sizeof(struct Sample));
    return 0;
}
```

Вывод:

```text
kind   0
value  8
code   16
size   24
```

<MemoryDiagram title="struct Sample: 11 байтов данных в 24 байтах">

| Байты   | 0      | 1–7         | 8–15    | 16–17  | 18–23     |
| ------- | ------ | ----------- | ------- | ------ | --------- |
| Поле    | `kind` | заполнитель | `value` | `code` | хвост     |
| Правило | —      | правило 2   | —       | —      | правило 3 |

</MemoryDiagram>

- `kind` — по смещению 0.
- `value` требует смещения, кратного 8. Ближайшее после байта 0 — 8, поэтому байты 1–7 — заполнитель.
- `code` требует кратного 2: смещение 16 подходит.
- Данные кончаются на байте 17, но выравнивание структуры — 8 (по `double`), поэтому размер округляется до 24. Без хвоста второй элемент массива `struct Sample arr[2]` начинался бы с 18 — и его `value` оказалось бы невыровненным.

## Порядок полей меняет размер

Те же три поля в другом порядке:

```c
#include <stddef.h>
#include <stdio.h>

struct Loose {
    char kind;
    double value;
    short code;
};

struct Tight {
    double value;    // сначала поля с самым строгим выравниванием
    short code;
    char kind;
};

int main(void) {
    printf("%zu %zu\n", sizeof(struct Loose), sizeof(struct Tight));
    printf("%zu %zu\n", 1000 * sizeof(struct Loose), 1000 * sizeof(struct Tight));
    return 0;
}
```

Вывод:

```text
24 16
24000 16000
```

Простое правило: **упорядочивайте поля по убыванию выравнивания**. Тогда каждое следующее поле уже выровнено, и заполнитель остаётся только в хвосте. Для одной структуры разница в 8 байтов незаметна, а для массива из миллиона записей это 8 МБ памяти и заметно лучшее использование кэша процессора.

Но порядок полей — ещё и документация: связанные по смыслу поля удобно держать рядом. Переставляйте поля ради размера там, где структур действительно много.

## Заполнители содержат мусор

Байты-заполнители не принадлежат ни одному полю. Присваивание полям их не трогает, поэтому в локальной структуре они содержат то, что было в памяти раньше:

```c
#include <stdio.h>

struct Reading {
    char sensor;
    int value;
};

void dump(const void *data, size_t size) {
    const unsigned char *bytes = data;
    for (size_t i = 0; i < size; i++) {
        printf("%02x ", bytes[i]);
    }
    printf("\n");
}

int main(void) {
    struct Reading r;
    r.sensor = 'T';
    r.value = 21;
    dump(&r, sizeof r);
    return 0;
}
```

Программа печатает 8 байтов: `54` (буква `T`), три байта заполнителя и `15 00 00 00` (число 21). Значения заполнителя случайны. AddressSanitizer такую ошибку не видит, а Valgrind сообщает о чтении неинициализированных байтов:

```text
==30== Conditional jump or move depends on uninitialised value(s)
==30==    at 0x48B26F6: __vfprintf_internal (vfprintf-process-arg.c:174)
==30==    by 0x48A765A: printf (printf.c:33)
==30==    by 0x109191: dump (main.c:11)
==30==    by 0x1091D1: main (main.c:20)
==30==  Uninitialised value was created by a stack allocation
==30==    at 0x1091AE: main (main.c:16)
```

Отсюда три практических следствия:

1. **Не сравнивайте структуры через `memcmp`.** Две структуры с одинаковыми полями могут иметь разный мусор в заполнителях. Сравнивайте поле за полем.
2. **Не записывайте структуры «как есть» в файл или сеть без обнуления.** Заполнители утащат с собой содержимое стека — возможно, пароль или ключ из предыдущего вызова функции. Такие утечки информации находили в ядрах операционных систем.
3. **Если структура всё же уходит наружу байтами — обнулите её целиком** перед заполнением: `memset(&r, 0, sizeof r);`.

```c
#include <stdio.h>
#include <string.h>

struct Reading {
    char sensor;
    int value;
};

int main(void) {
    struct Reading r;
    memset(&r, 0, sizeof r);          // все 8 байтов, включая заполнитель
    r.sensor = 'T';
    r.value = 21;
    const unsigned char *bytes = (const unsigned char *)&r;
    for (size_t i = 0; i < sizeof r; i++) {
        printf("%02x ", bytes[i]);
    }
    printf("\n");
    return 0;
}
```

Вывод:

```text
54 00 00 00 15 00 00 00
```

## Упакованные структуры

GCC и Clang позволяют убрать заполнители атрибутом `__attribute__((packed))`. Это нестандартное расширение: поля становятся невыровненными, доступ к ним медленнее, а указатель на такое поле нельзя безопасно передавать в обычные функции. Для чтения и записи двоичных форматов надёжнее разбирать байты вручную или копировать поля через `memcpy` из байтового буфера, как в уроке о выравнивании.

<Concept title="Размер структуры — сумма полей и заполнителей">

`sizeof(struct T)` = поля + заполнители между ними + хвост до кратного выравниванию структуры. Узнавайте его через `sizeof`, смещения — через `offsetof`, а сокращайте перестановкой полей от самых строгих к самым слабым.

</Concept>

## Частые ошибки

<CommonMistake title="Ручной подсчёт размера">

`malloc(n * (sizeof(char) + sizeof(int)))` для массива структур выделит 5 байтов на запись вместо 8. Только `n * sizeof(struct T)` (или `sizeof *p`).

</CommonMistake>

<CommonMistake title="memcmp для структур">

`memcmp(&a, &b, sizeof a) == 0` может вернуть «не равны» для структур с одинаковыми полями из-за мусора в заполнителях, а для `double` — ошибиться и в другую сторону (`0.0` и `-0.0`). Пишите функцию сравнения полей.

</CommonMistake>

<CommonMistake title="Запись структуры в файл без обнуления">

`fwrite(&r, sizeof r, 1, file)` для структуры, заполненной поле за полем, сохраняет мусор заполнителей. Обнулите структуру перед заполнением — или записывайте поля по отдельности в фиксированном формате.

</CommonMistake>

## Практика

1. **Раскладка структуры** — вычислить смещения полей и размер по правилам выравнивания.
2. **Лучший порядок полей** — минимальный размер после перестановки.
3. **Найди ошибку: мусор в заполнителях** — дамп байтов структуры (проверяется Valgrind).
4. **Сравнение записей** — сравнение по полям вместо `memcmp`.

## Итоги

- Компилятор размещает поля в порядке объявления, вставляя заполнители так, чтобы каждое поле было выровнено.
- Выравнивание структуры — максимальное среди полей; размер округляется до кратного ему, чтобы элементы массива оставались выровненными.
- `offsetof` показывает смещение поля, `sizeof` — полный размер с заполнителями.
- Порядок полей по убыванию выравнивания минимизирует размер.
- Заполнители содержат мусор: не сравнивайте структуры `memcmp` и обнуляйте их перед записью байтами в файл или сеть.
