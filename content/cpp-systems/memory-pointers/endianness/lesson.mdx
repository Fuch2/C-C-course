## В каком порядке лежат байты числа

Число `0x12345678` занимает четыре байта: `12`, `34`, `56`, `78`. Самый «весомый» из них — `12` (**старший** байт), наименее — `78` (**младший**). В каком порядке их положить в память, по адресам 1000, 1001, 1002, 1003? Есть два распространённых соглашения:

<MemoryDiagram title="0x12345678 в памяти">

| Адрес         | 1000 | 1001 | 1002 | 1003 |
| ------------- | ---- | ---- | ---- | ---- |
| little-endian | `78` | `56` | `34` | `12` |
| big-endian    | `12` | `34` | `56` | `78` |

</MemoryDiagram>

- **Little-endian** — младший байт по меньшему адресу. Так работают x86, x86-64 и (в обычном режиме) ARM — то есть почти все компьютеры и телефоны.
- **Big-endian** — старший байт первым, «как пишем на бумаге». Так устроены некоторые старые и встраиваемые процессоры, а главное — **сетевые протоколы** и многие форматы файлов.

Названия пришли из «Путешествий Гулливера»: лилипуты воевали из-за того, с какого конца разбивать яйцо — с тупого (big end) или острого (little end).

## Порядок байтов машины

Внутри одной программы порядок байтов не виден: `x + 1`, `x << 8`, сравнения работают со **значениями**, а не байтами. Порядок проявляется, только когда на число смотрят как на байты — через `unsigned char *`, `memcpy`, `fwrite`:

```c
#include <stdint.h>
#include <stdio.h>
#include <string.h>

int main(void) {
    uint32_t value = 0x12345678;
    unsigned char bytes[4];
    memcpy(bytes, &value, sizeof value);
    printf("%02x %02x %02x %02x\n", bytes[0], bytes[1], bytes[2], bytes[3]);
    printf("%s\n", bytes[0] == 0x78 ? "little-endian" : "big-endian");
    return 0;
}
```

Вывод:

```text
78 56 34 12
little-endian
```

## Почему это важно

Пока данные не покидают программу, порядок байтов можно не замечать. Но как только число записывают в файл или отправляют по сети **как байты памяти**, его прочитает другая программа — возможно, на машине с другим порядком байтов или в формате, где порядок зафиксирован:

| Формат или протокол         | Порядок байтов                 |
| --------------------------- | ------------------------------ |
| TCP/IP (заголовки, порты)   | big-endian («сетевой порядок») |
| PNG, JPEG, Java class-файлы | big-endian                     |
| BMP, WAV, ZIP               | little-endian                  |

Если программа на x86 запишет `fwrite(&port, sizeof port, 1, f)` для порта `8080` (`0x1F90`), в файл попадут байты `90 1F`. Сетевой протокол прочитает их как `0x901F` = 36895 — совсем другой порт.

## Переносимый способ: сдвиги

Решение, которое работает на **любой** машине, — собирать и разбирать числа сдвигами. Сдвиг работает со значением, поэтому результат не зависит от порядка байтов процессора:

```c
#include <stdint.h>
#include <stdio.h>

// Записывает x в 4 байта в порядке big-endian.
void put_u32_be(unsigned char *out, uint32_t x) {
    out[0] = (unsigned char)(x >> 24);
    out[1] = (unsigned char)(x >> 16);
    out[2] = (unsigned char)(x >> 8);
    out[3] = (unsigned char)x;
}

// Читает 4 байта в порядке big-endian.
uint32_t get_u32_be(const unsigned char *in) {
    return (uint32_t)in[0] << 24 | (uint32_t)in[1] << 16 | (uint32_t)in[2] << 8 | (uint32_t)in[3];
}

int main(void) {
    unsigned char packet[4];
    put_u32_be(packet, 0x12345678);
    printf("%02x %02x %02x %02x\n", packet[0], packet[1], packet[2], packet[3]);
    printf("%08x\n", (unsigned)get_u32_be(packet));
    return 0;
}
```

Вывод:

```text
12 34 56 78
12345678
```

Тот же код скомпилируется и даст тот же результат и на little-endian, и на big-endian процессоре. Для little-endian формата меняется только порядок индексов: `out[0] = x`, `out[1] = x >> 8`, и так далее.

Приведение `(uint32_t)in[0]` перед сдвигом обязательно. Без него `unsigned char` превращается в `int`, и `0xFF << 24` не помещается в `int` — неопределённое поведение (вспомните прошлые уроки), а результат после преобразования может «размножить» знаковый бит. С `uint32_t` всё вычисляется в беззнаковом 32-битном типе.

## Перестановка байтов

Иногда нужно просто перевернуть порядок байтов числа — например, прочитав его «не той стороной»:

```c
#include <stdint.h>
#include <stdio.h>

uint32_t swap32(uint32_t x) {
    return (x >> 24) | ((x >> 8) & 0x0000FF00u) | ((x << 8) & 0x00FF0000u) | (x << 24);
}

int main(void) {
    printf("%08x\n", (unsigned)swap32(0x12345678));
    printf("%u\n", (unsigned)swap32(0x901F0000u));
    return 0;
}
```

Вывод:

```text
78563412
8080
```

В POSIX для сетевого порядка есть функции `htonl`, `htons` (host to network) и `ntohl`, `ntohs` (network to host); на big-endian машине они ничего не делают, на little-endian — переставляют байты. GCC и Clang дают встроенную `__builtin_bswap32`. Но функции чтения и записи через сдвиги удобнее: они сразу работают с байтовым буфером и не требуют знать порядок байтов машины.

<Concept title="Значение и представление">

Порядок байтов — свойство **представления** числа в памяти, а не его **значения**. Арифметика, сравнения и сдвиги работают со значениями и одинаковы везде. Порядок байтов важен только на границе программы: при записи байтов в файл, сеть или разделяемую память. На этой границе фиксируйте порядок явно — сдвигами.

</Concept>

## Частые ошибки

<CommonMistake title="fwrite числа или структуры в переносимый формат">

`fwrite(&value, sizeof value, 1, f)` записывает байты в порядке текущей машины (и с заполнителями, если это структура). Файл не прочитается правильно на машине с другим порядком байтов. Записывайте поля через `put_u32_le`/`put_u32_be`.

</CommonMistake>

<CommonMistake title="Сдвиг unsigned char без приведения">

`b[0] << 24` выполняется в `int`; при `b[0] >= 0x80` — переполнение и неопределённое поведение. Пишите `(uint32_t)b[0] << 24`.

</CommonMistake>

<CommonMistake title="Перепутанный порядок формата">

Формат BMP хранит числа в little-endian, PNG — в big-endian. Перед разбором файла найдите в спецификации порядок байтов — это первое, что нужно знать о двоичном формате.

</CommonMistake>

## Практика

1. **Байты в сетевом порядке** — запись чисел в big-endian сдвигами.
2. **Разбор little-endian** — чтение чисел разной ширины из байтов.
3. **Найди ошибку: сдвиг в знаковый бит** — чтение без приведения к беззнаковому типу.
4. **Размер картинки BMP** — разбор полей заголовка настоящего формата.

## Итоги

- Little-endian хранит младший байт первым (x86, ARM), big-endian — старший первым (сетевые протоколы, многие форматы файлов).
- Порядок байтов виден только при обращении к представлению — через `unsigned char *`, `memcpy`, `fwrite`; арифметика от него не зависит.
- Переносимая запись и чтение чисел — сдвигами с явным порядком байтов; результат одинаков на любой машине.
- Перед сдвигом байт приводят к беззнаковому типу нужной ширины: `(uint32_t)b[0] << 24`.
- Для перестановки байтов есть `htonl`/`ntohl` в POSIX и `__builtin_bswap32` в GCC/Clang.
