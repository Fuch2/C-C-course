## Второй инструмент

AddressSanitizer требует пересборки программы со специальными флагами и не видит неинициализированные данные. **Valgrind** работает иначе: он запускает **обычную** программу на виртуальном процессоре и наблюдает за каждой командой. Его основной инструмент, **Memcheck**, для каждого байта памяти помнит, выделен ли он и записано ли в него значение — вплоть до отдельных битов.

```text
gcc -std=c17 -g -O0 main.c -o main
valgrind --leak-check=full --track-origins=yes ./main
```

| Параметр              | Зачем                                                                     |
| --------------------- | ------------------------------------------------------------------------- |
| `-g -O0` при сборке   | номера строк в отчётах и предсказуемое соответствие кода и команд         |
| `--leak-check=full`   | подробный отчёт о каждой утечке с местом выделения                        |
| `--track-origins=yes` | для неинициализированных значений показывать, **где** они возникли        |
| `--error-exitcode=99` | завершать программу с этим кодом, если найдены ошибки (удобно для тестов) |

Задачи этого урока проверяются Valgrind с этими параметрами.

## Неинициализированные значения

Вот программа, которую AddressSanitizer считает **полностью чистой**:

```c
#include <stdio.h>
#include <stdlib.h>

int main(void) {
    int n = 5;
    int *scores = malloc(n * sizeof *scores);
    if (scores == NULL) {
        return 1;
    }
    for (int i = 1; i < n; i++) {       // scores[0] не записан
        scores[i] = 10 * i;
    }
    int best = scores[0];
    for (int i = 1; i < n; i++) {
        if (scores[i] > best) {
            best = scores[i];
        }
    }
    printf("%d\n", best);
    char *label = malloc(32);
    if (label != NULL) {
        snprintf(label, 32, "best=%d", best);
    }
    return 0;
}
```

С ASan она печатает `40` и завершается без единого предупреждения: все обращения в границах блоков, а утечки LeakSanitizer не увидел — указатели на блоки ещё лежали в кадре `main` к моменту проверки. Valgrind находит три ошибки:

```text
==30== Conditional jump or move depends on uninitialised value(s)
==30==    at 0x1091F1: main (main.c:15)
==30==  Uninitialised value was created by a heap allocation
==30==    at 0x48417B4: malloc (in /usr/libexec/valgrind/vgpreload_memcheck-amd64-linux.so)
==30==    by 0x109178: main (main.c:6)
==30==
==30== 20 bytes in 1 blocks are definitely lost in loss record 1 of 2
==30==    at 0x48417B4: malloc (in /usr/libexec/valgrind/vgpreload_memcheck-amd64-linux.so)
==30==    by 0x109178: main (main.c:6)
==30==
==30== 32 bytes in 1 blocks are definitely lost in loss record 2 of 2
==30==    at 0x48417B4: malloc (in /usr/libexec/valgrind/vgpreload_memcheck-amd64-linux.so)
==30==    by 0x10923A: main (main.c:20)
==30==
==30== LEAK SUMMARY:
==30==    definitely lost: 52 bytes in 2 blocks
==30==    indirectly lost: 0 bytes in 0 blocks
==30==      possibly lost: 0 bytes in 0 blocks
==30==    still reachable: 0 bytes in 0 blocks
==30==
==30== ERROR SUMMARY: 3 errors from 3 contexts (suppressed: 0 from 0)
```

Разберём первую ошибку. **Conditional jump … depends on uninitialised value** — условие `if (scores[i] > best)` в строке 15 зависит от неинициализированного значения: `best` получил мусор из `scores[0]`. Memcheck сообщает не в момент копирования мусора (строка 13), а когда от него **зависит решение** программы — ветвление, адрес обращения или системный вызов. Строка «created by a heap allocation … main.c:6» благодаря `--track-origins=yes` указывает, откуда взялся мусор: из блока `malloc` без инициализации.

## Виды сообщений Memcheck

| Сообщение                                                    | Что случилось                                                  |
| ------------------------------------------------------------ | -------------------------------------------------------------- |
| `Invalid read of size N` / `Invalid write of size N`         | чтение или запись вне выделенного блока или в освобождённый    |
| `Conditional jump or move depends on uninitialised value(s)` | ветвление по неинициализированному значению                    |
| `Use of uninitialised value of size N`                       | мусор использован как адрес или передан в вычисление           |
| `Syscall param write(buf) points to uninitialised byte(s)`   | мусор уходит в файл или сеть — например, заполнители структуры |
| `Invalid free() / delete / delete[] / realloc()`             | двойное освобождение или `free` не того адреса                 |
| `Source and destination overlap in memcpy`                   | перекрытие областей в `memcpy`                                 |

Отчёт об ошибке границ похож на ASan, только формулировки другие:

```text
==30== Invalid read of size 4
==30==    at 0x109189: sum_values (main.c:7)
==30==    by 0x109216: main (main.c:21)
==30==  Address 0x4a3a054 is 0 bytes after a block of size 20 alloc'd
==30==    at 0x48417B4: malloc (in /usr/libexec/valgrind/vgpreload_memcheck-amd64-linux.so)
==30==    by 0x1091C2: main (main.c:14)
```

«0 bytes after a block of size 20» — то же, что «0 bytes to the right of 20-byte region» у ASan.

## Категории утечек

В конце работы Memcheck проверяет все невозвращённые блоки и делит их на четыре группы:

- **definitely lost** — на блок не указывает ни один указатель. Это настоящая утечка; исправлять обязательно.
- **indirectly lost** — на блок указывает только другой потерянный блок (узлы потерянного списка). Исчезнет, когда исправите «definitely lost».
- **possibly lost** — найден указатель только на середину блока. Часто это тоже утечка.
- **still reachable** — на блок ещё есть указатель (например, из глобальной переменной), но его не освободили. Это не потеря, но хорошая программа освобождает и такие блоки.

## ASan или Valgrind

| Свойство                                | AddressSanitizer         | Valgrind (Memcheck)                |
| --------------------------------------- | ------------------------ | ---------------------------------- |
| нужна пересборка                        | да, `-fsanitize=address` | нет, работает с готовой программой |
| замедление                              | примерно 2×              | 10–50×                             |
| неинициализированные значения           | нет                      | **да**                             |
| выход за локальные и глобальные массивы | **да**                   | почти нет (видит только кучу)      |
| после первой ошибки                     | останавливается          | продолжает и сообщает все          |
| платформы                               | Linux, macOS, Windows    | в основном Linux                   |

Инструменты дополняют друг друга. ASan удобен как постоянная проверка в тестах, Valgrind — как «вторая линия» для поиска неинициализированных данных и проверки готовых программ, которые нельзя пересобрать. Одновременно их не запускают: программа, собранная с ASan, под Valgrind не работает.

<Concept title="Valgrind следит за смыслом байтов">

Для каждого бита памяти Memcheck хранит «определён ли он». Копирование мусора не ошибка — мусор просто переносится вместе со своей пометкой. Ошибка возникает, когда от неопределённого значения зависит поведение программы. Поэтому место отчёта — это место **использования**, а `--track-origins=yes` показывает место **происхождения**.

</Concept>

## Частые ошибки

<CommonMistake title="Сборка с оптимизацией">

При `-O2` компилятор переставляет и объединяет операции, и строки в отчётах Valgrind могут не совпадать с кодом. Для отладки собирайте с `-g -O0`.

</CommonMistake>

<CommonMistake title="Игнорировать «still reachable»">

Блоки «still reachable» не утекли, но они маскируют настоящие проблемы и мешают читать отчёт. Освобождайте всю память перед выходом — тогда любой новый блок в отчёте сразу заметен.

</CommonMistake>

<CommonMistake title="Ожидать от ASan то же, что от Valgrind">

Чистый запуск с ASan не означает отсутствия неинициализированных чтений. Если программа ведёт себя по-разному от запуска к запуску, проверьте её Valgrind.

</CommonMistake>

## Практика

Все задачи этого урока проверяются **Valgrind**: ошибка найдена, даже если вывод программы совпал с ожидаемым.

1. **Найди ошибку: счётчики из malloc** — неинициализированный массив счётчиков.
2. **Найди ошибку: строка без нуля** — копия строки без завершающего нуля.
3. **Найди ошибку: утечка списка** — освобождается только голова.
4. **Найди ошибку: перевёрнутая копия** — запись на байт за блоком.

## Итоги

- Valgrind (Memcheck) проверяет готовую программу без пересборки: собирайте с `-g -O0` и запускайте с `--leak-check=full --track-origins=yes`.
- Главное преимущество перед ASan — обнаружение неинициализированных значений; ошибка сообщается в месте использования, `--track-origins` показывает место происхождения.
- Memcheck сообщает о неверных чтениях и записях, неверных освобождениях, перекрытии в `memcpy` и утечках.
- Утечки делятся на definitely, indirectly, possibly lost и still reachable; исправлять начинают с definitely lost.
- Valgrind медленнее ASan в 10–50 раз и видит в основном кучу; инструменты дополняют друг друга.
