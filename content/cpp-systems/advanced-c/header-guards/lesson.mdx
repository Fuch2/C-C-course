## Один заголовок — дважды в одном файле

Заголовки подключают друг друга. Модуль фигур описывает окружность через точку, поэтому его заголовок подключает заголовок точки:

```c point.h
struct Point {
    int x;
    int y;
};

static inline int manhattan(struct Point p) {
    return (p.x < 0 ? -p.x : p.x) + (p.y < 0 ? -p.y : p.y);
}
```

```c shapes.h
#include "point.h"

struct Circle {
    struct Point center;
    int radius;
};
```

А программе нужны и точки, и окружности:

```c main.c
#include "point.h"
#include "shapes.h"

int main(void) {
    struct Circle c = {{0, 0}, 5};
    return c.radius;
}
```

Сборка падает с ошибкой `redefinition of 'manhattan'`. Посмотрим на единицу трансляции после препроцессора: `point.h` вставлен дважды — один раз напрямую, второй раз через `shapes.h`:

```text
struct Point { int x; int y; };          ← из #include "point.h" в main.c
static inline int manhattan(…) { … }
struct Point { int x; int y; };          ← из #include "point.h" в shapes.h
static inline int manhattan(…) { … }
struct Circle { struct Point center; int radius; };
int main(void) { ... }
```

Тот же эффект в одном файле:

```c
#include <stdio.h>

struct Point {
    int x;
    int y;
};

static inline int manhattan(struct Point p) {
    return (p.x < 0 ? -p.x : p.x) + (p.y < 0 ? -p.y : p.y);
}

static inline int manhattan(struct Point p) {      // Ошибка компиляции: redefinition of 'manhattan'
    return (p.x < 0 ? -p.x : p.x) + (p.y < 0 ? -p.y : p.y);
}

int main(void) {
    struct Point p = {1, -2};
    printf("%d\n", manhattan(p));
    return 0;
}
```

А что со структурой? До C23 её повторное определение тоже было ошибкой: `redefinition of 'struct Point'`. C23 смягчил правило — **одинаковое** определение структуры, объединения или перечисления теперь можно повторить. GCC 14 это уже поддерживает, Clang 19 — ещё нет и по-прежнему сообщает об ошибке. Но функции и переменные повторять нельзя ни в одном стандарте, а заголовок почти всегда содержит что-то из них — или будет содержать завтра.

В маленьком проекте можно было бы следить за порядком включений вручную, но в большом это невозможно: заголовок стандартной библиотеки подключается десятками путей, и никто не знает их все.

## Что можно повторять, а что нет

Не всё в заголовке ломается при повторе. **Объявления** повторять можно: прототипы функций, объявления переменных с `extern`, одинаковые `typedef` (с C11) и одинаковые определения макросов. **Определения** функций с телом и переменных — нельзя. Определения структур, объединений и перечислений до C23 тоже повторять было нельзя, а в C23 — можно, если они полностью совпадают; поскольку не все компиляторы это уже умеют, на такую возможность не полагаются.

```c
#include <stdio.h>

int area(int w, int h);
int area(int w, int h);             // повтор прототипа — допустимо

typedef unsigned long long u64;
typedef unsigned long long u64;     // одинаковый typedef — допустимо с C11

#define LIMIT 100
#define LIMIT 100                   // одинаковый макрос — допустимо

int area(int w, int h) {
    return w * h;
}

int main(void) {
    u64 big = (u64)area(LIMIT, LIMIT);
    printf("%llu\n", big);
    return 0;
}
```

Вывод:

```text
10000
```

Заголовок, в котором есть хотя бы одно определение функции или переменной (а для компиляторов до C23 — и определение типа), при повторном включении сломает сборку. А такой заголовок — почти каждый.

## Защита: `#ifndef`, `#define`, `#endif`

Решение — **защита от повторного включения** (include guard). Весь текст заголовка оборачивают в три директивы препроцессора:

```c point.h
#ifndef POINT_H
#define POINT_H

struct Point {
    int x;
    int y;
};

#endif
```

- `#ifndef POINT_H` — «если макрос `POINT_H` **не** определён», оставить текст до `#endif`, иначе выбросить его;
- `#define POINT_H` — определить макрос (значение не нужно, важен сам факт определения);
- `#endif` — конец условного блока.

При **первом** включении `POINT_H` ещё не определён: препроцессор оставляет текст, по пути определяет `POINT_H` и вставляет структуру. При **втором** `POINT_H` уже определён, и всё до `#endif` выбрасывается. Структура оказывается в единице трансляции ровно один раз.

Проверим: вставим текст защищённого заголовка в файл дважды — так, как это сделал бы препроцессор:

```c
#include <stdio.h>

// ---- point.h: первое включение ----
#ifndef POINT_H
#define POINT_H
struct Point {
    int x;
    int y;
};
#endif

// ---- point.h: второе включение, через shapes.h ----
#ifndef POINT_H
#define POINT_H
struct Point {
    int x;
    int y;
};
#endif

int main(void) {
    struct Point p = {3, 4};
    printf("%d %d\n", p.x, p.y);
    return 0;
}
```

Вывод:

```text
3 4
```

Директивы `#ifndef` и `#define` — части препроцессора, которым посвящён отдельный блок уроков: там вы разберёте условную компиляцию подробно. Для защиты заголовков достаточно этого шаблона.

## Имя защитного макроса

Макрос должен быть **уникальным во всём проекте**, включая подключаемые библиотеки. Если в каталогах `net/` и `storage/` лежат два разных `util.h` и оба защищены макросом `UTIL_H`, то второй из них будет молча выброшен целиком — а ошибка проявится странно, например `unknown type name 'Buffer'` в совсем другом месте.

Обычно имя строят из названия проекта и пути к файлу, записанных заглавными буквами, а всё, кроме букв и цифр, заменяют на `_`:

| Файл                    | Макрос                  |
| ----------------------- | ----------------------- |
| `include/geo/point.h`   | `GEO_POINT_H`           |
| `src/net/http-client.h` | `GEO_NET_HTTP_CLIENT_H` |
| `src/storage/util.h`    | `GEO_STORAGE_UTIL_H`    |

В старом коде часто встречаются имена `_POINT_H` или `__POINT_H__`. Так делать **нельзя**: идентификаторы, начинающиеся с подчёркивания и заглавной буквы или с двух подчёркиваний, зарезервированы для компилятора и стандартной библиотеки. Совпадение с внутренним макросом библиотеки даст ту же загадочную ошибку.

## `#pragma once`

Почти все компиляторы — GCC, Clang, MSVC — понимают более короткую запись:

```c point.h
#pragma once

struct Point {
    int x;
    int y;
};
```

Препроцессор сам запоминает, что файл уже подключался. Имя макроса придумывать не нужно, конфликтов имён не бывает. Минус в том, что `#pragma once` не входит в стандарт C, и в редких случаях (одинаковые копии файла по разным путям, символические ссылки) компилятор может посчитать один файл двумя. На практике встречаются оба способа; в стандартной библиотеке и в этом курсе — `#ifndef`.

## Чего защита не делает

Защита работает **внутри одной единицы трансляции**. Каждый `.c` файл препроцессор обрабатывает с нуля: макрос `POINT_H`, определённый при сборке `main.c`, ничего не значит при сборке `shapes.c`. Поэтому защита не спасает от определения функции или переменной в заголовке: каждый файл получит свою копию, и линковщик сообщит `multiple definition`. Защита решает одну задачу — повторное включение в один и тот же файл.

## Циклические включения

Иногда два заголовка ссылаются друг на друга: сотрудник знает свой отдел, а отдел — своего руководителя.

```c employee.h
#ifndef EMPLOYEE_H
#define EMPLOYEE_H
#include "department.h"

struct Employee {
    char name[32];
    struct Department *dept;
};
#endif
```

```c department.h
#ifndef DEPARTMENT_H
#define DEPARTMENT_H
#include "employee.h"

struct Department {
    char title[32];
    struct Employee *head;
};
#endif
```

Без защиты такие файлы подключали бы друг друга бесконечно; GCC остановится с ошибкой `#include nested depth 200 exceeds maximum of 200`. С защитой бесконечности нет, но порядок всё равно ломается. Пусть `main.c` подключает `employee.h`: определяется `EMPLOYEE_H`, затем подключается `department.h`, который пытается подключить `employee.h` — тот уже «подключён» и выбрасывается. В результате `struct Department` компилируется **раньше**, чем `struct Employee`, хотя ссылается на неё.

Здесь это сработает случайно: поле `head` — указатель, а для указателя достаточно знать, что структура существует. Но если бы `department.h` использовал `struct Employee` по значению или обращался к её полям, сборка упала бы.

Правильное решение — **предварительное объявление** (forward declaration) вместо включения. Если заголовку нужны только указатели на структуру, ему достаточно строки `struct Employee;`:

```c
#include <stdio.h>
#include <string.h>

struct Department;               // предварительное объявление: поля пока неизвестны

struct Employee {
    char name[32];
    struct Department *dept;     // указатель на неполный тип — допустимо
};

struct Department {
    char title[32];
    struct Employee *head;
};

int main(void) {
    struct Department lab;
    struct Employee boss;
    strcpy(lab.title, "Лаборатория");
    strcpy(boss.name, "Иванова");
    lab.head = &boss;
    boss.dept = &lab;
    printf("%s: руководитель %s\n", boss.dept->title, lab.head->name);
    return 0;
}
```

Вывод:

```text
Лаборатория: руководитель Иванова
```

Правило: подключайте заголовок, когда нужен **полный** тип (поле по значению, `sizeof`, доступ к полям), и обходитесь предварительным объявлением, когда нужен только **указатель**. Это разрывает циклы и уменьшает число файлов, которые приходится пересобирать после правки заголовка.

<Concept title="Защита — это шаблон, который пишут всегда">

Не ждите, пока заголовок подключат дважды. Защиту добавляют в **каждый** заголовок сразу при создании: первые две строки — `#ifndef` и `#define`, последняя — `#endif`. Тогда порядок и число включений перестают иметь значение.

</Concept>

## Частые ошибки

<CommonMistake title="Одинаковые имена защитных макросов">

Скопировали `list.h` в `queue.h`, а `#ifndef LIST_H` оставили. Теперь файл, подключивший оба заголовка, получит только первый. Строите имя из пути к файлу — и следите за ним при копировании.

</CommonMistake>

<CommonMistake title="Текст за пределами защиты">

```c config.h
#ifndef CONFIG_H
#define CONFIG_H
#define MAX_USERS 64
#endif

struct Config { int users; };      // за #endif — повторится при каждом включении
```

Всё содержимое заголовка, кроме комментариев, должно лежать между `#define` и `#endif`.

</CommonMistake>

<CommonMistake title="Зарезервированные имена">

`#ifndef _CONFIG_H` и `#ifndef __CONFIG_H__` нарушают правило о зарезервированных идентификаторах. Пишите `PROJECT_CONFIG_H`.

</CommonMistake>

<CommonMistake title="Защита от multiple definition">

Защита не действует между разными `.c` файлами. Определение функции или переменной в заголовке остаётся ошибкой линковки независимо от защиты.

</CommonMistake>

## Практика

1. **Имя защитного макроса** — построить имя по пути к файлу.
2. **Найди ошибку: двойное включение** — заголовок без защиты попал в файл дважды.
3. **Проверка включений** — смоделировать препроцессор и найти повторные определения и циклы.

## Итоги

- Заголовок может попасть в одну единицу трансляции несколько раз — напрямую и через другие заголовки. Повторное определение типа — ошибка компиляции.
- Защита `#ifndef ИМЯ` / `#define ИМЯ` / `#endif` оставляет текст заголовка только при первом включении. Её пишут в каждом заголовке.
- Имя защитного макроса уникально в проекте: строится из названия проекта и пути. Имена с `_` и заглавной буквой или с `__` зарезервированы.
- `#pragma once` короче и избавляет от имён, но не входит в стандарт.
- Защита действует только внутри одной единицы трансляции и не спасает от `multiple definition`.
- Если заголовку нужен только указатель на структуру, вместо `#include` достаточно предварительного объявления `struct X;` — это разрывает циклические включения.
