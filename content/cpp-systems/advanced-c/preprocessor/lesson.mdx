## Цели обучения

- Разобраться в теме «Preprocessor» и её границах применимости.
- Объяснить типичную ошибку, а не только запомнить правильную запись.
- Проверить решение на нормальных и граничных входах.

## Теория

Препроцессор работает с токенами до обычного анализа типов. Он включает файлы, раскрывает макросы и выбирает условные ветви. Он не знает значений переменных времени выполнения. После его работы компилятор видит уже преобразованный текст, поэтому сообщение об ошибке макроса удобнее исследовать через результат gcc -E.

Разделяйте причины: синтаксическая ошибка в раскрытии относится к компиляции; отсутствие определения внешнего имени проявится позже. Директивы не являются инструкциями процессора. Например #if выбирает один вариант программы при сборке, а if выбирает ветвь для каждого конкретного ввода. Конфигурация сборки должна воспроизводиться явно, а не зависеть от случайного набора макросов окружения.

## Запускаемый пример

Пример не требует stdin. Выполните его кнопкой «Запустить», затем измените одно значение и предскажите новый результат до повторного запуска.

```c
#include <stdio.h>
#define CHANNELS 3
int main(void) {
    printf("%d\n",CHANNELS+1);
    return 0;
}
```

## Разбор выполнения

Сначала создаются объекты и выбирается операция, затем вычисляется аргумент вывода. Ожидаемый stdout:

```text
4
```

Это редактор рецепта до приготовления: после редактирования повар получает один окончательный рецепт. Проверьте, какая часть примера задаётся при трансляции, а какая выполняется в main. Нельзя проверять runtime-переменную директивой #if; неизвестный идентификатор в её выражении обычно становится нулём.

```sh
gcc -std=c17 -E main.c -o main.i
gcc -std=c17 -S main.c -o main.s
gcc -std=c17 -c main.c -o main.o
```

Сравните исходный макрос с раскрытым выражением в main.i. .s показывает результат генерации ассемблера, .o содержит объектный код для последующей линковки. Эти команды выполняются в отдельной доверенной среде сборки.
