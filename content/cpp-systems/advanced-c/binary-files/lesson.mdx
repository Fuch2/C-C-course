## Текст или байты

Данные можно сохранить двумя способами. **Текстовый** формат — CSV, JSON, конфигурационные файлы — читается человеком и одинаково понимается любой системой, но он объёмный, медленно разбирается, а дробные числа при переводе в текст и обратно теряют точность. **Двоичный** формат — изображения, архивы, базы данных, сохранения игр — компактен, быстро читается и хранит числа точно, но его нельзя открыть в блокноте, и он требует точного описания.

Число 1 000 000 в тексте — 7 байтов `"1000000"`, в двоичном виде — 4 байта `40 42 0F 00`. Файл из миллиона таких чисел — 7 и 4 мегабайта, а разбор текста ещё и в десятки раз медленнее.

## Формат — это спецификация байтов

Двоичный формат описывает каждый байт файла:

- **сигнатура** («магическое число») — первые байты, по которым программа узнаёт тип файла;
- **версия** формата — чтобы новые программы читали старые файлы и отвергали слишком новые;
- **порядок байтов** многобайтовых чисел и их **размеры**;
- **расположение полей**: смещение и тип каждого;
- способ хранения **строк** и **списков**: обычно сначала длина, потом данные;
- иногда **контрольная сумма** для проверки целостности.

Сигнатуры известных форматов:

| Формат | Первые байты              | Как выглядят             |
| ------ | ------------------------- | ------------------------ |
| PNG    | `89 50 4E 47 0D 0A 1A 0A` | `.PNG....`               |
| BMP    | `42 4D`                   | `BM`                     |
| ZIP    | `50 4B 03 04`             | `PK..`                   |
| PDF    | `25 50 44 46`             | `%PDF`                   |
| ELF    | `7F 45 4C 46`             | `.ELF` — программы Linux |

Сигнатура PNG придумана хитро: байт `89` отличает файл от текста, а `0D 0A` и `0A` ломаются, если файл по ошибке передали в текстовом режиме, — испорченный файл сразу видно.

## Почему не `fwrite(&структура)`

Соблазнительно записать структуру целиком одним `fwrite`. Но байты структуры в памяти — не формат, а деталь конкретной программы. Вы знаете из модуля о памяти, чем они отличаются на разных машинах:

```c
#include <stdio.h>
#include <stdint.h>

struct Header {
    char magic[3];
    uint32_t count;
    uint16_t version;
};

int main(void) {
    printf("сумма полей %zu, sizeof %zu\n",
           sizeof(char[3]) + sizeof(uint32_t) + sizeof(uint16_t), sizeof(struct Header));
    return 0;
}
```

Вывод:

```text
сумма полей 9, sizeof 12
```

Один байт выравнивания после `magic`, чтобы `count` начинался с адреса, кратного 4, и два в конце — их значения не определены. Порядок байтов в `count` зависит от процессора. Другой компилятор может выровнять иначе. Поэтому двоичный формат кодируют **поле за полем**, явно задавая порядок байтов — сдвигами, как в уроке о порядке байтов.

## Запись: поле за полем

Удобно завести функции записи чисел заданной ширины в little-endian — этот порядок используют большинство современных форматов (BMP, ZIP, WAV):

```c
#include <stdint.h>
#include <stdio.h>
#include <string.h>

static void put_u16(FILE *f, uint16_t v) {
    fputc(v & 0xFF, f);
    fputc(v >> 8, f);
}

static void put_u32(FILE *f, uint32_t v) {
    for (int i = 0; i < 4; i++) {
        fputc((v >> (8 * i)) & 0xFF, f);
    }
}

static void put_string(FILE *f, const char *s) {        // длина, затем байты
    size_t len = strlen(s);
    fputc((int)len, f);
    fwrite(s, 1, len, f);
}

int main(void) {
    FILE *f = fopen("save.bin", "wb+");
    if (f == NULL) {
        return 1;
    }
    fwrite("SAVE", 1, 4, f);          // сигнатура
    put_u16(f, 1);                    // версия
    put_string(f, "Alice");           // имя игрока
    put_u32(f, 123456);               // очки
    rewind(f);
    int c, count = 0;
    while ((c = fgetc(f)) != EOF) {
        printf("%02X ", c);
        count++;
    }
    printf("\nвсего %d байтов\n", count);
    fclose(f);
    return 0;
}
```

Вывод:

```text
53 41 56 45 01 00 05 41 6C 69 63 65 40 E2 01 00
всего 16 байтов
```

Каждый байт файла объясним: `SAVE`, версия `01 00` (младший байт первым), длина имени `05`, буквы `Alice`, очки 123 456 = `0x0001E240` в порядке `40 E2 01 00`. Строка хранится без завершающего нуля — длина известна заранее, и читатель не должен искать конец.

## Чтение: доверять нельзя ничему

Двоичный файл мог быть повреждён, обрезан, создан другой версией программы — или специально подготовлен злоумышленником. Поэтому читатель проверяет **всё**: сигнатуру, версию, каждое число на допустимость и каждую длину на то, хватает ли данных в файле. Числа собирают из `unsigned char`: знаковый `char` с байтом `0xE2` дал бы отрицательное значение и испортил результат.

```c
#include <stdint.h>
#include <stdio.h>
#include <string.h>

static int get_u16(FILE *f, uint16_t *out) {
    unsigned char b[2];
    if (fread(b, 1, 2, f) != 2) {
        return 0;
    }
    *out = (uint16_t)(b[0] | b[1] << 8);
    return 1;
}

static int get_u32(FILE *f, uint32_t *out) {
    unsigned char b[4];
    if (fread(b, 1, 4, f) != 4) {
        return 0;
    }
    *out = (uint32_t)b[0] | (uint32_t)b[1] << 8 | (uint32_t)b[2] << 16 | (uint32_t)b[3] << 24;
    return 1;
}

static const char *load(FILE *f, char *name, uint32_t *score) {
    char magic[4];
    uint16_t version;
    if (fread(magic, 1, 4, f) != 4 || memcmp(magic, "SAVE", 4) != 0) {
        return "не файл сохранения";
    }
    if (!get_u16(f, &version)) {
        return "файл обрезан";
    }
    if (version != 1) {
        return "неподдерживаемая версия";
    }
    int len = fgetc(f);
    if (len == EOF || len > 31 || fread(name, 1, (size_t)len, f) != (size_t)len) {
        return "повреждено имя";
    }
    name[len] = '\0';
    if (!get_u32(f, score)) {
        return "файл обрезан";
    }
    return NULL;
}

int main(void) {
    const unsigned char good[] = {'S', 'A', 'V', 'E', 1, 0, 3, 'B', 'o', 'b', 0x10, 0x27, 0, 0};
    const unsigned char cut[] = {'S', 'A', 'V', 'E', 1, 0, 3, 'B', 'o'};
    const unsigned char *files[] = {good, cut};
    size_t sizes[] = {sizeof good, sizeof cut};
    for (int i = 0; i < 2; i++) {
        FILE *f = tmpfile();
        if (f == NULL) {
            return 1;
        }
        fwrite(files[i], 1, sizes[i], f);
        rewind(f);
        char name[32];
        uint32_t score;
        const char *error = load(f, name, &score);
        if (error != NULL) {
            printf("ошибка: %s\n", error);
        } else {
            printf("%s: %u очков\n", name, (unsigned)score);
        }
        fclose(f);
    }
    return 0;
}
```

Вывод:

```text
Bob: 10000 очков
ошибка: повреждено имя
```

Проверка длины имени — `len > 31` — защищает буфер `name`: без неё файл с длиной 200 записал бы данные за его границу. Это одна из самых частых уязвимостей разборщиков: **длина из файла — это ввод, а не гарантия**. Перед `malloc(count * size)` по числу из файла тоже проверяют разумный предел и переполнение умножения.

## Шестнадцатеричный дамп

Чтобы увидеть содержимое двоичного файла, используют **дамп**: смещение, байты в шестнадцатеричном виде и те же байты как символы. В Linux — `xxd файл` или `hexdump -C файл`:

```text
$ hexdump -C save.bin
00000000  53 41 56 45 01 00 05 41  6c 69 63 65 40 e2 01 00  |SAVE...Alice@...|
00000010
```

Непечатаемые байты в правой колонке заменены точками. Читая дамп, вы сверяете его со спецификацией формата: где сигнатура, где длина, где число — именно так отлаживают программы, работающие с двоичными файлами.

<Concept title="Формат определяют байты, а не структуры">

Двоичный формат — договор о том, какой байт что означает, независимо от процессора и компилятора. Программа переводит свои структуры в эти байты (сериализация) и обратно (десериализация) явным кодом. Писатель следует спецификации точно, читатель проверяет каждое поле и каждую длину — и тогда файл, записанный на одной машине, правильно прочитается на любой другой.

</Concept>

## Частые ошибки

<CommonMistake title="fwrite структуры как формат">

Выравнивание, порядок байтов и размеры типов зависят от платформы. Записывайте поля по одному с явным порядком байтов.

</CommonMistake>

<CommonMistake title="char вместо unsigned char">

`(b[1] << 8) | b[0]` для `char b[2]` с байтом `0xE2` на платформах, где `char` знаковый (x86-64), даст отрицательное значение из-за расширения знака, а на ARM — правильное: одна и та же программа ведёт себя по-разному. Для байтов файла — `unsigned char`, а перед сдвигом — приведение к широкому беззнаковому типу.

</CommonMistake>

<CommonMistake title="Длина из файла без проверки">

Число записей, длина строки, размер блока из файла должны быть проверены: не больше буфера, не больше разумного предела и не больше оставшихся байтов. Иначе повреждённый файл приведёт к переполнению буфера или огромному выделению памяти.

</CommonMistake>

<CommonMistake title="Не проверить, что файл закончился">

Файл с лишними байтами после данных — тоже повреждённый или другой версии. Если формат задаёт точный размер, после разбора проверьте, что дальше `EOF`.

</CommonMistake>

## Итоги

- Двоичный формат компактен и точен, но требует спецификации каждого байта: сигнатура, версия, порядок байтов, размеры и расположение полей, способ хранения строк.
- Байты структуры в памяти — не формат: выравнивание, порядок байтов и размеры типов зависят от платформы.
- Числа записывают и читают по байтам сдвигами с явным порядком; байты хранят в `unsigned char`.
- Строки и списки хранят с длиной перед данными.
- Читатель проверяет сигнатуру, версию, каждое значение и каждую длину; длина из файла — ввод, а не гарантия.
- Шестнадцатеричный дамп (`xxd`, `hexdump -C`) показывает байты файла для сверки со спецификацией.
