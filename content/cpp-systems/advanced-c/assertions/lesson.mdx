## Проверки для программиста

В прошлом уроке ошибки делились на три вида. Отказы окружения и неверные данные программа обрабатывает. А **ошибки программиста** — функцию вызвали с нарушением договора, структура данных пришла в невозможное состояние — обрабатывать бессмысленно: программа уже работает не так, как задумано. Такие ошибки нужно **найти** — как можно ближе к месту, где они возникли.

Для этого есть макрос `assert` из `<assert.h>`. Он проверяет условие, которое при правильной программе истинно **всегда**. Если условие ложно, `assert` печатает в `stderr` выражение, файл, строку и функцию и аварийно завершает программу вызовом `abort`:

```c
#include <assert.h>
#include <stdio.h>

static double average(const int *values, int count) {
    assert(count > 0 && "пустой массив");
    long long sum = 0;
    for (int i = 0; i < count; i++) {
        sum += values[i];
    }
    return (double)sum / count;
}

int main(void) {
    int data[] = {4, 8};
    printf("%.1f\n", average(data, 2));
    printf("%.1f\n", average(data, 0));      // Ошибка выполнения: нарушено условие assert
    return 0;
}
```

Программа завершится с кодом 134 (сигнал `SIGABRT`), а в `stderr` появится:

```text
program: main.c:5: average: Assertion `count > 0 && "пустой массив"' failed.
```

Сообщение указывает точное место нарушенного предположения. Строка `"пустой массив"` в условии — приём для пояснения: строковый литерал всегда истинен, поэтому на результат проверки не влияет, но попадает в текст сообщения.

Запустите пример: строка `6.0` от первого вызова тоже исчезнет. Когда вывод идёт не в терминал, `stdout` буферизуется блоками, а `abort` завершает процесс, не сбрасывая буферы. Поэтому после аварийного завершения не стоит доверять тому, что вывод «дошёл до места».

## Что проверять через `assert`

`assert` выражает **предположения о коде**:

- **предусловия** — что функция требует от аргументов: указатель не `NULL`, индекс в пределах, массив отсортирован;
- **постусловия** — что функция гарантирует на выходе: результат в диапазоне, буфер завершён нулём;
- **инварианты** — что всегда верно для структуры данных: `size <= capacity`, куча упорядочена, список не зациклен.

Но не всё, что может пойти не так, — предмет `assert`:

| Ситуация                                           | Чем проверять                |
| -------------------------------------------------- | ---------------------------- |
| своя функция получила `NULL` вопреки договору      | `assert`                     |
| индекс, вычисленный своим же кодом, вне массива    | `assert`                     |
| пользователь ввёл `-5` вместо положительного числа | обработка ошибки и сообщение |
| `fopen` вернул `NULL`                              | обработка ошибки             |
| `malloc` вернул `NULL`                             | обработка ошибки             |
| в файле испорченная запись                         | обработка ошибки             |

Простое правило: если условие может нарушиться при правильной программе — из-за данных или окружения, — это не `assert`. Программа, которая падает на неверном вводе, — неудачная программа, а не строгая.

## `NDEBUG`: проверки исчезают

Если до подключения `<assert.h>` определён макрос `NDEBUG`, `assert(x)` превращается в `((void)0)` — выражение **не вычисляется вообще**. Финальные сборки часто компилируют с `-DNDEBUG` (так делает, например, режим `Release` в CMake), чтобы проверки не тратили время. Отсюда главное правило: **внутри `assert` не должно быть действий**, только проверка.

```c
#define NDEBUG                     // как в финальной сборке
#include <assert.h>
#include <stdio.h>

int main(void) {
    int processed = 0;
    assert(++processed == 1);      // действие внутри assert — исчезнет
    printf("обработано: %d\n", processed);

    FILE *f = fopen("log.txt", "w");
    assert(f != NULL);             // проверка тоже исчезнет — f не проверен!
    if (f != NULL) {
        fclose(f);
    }
    return 0;
}
```

Вывод:

```text
обработано: 0
```

В отладочной сборке программа напечатала бы 1, в финальной — 0. А `assert(f != NULL)` вместо обработки ошибки в финальной сборке не защищает ни от чего. Правильно: действие — отдельной строкой, проверка — `assert` только для условий о самом коде.

## `static_assert`: проверка при компиляции

Некоторые предположения можно проверить ещё до запуска — если они выражаются константным выражением. Для этого есть `static_assert(условие, "сообщение")`. Ложное условие — ошибка компиляции с вашим сообщением.

В C23 `static_assert` — ключевое слово языка: заголовок подключать не нужно, а сообщение можно опустить — `static_assert(sizeof(int) >= 4);`. В C11 и C17 то же самое записывалось как `_Static_assert(условие, "сообщение")` с обязательным сообщением, а короткое имя `static_assert` давал `<assert.h>`; так написан почти весь существующий код. Ниже `<assert.h>` подключён ради `assert`:

```c
#include <assert.h>
#include <limits.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>

static_assert(CHAR_BIT == 8, "программа рассчитана на 8-битные байты");
static_assert(sizeof(int) >= 4, "int должен быть не меньше 32 бит");

struct Packet {
    uint8_t type;
    uint8_t flags;
    uint16_t length;
    uint32_t checksum;
};
static_assert(sizeof(struct Packet) == 8, "в Packet не должно быть заполнителей");
static_assert(offsetof(struct Packet, checksum) == 4, "checksum должен начинаться с байта 4");

enum Color { RED, GREEN, BLUE, COLOR_COUNT };
static const char *const COLOR_NAMES[] = {"красный", "зелёный", "синий"};
static_assert(sizeof COLOR_NAMES / sizeof COLOR_NAMES[0] == COLOR_COUNT,
              "таблица названий не совпадает с перечислением");

int main(void) {
    printf("%s, пакет %zu байт\n", COLOR_NAMES[GREEN], sizeof(struct Packet));
    return 0;
}
```

Вывод:

```text
зелёный, пакет 8 байт
```

Все проверки выполнились при компиляции и ничего не стоят во время работы. Последняя особенно полезна: если кто-нибудь добавит в перечисление `YELLOW`, а в таблицу названий забудет, сборка остановится с понятным сообщением, а не программа напечатает мусор. Это та же задача, которую решают X-макросы, — но без них.

```c
#include <assert.h>

static_assert(sizeof(long) == 8, "нужен 64-битный long");   // Ошибка компиляции, если long не 64-битный
static_assert(1 + 1 == 3, "арифметика сломалась");           // Ошибка компиляции: static assertion failed

int main(void) {
    return 0;
}
```

## Проверка инвариантов

Для структур данных удобно написать функцию, которая проверяет **все** инварианты, и вызывать её через `assert` в конце каждой изменяющей функции. В отладочной сборке любая ошибка в коде структуры будет поймана сразу после неправильного изменения, а не через тысячу операций:

```c
#include <assert.h>
#include <stdio.h>

typedef struct {
    int items[16];
    int size;
} SortedSet;

static int set_valid(const SortedSet *s) {
    if (s->size < 0 || s->size > 16) {
        return 0;
    }
    for (int i = 1; i < s->size; i++) {
        if (s->items[i - 1] >= s->items[i]) {     // строго по возрастанию, без повторов
            return 0;
        }
    }
    return 1;
}

static int set_insert(SortedSet *s, int value) {
    assert(set_valid(s));                         // предусловие
    int i = s->size;
    while (i > 0 && s->items[i - 1] > value) {
        i--;
    }
    if ((i > 0 && s->items[i - 1] == value) || s->size == 16) {
        return 0;                                 // уже есть или нет места — не ошибка кода
    }
    for (int j = s->size; j > i; j--) {
        s->items[j] = s->items[j - 1];
    }
    s->items[i] = value;
    s->size++;
    assert(set_valid(s));                         // постусловие: инвариант сохранён
    return 1;
}

int main(void) {
    SortedSet s = {{0}, 0};
    int input[] = {5, 1, 9, 5, 3};
    for (int k = 0; k < 5; k++) {
        printf("%d: %s\n", input[k], set_insert(&s, input[k]) ? "добавлено" : "уже есть");
    }
    for (int i = 0; i < s.size; i++) {
        printf("%d ", s.items[i]);
    }
    printf("\n");
    return 0;
}
```

Вывод:

```text
5: добавлено
1: добавлено
9: добавлено
5: уже есть
3: добавлено
1 3 5 9
```

Проверка `set_valid` проходит весь массив — это дорого, но только в отладочной сборке: с `NDEBUG` вызовы исчезнут вместе с `assert`. Повтор элемента здесь — не ошибка программиста, а обычный исход, поэтому о нём сообщает возвращаемое значение, а не `assert`.

<Concept title="assert — документация, которую проверяет машина">

Комментарий «здесь count всегда больше нуля» может устареть, а `assert(count > 0)` проверяется при каждом запуске отладочной сборки. Хорошо расставленные проверки делают ошибку видимой там, где она возникла, — вместо загадочного сбоя далеко от причины. Но это инструмент для поиска ошибок в коде, а не для обработки ошибок данных: в финальной сборке его может не быть.

</Concept>

## Частые ошибки

<CommonMistake title="Действие внутри assert">

`assert(stack_push(&s, x));` — с `NDEBUG` элемент никогда не добавится. Сохраните результат в переменную, а проверяйте переменную.

</CommonMistake>

<CommonMistake title="assert вместо проверки ввода">

`assert(n > 0)` для числа, введённого пользователем, аварийно завершит программу на неверных данных — или, с `NDEBUG`, пропустит их дальше. Неверный ввод — повод для сообщения, а не для `abort`.

</CommonMistake>

<CommonMistake title="static_assert с неконстантным выражением">

`static_assert(len < 100, "…")` для переменной `len` не скомпилируется: условие должно быть известно при компиляции. Для значений времени выполнения — обычный `assert`.

</CommonMistake>

<CommonMistake title="Надежда на вывод перед abort">

`printf` перед сработавшим `assert` может так и не появиться: `abort` не сбрасывает буферы. Отладочную печать направляйте в небуферизованный `stderr`.

</CommonMistake>

## Практика

1. **Найди ошибку: действие внутри assert** — финальная сборка теряет операции.
2. **Найди ошибку: assert вместо проверки ввода** — программа падает на неверных данных.
3. **Найди ошибку: таблица и перечисление** — `static_assert` останавливает сборку.
4. **Двоичная куча с проверкой инварианта** — проверка кучи и вставка с `assert`.

## Итоги

- `assert(условие)` проверяет предположения о коде: предусловия, постусловия, инварианты. При нарушении печатает место в `stderr` и вызывает `abort`.
- `assert` — для ошибок программиста; неверные данные и отказы окружения обрабатывают явно.
- С `NDEBUG` выражение внутри `assert` не вычисляется: никаких действий внутри проверки.
- `abort` не сбрасывает буферы `stdout` — вывод перед аварийным завершением может пропасть.
- `static_assert(условие, "сообщение")` проверяет константные выражения при компиляции: размеры типов, расположение полей, соответствие таблиц перечислениям. В C23 это ключевое слово, и сообщение необязательно; в старом коде — `_Static_assert`.
- Функция проверки инвариантов, вызванная через `assert` после каждого изменения, ловит ошибку в коде структуры сразу.
