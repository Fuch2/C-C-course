## Компилятор вправе убирать обращения к памяти

Стандарт C описывает программу как поведение **абстрактной машины**, а компилятор обязан сохранить только **наблюдаемое** поведение: вывод, работу с файлами и ещё одну вещь, о которой этот урок. Всё остальное он вправе переставлять, объединять и выбрасывать — это правило «как если бы» (as-if), на котором держатся все оптимизации.

Например, в цикле ожидания

```c
int ready = 0;                // где-то кто-то установит 1

void wait_for_device(void) {
    while (!ready) {
        // ждём
    }
}
```

компилятор видит, что внутри цикла `ready` никто не меняет. С оптимизацией (`-O2`) он прочитает переменную **один раз**, и цикл превратится в

```text
if (!ready)
    for (;;) { }              // бесконечный цикл без чтения памяти
```

Для обычной программы это правильно: значение действительно не может измениться. Но если `ready` меняет устройство, обработчик сигнала или другой поток, программа зависнет навсегда. Без оптимизации (`-O0`, как в песочнице курса) всё работает — и тем коварнее ошибка, которая появляется только в финальной сборке.

## `volatile`: каждое обращение — настоящее

Квалификатор `volatile` сообщает компилятору: у этого объекта есть «наблюдатель» снаружи программы. Поэтому **каждое** чтение и **каждая** запись, написанные в коде, должны выполниться — в том порядке и в том количестве, в каком они написаны относительно других обращений к `volatile`-объектам. Компилятор не может держать значение в регистре, объединять записи или выбрасывать «лишние» чтения.

```c
volatile int ready = 0;       // теперь цикл читает память на каждой итерации
```

Обращения к `volatile` — часть наблюдаемого поведения программы, наравне с выводом. Синтаксис такой же, как у `const`, и читается так же — справа налево:

| Объявление                         | Что `volatile`                                                 |
| ---------------------------------- | -------------------------------------------------------------- |
| `volatile uint32_t status;`        | сама переменная                                                |
| `volatile uint32_t *reg;`          | объект, на который указывает `reg` (указатель на volatile)     |
| `uint32_t *volatile p;`            | сам указатель `p`                                              |
| `const volatile uint32_t *status;` | объект меняет кто-то снаружи, а программе писать в него нельзя |

Сочетание `const volatile` выглядит странно, но точно описывает регистр состояния устройства: программа его только читает, а меняется он сам.

## Три законных применения

`volatile` нужен там, где значение объекта меняется **вне обычного хода программы**:

1. **Регистры устройств.** В микроконтроллерах периферия отображена в адреса памяти: запись в «переменную» по адресу `0x40021018` включает светодиод, а чтение другого адреса возвращает текущее состояние кнопки. Каждое обращение — команда устройству. Об этом — следующий урок.
2. **Флаги обработчиков сигналов.** Сигнал может прервать программу между любыми двумя инструкциями.
3. **Локальные переменные при `setjmp`/`longjmp`.**

Разберём два последних — их можно запустить в песочнице.

## Обработчик сигнала

**Сигнал** — уведомление, которое операционная система или сама программа посылает процессу: `SIGINT` приходит при нажатии Ctrl+C, `SIGTERM` — при просьбе завершиться, `SIGSEGV` — при обращении к недоступной памяти. По умолчанию большинство сигналов завершают программу, но функция `signal` из `<signal.h>` позволяет установить свой **обработчик**.

Обработчик вызывается асинхронно — посреди любой операции основной программы. Поэтому стандарт разрешает ему очень немногое: записать значение в переменную типа `volatile sig_atomic_t` и завершиться. Вызывать `printf`, `malloc` и большинство библиотечных функций в обработчике нельзя: сигнал мог прийти, когда основная программа была внутри той же `printf`. Обычный приём — обработчик ставит флаг, а основной цикл его проверяет:

```c
#include <signal.h>
#include <stdio.h>

static volatile sig_atomic_t stop_requested = 0;

static void on_interrupt(int sig) {
    (void)sig;
    stop_requested = 1;               // только флаг — никакого printf
}

int main(void) {
    signal(SIGINT, on_interrupt);
    long long processed = 0;
    for (int step = 1; step <= 10 && !stop_requested; step++) {
        processed += step;
        printf("шаг %d\n", step);
        if (step == 3) {
            raise(SIGINT);            // так программа посылает сигнал сама себе
        }
    }
    printf("остановлено, обработано %lld\n", processed);
    return 0;
}
```

Вывод:

```text
шаг 1
шаг 2
шаг 3
остановлено, обработано 6
```

`raise` посылает сигнал самой программе — здесь это замена нажатию Ctrl+C. Тип `sig_atomic_t` гарантирует, что запись значения не прервётся на середине, а `volatile` — что цикл действительно перечитывает флаг на каждой итерации.

Ещё одна особенность стандартной функции `signal`: перед вызовом обработчика реализация вправе вернуть сигналу действие по умолчанию. Так поступает glibc при компиляции с `-std=c17`: второй `SIGINT` уже завершит программу. Если обработчик должен срабатывать многократно, он переустанавливает себя первой строкой — `signal(sig, on_interrupt);` — а в POSIX-программах вместо `signal` используют `sigaction`, где поведение задаётся явно.

## `setjmp` и `longjmp`

`setjmp` запоминает точку в программе, а `longjmp` возвращается в неё из любой глубины вызовов — как исключения в других языках. Сначала `setjmp` возвращает 0; после `longjmp(env, код)` выполнение снова оказывается в `setjmp`, но теперь он возвращает переданный код.

Подвох в локальных переменных функции, вызвавшей `setjmp`. Если такую переменную изменили **между** `setjmp` и `longjmp`, после возврата её значение по стандарту **не определено**: компилятор мог держать её в регистре, а `longjmp` восстанавливает регистры на момент `setjmp`. `volatile` заставляет хранить переменную в памяти, и значение сохраняется:

```c
#include <setjmp.h>
#include <stdio.h>

static jmp_buf on_error;

static int checked_divide(int a, int b) {
    if (b == 0) {
        longjmp(on_error, 1);          // прыжок назад, минуя все return
    }
    return a / b;
}

int main(void) {
    int pairs[][2] = {{20, 4}, {9, 3}, {7, 0}, {8, 2}};
    volatile int done = 0;             // меняется после setjmp — нужен volatile
    if (setjmp(on_error) == 0) {
        for (int i = 0; i < 4; i++) {
            printf("%d\n", checked_divide(pairs[i][0], pairs[i][1]));
            done++;
        }
    } else {
        printf("деление на ноль после %d успешных операций\n", done);
    }
    return 0;
}
```

Вывод:

```text
5
3
деление на ноль после 2 успешных операций
```

`longjmp` — грубый инструмент: он не вызывает никакой очистки, и ресурсы, выделенные между `setjmp` и `longjmp`, останутся неосвобождёнными. В обычном коде ошибки передают кодами возврата (урок об обработке ошибок). `setjmp`/`longjmp` встречаются в интерпретаторах, разборщиках и библиотеках вроде libpng, где ошибка может случиться глубоко в рекурсии.

## Чего `volatile` не делает

`volatile` не делает операции **атомарными** и не синхронизирует потоки. Выражение `counter++` для `volatile int counter` — это чтение, сложение и запись; два потока, выполняющие его одновременно, теряют обновления. `volatile` также не запрещает процессору переставлять обращения к памяти и не гарантирует, что запись одного ядра сразу увидит другое.

Для потоков в C11 есть `_Atomic` и `<stdatomic.h>`:

```c
#include <stdatomic.h>

atomic_int counter = 0;
atomic_fetch_add(&counter, 1);       // атомарное увеличение из любого потока
```

Если вы встретите `volatile` как средство «потокобезопасности» — это ошибка, распространённая среди тех, кто пришёл из Java или C#, где у этого слова другой смысл.

## Ещё одно применение: очистка секретов

Компилятор вправе выбросить `memset(password, 0, sizeof password)` перед возвратом из функции: после этого массив больше не читается, значит, запись «не наблюдаема». Пароль останется в памяти. Чтобы очистка не исчезла, используют специальные функции (`explicit_bzero` в Linux и BSD, `memset_s` из приложения K стандарта) или запись через указатель на `volatile`:

```c
static void secure_zero(void *p, size_t n) {
    volatile unsigned char *bytes = p;
    while (n--) {
        *bytes++ = 0;                 // каждая запись обязательна
    }
}
```

<Concept title="volatile — договор с внешним миром">

`volatile` говорит компилятору: «у этого объекта есть свидетель за пределами программы — устройство, обработчик сигнала, `longjmp`». Компилятор перестаёт оптимизировать обращения к нему и выполняет их ровно так, как написано. Больше `volatile` ничего не обещает: ни атомарности, ни порядка между ядрами процессора.

</Concept>

## Частые ошибки

<CommonMistake title="volatile вместо атомарных операций">

`volatile int` в многопоточной программе не защищает от гонок. Для общих данных потоков используйте `_Atomic`, мьютексы или другие средства синхронизации.

</CommonMistake>

<CommonMistake title="Флаг сигнала без volatile">

В отладочной сборке всё работает, а с `-O2` цикл ожидания флага становится бесконечным: компилятор прочитал флаг один раз. Флаги обработчиков — `volatile sig_atomic_t`.

</CommonMistake>

<CommonMistake title="printf в обработчике сигнала">

`printf` может держать внутреннюю блокировку или буфер в промежуточном состоянии, когда приходит сигнал. Повторный вход в неё из обработчика приводит к взаимоблокировке или порче вывода. В обработчике — только запись флага.

</CommonMistake>

<CommonMistake title="volatile не у того">

`volatile uint32_t *reg` — значение по адресу меняется извне. `uint32_t *volatile reg` — меняется сам указатель. Для регистров почти всегда нужно первое.

</CommonMistake>

## Итоги

- Компилятор сохраняет только наблюдаемое поведение и вправе убирать, объединять и переставлять обычные обращения к памяти.
- `volatile` делает каждое чтение и каждую запись объекта наблюдаемыми: они выполняются так, как написаны.
- Законные применения: регистры устройств, флаги обработчиков сигналов (`volatile sig_atomic_t`), локальные переменные, изменённые между `setjmp` и `longjmp`.
- `const volatile` — объект меняется извне, но программа в него не пишет; `volatile T *` — указатель на volatile, `T *volatile` — volatile-указатель.
- Обработчик сигнала только ставит флаг; работа выполняется в основном цикле. После срабатывания `signal` может вернуть действие по умолчанию — многократный обработчик переустанавливает себя.
- `volatile` не даёт атомарности и не синхронизирует потоки — для этого `_Atomic` и `<stdatomic.h>`.
