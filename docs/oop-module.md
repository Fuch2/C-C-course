# Объектно-ориентированное программирование в C++

Модуль `cpp-oop` продолжает «Основы C++»: 28 последовательных уроков C++23, в каждом — текст с запускаемыми примерами, не меньше 8 вопросов и 4 задачи (базовая, средняя, «Найди ошибку» и повышенной сложности), всего 112 задач. Три урока содержат этапы сквозного проекта.

## Учебный маршрут

1. `struct` и `class`, конструкторы, `public` и `private`, деструктор, `this`, инкапсуляция и инварианты.
2. Перегрузка операторов (`<=>`, арифметика, `[]`) и печать через `std::formatter` и `std::print`.
3. Композиция и агрегация, наследование, `protected`.
4. `virtual`, `override`, `final`, чисто виртуальные функции, абстрактные классы, виртуальный деструктор, полиморфизм во время выполнения и срезка.
5. Интерфейсы, `std::variant` и `std::visit`, шаблоны и концепты, стирание типа.
6. SOLID и выбор между композицией и наследованием.

Каждый урок собирается из `lesson.mdx` и `lesson.src.mjs` в своём каталоге командой `node --import tsx scripts/lessons/build.ts /cpp-oop/`.

## Проект «Система обработки датчиков»

Карточка проекта связана с уроками:

- `/lesson/oop-pure-virtual`: модели `Measurement`, `Sensor`, `TemperatureSensor`, `PressureSensor`.
- `/lesson/oop-interfaces`: фильтр с инвариантом границ.
- `/lesson/oop-composition-vs-inheritance`: полный `TelemetryProcessor` с готовым консольным адаптером.

`Measurement` — копируемое значение. `Sensor` — минимальный абстрактный интерфейс чтения с виртуальным деструктором. Конкретные датчики закрывают поля и переопределяют чтение. Температура преобразуется как `raw + offset`, давление — как `raw * scale`. `Filter` хранит замкнутый диапазон, отклоняя обратные границы исключением. `TelemetryProcessor` владеет фильтром по значению и датчиками через `vector<unique_ptr<Sensor>>`, запрещает копирование, отклоняет пустого владельца и неправильное число входов. При обработке вызывает каждый источник ровно один раз, фильтрует преобразованные значения и сохраняет порядок результатов. Новый вид датчика не требует изменения процессора.

Данные проекта — целые коды учебного протокола. Значения разных физических величин не суммируются. Подключение оборудования, размерные типы, разные диапазоны для разных величин и транспорт не входят в этот проект. Результат обработки — набор отдельных измерений и число принятых записей.

Ученик самостоятельно заполняет тела методов и переносит свои реализации ранних этапов в итоговый файл. Стартовый код намеренно содержит незавершённые учебные тела методов с исключениями; они не имитируют работу датчиков и не проходят проверки. Авторское решение доступно только по штатному запросу разбора.

## Автоматические проверки

```sh
npm run content:check
npm run typecheck
npm run lint
npm test
npm run test:integration
npm run build
npm run test:oop
npm run test:oop-project
```

`test:oop` (общий скрипт `scripts/lessons/verify-module.ts`) запускает все эталонные решения на GCC и Clang с ASan/UBSan, отрицательные контроли задач «Найди ошибку» и все примеры из текстов уроков. Компиляция и исполнение идут только через `apps/runner` в отдельных ограниченных Docker-контейнерах; режим диагностики задаёт доверенный скрипт. Отчёт — `docs/verification/oop.json`.

`test:oop-project` отдельно проверяет:

- абстрактность базы, публичную подстановку, `final`, виртуальный деструктор и запрет копирования процессора;
- сторонний наследник `Sensor`, счётчик чтений, передачу владения и ровно одно уничтожение каждого датчика;
- независимость результатов повторных вызовов и копий измерений;
- отказ `nullptr`, размеры до первого чтения, исключение источника и освобождение объектов;
- включение границ, точечный диапазон, фильтрацию после преобразования;
- отрицательные контроли: исключённая нижняя граница, фильтрация сырого значения, лишнее чтение;
- отклонение некорректного `override` и наследования от `final` реальным компилятором.

Публичные и скрытые проверки отправленного учеником итогового файла оценивают протокол stdin/stdout. Контрактный Docker-suite проверяет авторскую архитектуру, а не автоматически внедряется в произвольный файл ученика. Для полного ревью ученика дополнительно проверяются структура типов, владение и сигнатуры. Такое разделение не обещает доказать архитектуру по совпадению вывода. API не раскрывает скрытые входы, ожидаемые результаты, эталонный код и ответы quiz.

## Поддержка контента

Источники урока — `lesson.mdx` (текст) и `lesson.src.mjs` (метаданные, вопросы, задачи); `lesson.json` создаёт сборщик `scripts/lessons/build.ts`, проверяя эталоны, примеры, вопросы с выводом и отрицательные контроли в sandbox. Третий этап проекта описан в `content/cpp-systems/projects/oop-telemetry/stages.mjs` и подключается в урок «Композиция или наследование».

Технические правила сверены с проектом стандарта C++: [виртуальные функции](https://eel.is/c++draft/class.virtual), [деструкторы](https://eel.is/c++draft/class.dtor), [доступ при наследовании](https://eel.is/c++draft/class.access.base), [variant](https://eel.is/c++draft/variant), [концепты](https://eel.is/c++draft/temp.concept). Учебные тексты, задачи и исходники авторские; используется C++23.
