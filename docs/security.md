# Границы безопасности runner

Ни web, ни процесс runner не запускают пользовательский бинарный файл на хосте. Компиляция тоже выполняется внутри sandbox: исходник может содержать недоверенные директивы препроцессора. Требуется Docker с Linux-контейнерами и cgroup v2; runner проверяет версию при старте и отказывается работать с неподдерживаемой конфигурацией.

Каждая работа запускается с `--network none`, `--read-only`, `--cap-drop ALL`, `--security-opt no-new-privileges:true`, UID/GID 10001, лимитом памяти 256 МБ без swap, CPU 1, PID 64, открытых файлов 64 и размера файла 16 МБ. `/work` — отдельный tmpfs 64 МБ, `/tmp` — tmpfs 16 МБ с noexec; оба nosuid/nodev. Docker socket и каталоги хоста в sandbox не монтируются. Default seccomp Docker не отключается. Privileged-режим не используется, Docker logging отключён, чтобы вывод не заполнял диск daemon.

Контроль времени и сбор stdout/stderr находятся в доверенном Node.js runner, за пределами namespace пользовательской программы. Единственный запускаемый им внешний процесс — Docker CLI с массивом фиксированных аргументов, без shell. Пользовательский stdout не интерпретируется как управляющий JSON. Компиляция ограничена 15 секундами, исполнение — `timeoutMs` от 100 до 10 000 мс (по умолчанию 2000), вывод каждой фазы — общими 32 КБ stdout + stderr. Время исполнения включает накладные расходы Docker exec. Некорректный UTF-8 заменяется знаком `?` без увеличения байтового бюджета.

Pipeline: приватная временная папка с исходником → новый контейнер → передача исходника через stdin Docker exec → компилятор → бинарный файл внутри `/work` → выполнение → сбор потоков → принудительное удаление контейнера и временной папки в `finally`. Каждый тест задания заново компилируется в отдельном контейнере: между тестами не переносятся процессы, файлы или изменённые бинарные файлы. Исходник ограничен 64 КБ UTF-8, stdin — 16 КБ. Исполняемые файлы никогда не копируются на хост.

Лимиты памяти и процессов обеспечиваются Docker/cgroups. Счётчики `memory.events` и `pids.events` cgroup v2 позволяют отличить исчерпание ресурса от обычной ошибки программы; при исчерпании PID используется также Docker top. Переполнение вывода, SIGXFSZ и превышение cgroup возвращают `resource_limit`. Timeout ограничивает и программы, закрывшие stdout/stderr. При достижении лимита останавливается Docker exec, затем удаляется весь контейнер; проверка ресурсов и cleanup добавляют ограниченное время к HTTP-ответу.

Очередь допускает 2 активные работы и 8 ожидающих; ожидание не дольше 20 секунд. У пакета до 12 тестов общий бюджет 90 секунд. Удаление контейнера проверяется и повторяется до трёх раз; если Docker не подтверждает очистку, runner перестаёт принимать работу. При старте удаляются оставшиеся sandbox только с собственным `RUNNER_INSTANCE_ID`; разные экземпляры должны иметь разные стабильные ID. SIGINT/SIGTERM закрывают очередь, запрещают новые фазы и дожидаются очистки активных работ. `--rm` и ограниченное время жизни начального процесса — дополнительные механизмы, а не замена cleanup. При недоступности Docker исполнение на хосте не применяется.

Внутренний API требует ключ не короче 32 символов, сравниваемый через timingSafeEqual. Пользователь не выбирает образ, команду Docker, mount, переменные окружения или флаги компилятора. Web проверяет Origin изменяющих запросов, объём тела и Zod-схему; интерфейс не использует небезопасный HTML/MDX runtime. Markdown не исполняет JSX или HTML.

**Доверенный runner имеет доступ к Docker daemon.** В Compose он работает с UID 0 для доступа к socket и группой 10001 для чтения секрета, но без capabilities и с read-only root. Это не устраняет полномочия самого socket. Поэтому runner не публикует порт хоста, а данная конфигурация рассчитана на локальное использование. Для многопользовательского публичного сервиса нужна отдельная модель угроз и выделенный узел выполнения; обычный Docker не является абсолютной защитой от уязвимостей ядра.

Тесты проверяют реальное поведение: все пары компилятора/стандарта, ошибки компиляции, stdout/stderr, бесконечный цикл, закрытые потоки, переполнение вывода, рост памяти, fork bomb, невозможность записи в корень, отсутствие Docker socket и внешней сети. Эти тесты подтверждают конкретные ограничения, а не отсутствие любых возможных уязвимостей.

Справочные параметры: [Docker run](https://docs.docker.com/engine/containers/run/) и [Docker Engine security](https://docs.docker.com/engine/security/).
