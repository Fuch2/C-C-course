# Code review проекта «Код / Система»

Дата проверки: 15 сентября 2026 года.

## Область проверки

Проверены структура monorepo, Next.js API, Prisma/SQLite, course engine, публичная фильтрация учебного контента, Docker runner и ограничения sandbox. Также были запущены доступные статические проверки, тесты и production-сборка.

## Найденные проблемы

### HIGH — файловая загрузка курса выполняется внутри Prisma-транзакции — ИСПРАВЛЕНО

Связанные участки:

- `apps/web/lib/progress.ts:11`
- `apps/web/lib/progress.ts:32`
- `apps/web/lib/progress.ts:85`
- `apps/web/lib/progress.ts:99`

`loadCourse()` вызывается после открытия интерактивной Prisma-транзакции. На холодном кэше загрузка, разбор и валидация 212 уроков могут занять больше стандартного таймаута Prisma в 5 секунд.

Проблема проявилась при штатном запуске `npm run test:integration`:

```text
Transaction already closed: A query cannot be executed on an expired transaction.
The timeout for this transaction was 5000 ms.
```

Одновременно первый запрос к `/api/profile` вернул HTTP 500. Одиночные и последовательные прогоны прошли, поэтому ошибка зависит от конкуренции за ресурсы и времени холодной загрузки.

Последствия:

- чтение урока может не сохраниться;
- результат quiz может не сохраниться;
- успешно выполненное упражнение может не обновить прогресс;
- API может вернуть HTTP 500 при повышенной нагрузке или холодном кэше.

Рекомендация: загружать неизменяемую структуру курса до открытия транзакции и передавать в `recordProgress()` и `syncCourseProgress()` готовый список уроков и режим completion. Внутри транзакции должны остаться только операции SQLite. Увеличение timeout допустимо как временная мера, но не устраняет файловый I/O в критической секции.

### MEDIUM — курсор истории может пропускать попытки — ИСПРАВЛЕНО

Связанные участки:

- `apps/web/app/api/lessons/[lessonId]/[action]/route.ts:46`
- `apps/web/app/api/lessons/[lessonId]/[action]/route.ts:50`
- `apps/web/app/api/lessons/[lessonId]/[action]/route.ts:75`
- `apps/web/app/api/playground/[action]/route.ts:30`
- `apps/web/app/api/playground/[action]/route.ts:34`
- `apps/web/app/api/playground/[action]/route.ts:44`

История сортируется только по `createdAt DESC`, а следующая страница выбирается условием `createdAt < cursor`. Если несколько попыток имеют одинаковый timestamp и граница страницы проходит между ними, оставшиеся записи с этим timestamp не попадут ни на одну страницу.

Рекомендация: использовать стабильный составной порядок `(createdAt DESC, id DESC)` и курсор, содержащий оба значения.

### MEDIUM — история попыток не имеет retention или общей квоты — ИСПРАВЛЕНО

Связанные участки:

- `apps/web/app/api/lessons/[lessonId]/[action]/route.ts:268`
- `apps/web/app/api/playground/[action]/route.ts:62`
- `apps/web/app/api/playground/[action]/route.ts:127`
- `prisma/schema.prisma:65`
- `compose.yaml:113`

Каждый запуск сохраняет исходный код, stdin и сериализованный результат. `limitSubmission()` ограничивает частоту запусков, но не общий объём истории. SQLite хранится в named volume без заданной квоты, поэтому база монотонно растёт и при длительном использовании может заполнить диск.

Для локального single-user приложения вероятность ниже, но риск остаётся эксплуатационным.

Рекомендации:

- хранить последние N попыток для каждого упражнения;
- либо удалять попытки старше заданного срока;
- сокращать stdout/stderr старых попыток;
- контролировать свободное место и размер базы.

### LOW — проект не проходит собственную проверку форматирования — ИСПРАВЛЕНО

`npm run format:check` обнаружил 58 файлов, не соответствующих Prettier. Основные группы:

- `content/cpp-systems/algorithms-structures/`;
- `content/cpp-systems/cpp-lifetime/`;
- `content/cpp-systems/cpp-oop/`;
- `scripts/author-cpp-fundamentals.mjs`;
- `scripts/author-oop.mjs`.

Проблема не влияет на runtime, но делает общий quality gate красным.

### LOW — проектные инструкции расходятся с текущим состоянием — ИСПРАВЛЕНО

- `AGENTS.md:5` указывает 7 модулей и 164 урока.
- `README.md:3` и фактическая проверка показывают 9 модулей и 212 уроков.
- `TODO.md:21-27` помечает модуль «Основы C++» незавершённым, хотя README описывает его как опубликованный.

Устаревшие инструкции могут направлять разработчиков и автоматизированных агентов по неверным инвариантам.

## Безопасность и положительные результаты

- Не найдено прямого пути выполнения пользовательского C/C++ на хосте.
- Docker вызывается через `spawn()` с массивом аргументов, без shell-интерполяции: `apps/runner/src/sandbox.ts:95`.
- Sandbox использует отдельный контейнер для каждого теста.
- Применяются non-root UID, `--network none`, read-only root, `cap-drop ALL`, `no-new-privileges`, а также ограничения PID, CPU, RAM, размера файлов и вывода.
- При неподтверждённом удалении контейнера runner блокирует новые запуски.
- Hidden tests, эталонные решения, пояснения решений и правильные ответы quiz исключены из публичного представления урока.
- Результаты скрытых тестов не раскрывают stdin, expected, actual или stderr.
- API учебных ресурсов проверяет части пути, допустимое расширение и итоговый путь через `realpath`, защищаясь от directory traversal.
- Runner использует bearer-токен с `timingSafeEqual` и не публикуется напрямую на host port в Compose.
- Web в стандартной конфигурации Compose привязан только к `127.0.0.1`.
- Небезопасная интерполяция пользовательских данных в SQL не обнаружена.
- Production-секреты в исходниках не обнаружены; содержимое `.env` не читалось.

## Условие безопасной эксплуатации

Приложение спроектировано как локальная установка для одного пользователя и не имеет аутентификации web API. Проверка `Origin` является дополнительным CSRF-барьером, но не заменяет аутентификацию.

Если web-сервис будет опубликован во внешней сети, любой клиент сможет работать с общим локальным профилем и запускать код через runner в рамках установленных лимитов. Для сетевого развёртывания необходимы полноценные authentication, authorization, CSRF protection и per-user quotas.

Runner имеет доступ к Docker socket и поэтому является доверенной границей с фактическими полномочиями Docker daemon. Прямой путь передачи пользовательских данных в команды управления Docker не найден, однако для усиления изоляции желательно использовать отдельный rootless Docker daemon, VM или специализированный worker.

## Итог внесённых исправлений

Все найденные проблемы устранены. Ключевые изменения:

- Транзакции прогресса: `loadCourse()` вызывается до открытия интерактивной Prisma-транзакции, а подготовленный snapshot курса передаётся в `syncCourseProgress()` и `recordProgress()` обязательным параметром. Внутри транзакций больше нет файлового I/O. Затронуты `apps/web/lib/progress.ts` и `apps/web/app/api/lessons/[lessonId]/[action]/route.ts`.
- История попыток: добавлен серверный helper `apps/web/lib/attempt-history.ts` с opaque-курсором `(createdAt, id)`, составной сортировкой и атомарным retention на 100 последних попыток для каждого упражнения. Общий контракт применён в API урока и playground. `ExerciseStats.attempts` остаётся пожизненным агрегатом.
- Схема и миграция: индекс `Attempt` заменён на `[userId, lessonId, createdAt, id]`; миграция `202609150001_attempt_history_retention` однократно обрезает существующую историю до 100 записей в каждой группе.
- Quality gate: `npm run format:check` добавлен в агрегированный `npm run check`; весь проект приведён к Prettier.
- Документация: `AGENTS.md`, `README.md` и `TODO.md` синхронизированы с фактическими 9 модулями и 212 уроками.
- Дополнительно исправлен предсуществующий баг `scripts/verify-solutions.ts`: фиксированная ёмкость очереди 500 не покрывала 526 проверок (263 упражнения × 2 компилятора), из-за чего полный offline-прогон падал с 429. Ёмкость теперь вычисляется из числа задач.
- Независимый security-аудит нового кода подтвердил: курсор не может подменить `userId`/`lessonId`, SQL-инъекций и prototype pollution нет, массовое удаление через пользовательский ввод недостижимо. Найденный LOW-дефект (календарно-невалидная дата в курсоре давала HTTP 500 вместо 400) исправлен явной проверкой `Number.isNaN(createdAt.getTime())`.

## Ограничения review

- Текущая директория не является Git-репозиторием, поэтому review выполнен по полному актуальному состоянию проекта, а не по PR-диффу.
- Динамические Docker-тесты sandbox не были повторены, поскольку Docker Desktop находился в состоянии pause.
- Оценка sandbox основана на статическом анализе кода, Compose и существующих тестов; её следует подтвердить полным `npm run test:runner` на Docker host с cgroup v2.

## Вердикт

Архитектура приложения и особенно ограничения Docker sandbox в целом продуманы. Критичных уязвимостей или прямого sandbox escape не обнаружено. Главный дефект — файловая загрузка курса внутри Prisma-транзакции: он уже приводит к сбоям штатного integration-набора и должен быть исправлен в первую очередь.
